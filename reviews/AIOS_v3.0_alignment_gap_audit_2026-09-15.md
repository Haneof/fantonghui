## 1. 明确判词：会在哪个里程碑彻底卡死？

答案不是一个里程碑，是**四种不同性质的卡死，发生在四个不同位置**。必须分开说，否则会把"能跑通"误当成"对齐了"。

### 判词一：**M0.1 无法启动 —— 治理级卡死（现在就已经卡住了）**

M0 gate 已于 2026-09-14 判定 PASS（`reviews/M0/M0-001_final_PASS_2026-09-14.md` … `M0-022_chief_gate_ready_2026-09-14.md`），契约由 `schemas/r2/m0_contract_snapshot.json` + `tests/unit/contracts/test_m0_schema_snapshot.py` **冻结并自动强制**。

而 v3.0 / R3 要求的以下对象**全部不在冻结的 `ObjectType` 枚举中**（现有 20 类：observation / entity / relation / dimension_definition / dimension_membership / dimension_derivation / claim / evidence_set / event / summary / goal / dependency / task / wake / session / action / outcome / operation_experience / tool_proposal）：

| v3.0 要求的一等对象 | 出处 | 冻结契约状态 | 直接后果 |
|---|---|---|---|
| `Prediction` | 第五十~五十三条、R3 §3.1 | **不存在**。`prediction` 仅是 `ClaimType` 的一个枚举值；`Claim` 模型无 `expected_change` / `time_window` / `verification_state` / `actual_outcome_ref` | **R3-03（预测证伪闭环）物理上无法实现**，而它是 gate 验收项 |
| `LifeChapter` | 第二十九条、R3 §4.4 | **不存在** | **R3-05（相变与章节归档）物理上无法实现** |
| `CockpitManifest` | 第八十四条 | **不存在** | 单次看盘无契约承载 |
| `TriggerCriteria` | 第八十六条 | **不存在**；`Task` 只有 `next_wake_at`/`deadline`/`recurrence`/`dependency_refs` | 条件驱动任务**无法表达** |
| `SpeakerIdentity`（声纹） | 第三十三条之 3 | **不存在** | 声纹绑定与 6 个月淘汰**无法实现、无法测试** |
| `DeliveryLedger` | 第九十八条之一 FSM | **不存在** | 投递黑洞（见 §7） |
| `ComputeBudget` | 第七十六条（散文） | **不存在**；`ErrorCode.BUDGET_EXHAUSTED` 已定义但**无人抛出** | 零资源治理 |

**卡死形态**：要加这些对象 → `test_m0_schema_snapshot.py` 判红；不加 → v3.0 不可实现。**这是一条双向死锁，且它就在项目当前位置。** 第一百一十条之 3 明确规定修改基础契约"必须以正式架构变更处理，不能由单个开发任务顺手改变"——**所以必须先出 M0.1 契约修正案，否则 M1 开工即违宪。**

### 判词二：**M2 —— 宪法级硬冲突首次变为不可同时满足**

M2 是"主动运行闭环"，也是 v3.0 运行机制（第二十三章触发、第二十四章认知工作台）的落地点。这里有**两条互相矛盾的最高指令**：

- 【总工任务书】M2-010 §I 明确禁止：**"禁止把固定调用顺序写进工具层"**；M2-012 §B：**"不能退化成固定十三步脚本"**；M2-012 §D：**"系统提示只规定责任/约束/工具，不强制先看哪个维度"**；M2-012 §G 测试：**"同场景模型可以先搜关键词或先看当前窗口"**；M2-012 §I：**"禁止'每次必须先读全局人生'"**。
- 【V3宪法】第八十四条之 2：心智启动四步序 **"顺序绝对不可颠倒！"**
- 【V3宪法】第一百一十条之 14（15 条不可变更基础契约）：**"AI 可以自主选择世界操作路径，不被固定认知流水线限制"**；第八十六条之 3：**"绝对不得强制固定的维度阅读顺序"**；R1-01：**"AI 可以跳过无必要工作项仍正确完成任务"**。

**M2-012 完全符合第 14 条基础契约与第八十六条，同时完全违反第八十四条。这不是任务书写错了，这是 v3.0 自己打自己**（详见配套报告 C3）。**编码代理拿到 M2-012 与第八十四条会无法同时满足，只能任选一条，另一条判违宪。**

### 判词三：**M4 —— 技术性硬卡死（第一次真正跑不动）**

M4 是"连续 30 天虚拟人生"。M4-001 的验收标准原文只有一句：**"符合虚拟世界规范 5.2"**。而【测试规范】§5 的负载档位是：

| 尺度 | 建议观测规模 |
|---|---|
| 1 天 | 2,000–10,000 条 |
| **1 个月** | **60,000–300,000 条** |
| 1 年 | **70 万–360 万条** |

**我对真实 schema 的实测结果**（`reviews/evidence/`，复刻 `sqlite_store.py::_initialize()` 逐字一致）：

| as_of revision | fetchall + Python 去重 + 逐行 json.loads | **峰值 RSS** |
|---|---|---|
| 100,000 | 1.24 s | 463 MB |
| **300,000** | **3.94 s** | **1,360 MB** |
| 1,000,000 | — | **MemoryError（3.2 GB 上限即崩）** |

内存放大系数实测 **4.53 KB/对象**（payload 仅 649 B）。而 `Session.snapshot_world_revision` 已在冻结契约中，意味着**每次会话都要拍一次世界快照**，这条 O(N) 时间 + O(N) 内存的路径就在关键路径上。

**结论：M4 要求的最小档位（60,000 条）勉强可跑，最大档位（300,000 条）单快照 1.36 GB / 3.94 s，M7 要求的 360 万条必然 OOM。**

**更严重的排期错误**：唯一处理规模的 Issue 是 **M7-002「规模、索引、世界版本和存储增长基准」——排在倒数第二个里程碑**。它的验收是"100 万对象后'近 7 天某实体相关事件'仍可在设定目标内返回"。**这个测试会在 M7 才发现 M4 就已经崩了的东西。** 规模基准必须前置到 M1（见 §9 的 M1-020）。

同时 M4 还需要：跨日的羁绊厚度、承诺/内疚清单、沟通风格进化、分寸感——**这些对象在 M3-010 里全都没有**（M3-010 只做 `subject=ai` 的 Action/Outcome/Task/Claim/Event + `self.inspect`，即 v2.0 的"AI 行为日志"，**不是 v3.0 第十九条的五个 AI 世界种子维度**）。所以 **V3-01 / R3-07 / V3-02 在 M4 无法度量**。

### 判词四：**M8-003 —— 项目级卡死（真正的死亡点）**

M8-003 是"是否进入真实设备/真实用户原型的 Gate"。**走到这里团队会发现：柔性手环、马达震动 FSM、骨传导、三层 UI、23cm 态势画布、技能插件、端侧音频/视觉管线、功耗模型——在 86 个 Issue 中命中数全部为 0。** 【架构规划】§4 明确写的是 **"控制台：浏览器界面"**，【工作台规格】§2 画的是 **PC 多面板桌面布局**（紧急事项条 / 任务面板 / 世界浏览区 / 证据与主张区 / 操作轨迹）。

**也就是说：按现有规划一路实施到 M8，交付物是一个"v2.0 的 PC 桌面认知工作台"，而宪法定义的产品是一个"零 UI 的柔性全屏随身手环"。这是两个不同的产品。**

> **总判词**：
> **项目不会因为"代码跑不起来"而卡死——它会一路绿灯通过 M1、M2、M3 的全部 gate（因为这些 gate 的验收编号是 v2.0/R2 世代的），在 M4 撞上第一个技术硬墙（快照 OOM + 长对话上下文溢出），然后在 M8-003 撞上真正的项目死亡点：交付物与宪法产品定义不是同一个东西。**
> **最危险的不是卡死，是"全部 PASS 但交付错产品"。** 而这一点已经被下面这个编号冲突**制度性地掩盖了**。

## 2. 逐项审查（1）：唤醒与看板机制 —— **部分对齐 + 顺序冲突 + 无预算**

**核对结论：不是"仍在按老式逐步对话设计"那么简单，实际是三件事叠加。**

### 2.1 已经对齐的部分（要肯定）

【工作台规格】§3 的"唤醒时的初始工作包"11 个字段（当前时间 / 可见世界版本 / 唤醒原因 / 紧急事项 / 当前世界 / 任务摘要 / 承诺 / 未确认认知 / AI自身状态 / 数据质量 / 操作范围）**与宪法第八十四条之 3 的看板核心要素高度吻合**，且比宪法更细（多了"数据质量"与"未确认认知"）。【总工任务书】M2-009 `workspace.open` 把它落成了 `WorkspaceSnapshot` Pydantic 契约，§I 还明确禁止"把自然语言大摘要作为唯一入口"。**这条是对齐的，而且质量不错。**

【架构规划】§7.1 的主链 `新资料 → 更新基础世界 → 机械触发/到期/巡检 → 唤醒AI → 自主调查 → 形成认知 → 判断帮助 → 行动或沉默 → 留下后续任务` 与宪法第三十四条的主链一致。

### 2.2 冲突一：**十三步循环把顺序写反了**

【工作台规格】§10「十三步认知循环如何落实」的顺序是：

```
1. 唤醒来源  2. 紧急程度检查  3. 当前世界检查  4. AI自身状态与承诺检查
5. 观察计划  6. 工具操作  7. 认知产出  8. 世界更新  9. 帮助决策
10. 后续任务  11. 行动与等待  12. 结果回写  13. AI自身更新
```

【V3宪法】第八十四条之 2 的四步序是：

```
① 照镜子（自省我是谁与底线）  ② 校准羁绊模型  ③ 定态度与语调  ④ 审视用户世界与触发源
```

**十三步的第 1~3 步（唤醒来源 → 紧急程度 → 当前世界）恰好是四步序的第 ④ 步；十三步的第 4 步（AI自身状态与承诺）才是四步序的第 ①②步。** 也就是说：**工作台规格把"看世界"排在"看自己"之前，宪法把"看自己"排在"看世界"之前，顺序完全颠倒。**

【工作台规格】§2 的界面布局同样如此：左列第一格是"本次唤醒 / 触发来源 / 合并次数"，右列才是"AI自身当前状态 / 角色、承诺、经验"。**面板的物理排布也在强化错误的顺序。**

**而 M2-012 站在第三边**：它既不按十三步也不按四步序，而是"模型可多轮 tool calls / 不强制先看哪个维度 / 禁止固定十三步脚本"。**于是同一件事有三套互斥规定**：工作台规格（十三步，看世界在前）、宪法第八十四条（四步序，看自己在前，不可颠倒）、任务书 M2-012（都不许固定）。**编码代理拿到这三份文档，唯一理性的行为是随便选一个。**

### 2.3 冲突二：**"单次交付"没有 token 预算，就不是单次交付**

宪法第八十四条之 1 严禁的是 **"系统发提示词 → AI 说好的我知道了 → 再发下一段"** 这种系统侧多轮握手。M2-012 的"模型可多轮 tool calls"是 **AI 侧主动调用**，严格讲**不违反**第八十四条之 1（宪法第九十一条的原子操作清单本身就假定 AI 会调工具）。**这一条要还给任务书，它没有错。**

**但真正的冲突在别处**：M2-009 §C 只说"工作包只给相关摘要 + 索引入口"，§G 测试是"有 500 条相关历史只返回摘要 + 查询入口"——**没有任何 token 上限**。而宪法第八十五条同时要求"1500 token 活跃窗口"和"1 秒首字响应"。**一个没有 token 预算的 Manifest 不可能是 single-shot**：它可能返回 200 token，也可能返回 40,000 token，取决于世界状态。**"单次看盘"的本质不是"只调用一次 `workspace.open`"，而是"这一次调用的输出必须有确定的、分层的、可预算的 token 上限"。这一层含义在全部四份文档中完全缺失。**

### 2.4 缺失：四步序不可测试 → 必然退化

宪法第一百一十四条的验收项（A 系列 / R1 / R2 / R3 / V3）**没有任何一条能验证四步序被执行**。一个只输出 1~3 句话的系统，其内部是否真的先自省后看世界，**从外部行为不可观测**。【工作台规格】W01~W12 也没有。**没有可观测性 = 没有强制力 = M2 之后它必然退化成一段被忽略的 system prompt。**

### 2.5 裁定

| 项 | 裁定 |
|---|---|
| 看板字段内容 | **部分对齐**（11 字段 vs 宪法 5 要素，实际更完整） |
| 看板 token 预算 / KV-cache 字段序 | **完全缺失** |
| 心智启动顺序 | **逻辑冲突（三套互斥规定）** |
| 十三步循环 | **v2.0 遗留，与第八十四条顺序颠倒，且引用了错误的宪法条号（第三十四条）** |
| 四步序可测试性 | **完全缺失（零验收项）** |
| 单次交付 vs 多轮 tool loop | **不冲突**（宪法禁的是系统侧握手；任务书 M2-012 无罪） |

## 3. 逐项审查（2）：任务调度与 Token 浪费防范 —— **架构死角，条件过滤引擎不存在**

**核对结论：M2-005/M2-006/M2-002~004 里没有任何一处定义条件过滤引擎。会发生严重空转，而且宪法自己还额外要求了一个空转源。**

### 3.1 现状：调度器是纯时间驱动

【总工任务书】M2-005 §C 原文：**"scheduler 根据 `next_wake`/`deadline`/`recurrence` 生成 Wake"**。M2-006 补齐的是**时间语义**（scheduled 绝对/相对、deadline 提前检查、recurring 父任务 + `occurrence_id`、todo 必须 `next_review`、follow-up 绑定原 Action/Outcome、停机后 catch-up/skip/merge/expire）。

**这四类里只有"时间"一类。** 宪法第八十六条之 2 要求的四类激活条件是：

| 宪法要求的条件类型 | 任务书是否实现 | 落点 |
|---|---|---|
| `time_reached` | ✅ 已实现 | M2-005/M2-006 `next_wake_at`/`deadline`/`recurrence` |
| `dependency_ready` | ⚠️ 部分 | `Task.dependency_refs` + 状态机 `BLOCKED`；**但"依赖完成后自动转 READY"只在 M2-005 §G 测试里以"等待证据后新资料到达变 READY"一句带过，无引擎设计** |
| `event_occurred` | ⚠️ **在另一套机制里** | M2-007 的 `watch.register`（机械条件 DSL + `on_match`/`on_timeout`）——**但 Watch 是独立于 Task 的对象，只服务"观察任务/验证任务"两类，不是所有 Task 的通用激活条件** |
| `context_matched` | ❌ **完全不存在** | 宪法举例"检测到用户进入特定商圈 GPS、心率持续处于低谷、进入独自独处静默期"。**没有任何 Issue、没有任何模块负责情境匹配；模拟器（M2-014）也不生成 GPS 围栏/独处状态这类情境信号** |

**接口层同样缺失**：任务书 M2-005 §F 的接口是 `task.create/update/query/cancel/transition`。宪法第九十一条要求的是 `task.create_conditional(condition, action)` 和 **`task.inspect_ready()`**。**`task.inspect_ready` 这个"只返回已就绪任务"的核心原语，在全部四份文档中零命中。**

【工作台规格】§5.5 的 `task.query` 输入是"状态、类型、人物、App、时间条件"——**注意：可以按状态查、按时间查，但不能按"是否已满足激活条件"查**。§7.1 的 Task 工程字段清单（21 个字段）与冻结的 `Task` 模型一致，**同样没有 `trigger_criteria`**。

### 3.2 会发生什么：三个空转源

**空转源 1（任务书自带）**：【工作台规格】§7.2 对"待办任务"的规则是 **"必须进入定期任务盘点或相关情境唤醒"**；M2-006 §C 是 **"todo 必须 `next_review`"**。**"定期盘点"就是宪法第八十六条明令禁止的"无脑遍历"**——一个用了两年、积累了 300 条待办的系统，每次盘点都要把 300 条塞进上下文。**这一条是任务书主动写进去的空转源，而宪法明令禁止它。**

**空转源 2（宪法自带，任务书完全没实现）**：宪法第八十条之 1 的"长平稳心跳"——**每 3~5 小时触发一次轻量心跳唤醒，驱动 AI 主动找用户聊天**。这在【总工任务书】86 个 Issue 中 **`心跳` 与 `巡检` 双双零命中**；M2-002 的机械触发只有 6 类（数值幅度、趋势、状态切换、持续时间、关键词/实体、长时间无更新），**"长时间无更新"是"数据源停摆"告警（【工作台规格】§6 明确区分三种情况），不是"长平稳主动探寻心跳"**。两者语义完全不同：前者是"来源不上报了，可能坏了"，后者是"一切正常，但该去关心一下用户内心了"。

**而这正是最大的 token 黑洞**：按配套报告实测，心跳每 3 小时一次 = 240 次/月 ×（四步序 600~1200 tok + 四层上下文 1500~4000 tok + 输出 150 tok）= **0.54M ~ 1.28M token/月，无条件固定开销**。宪法第八十六条宣称"条件驱动零浪费"省下了任务遍历，**却没管住自己第八十条新造的这头大象**。

**空转源 3（更糟）**：宪法第八十条之 2 要求 **"AI 醒来后必须第一优先研判用户当前是否方便"**，判据是"工作时间、深度学习、会议专注期、驾驶中、深夜睡眠"。**这五个判据全部是机械可判的**（日历 + IMU 运动状态 + 时段 + 驾驶检测 + 最近"别烦我"计数），**却被安排给了 LLM**。也就是说：**为了决定"要不要打扰用户"，系统先花掉一次完整的四步序 + 四层上下文。** 这直接违反宪法自己的第七十七条（"触发器负责叫醒 AI，不负责理解人生"）与第七十九条（机械机制清单）。

### 3.3 裁定

| 项 | 裁定 |
|---|---|
| 条件过滤引擎 | **架构死角：不存在** |
| `task.inspect_ready` / `task.create_conditional` | **完全缺失** |
| `context_matched`（情境匹配） | **完全缺失，且模拟器不产出情境信号** |
| `event_occurred` | **机制割裂**：Watch 与 Task 两套对象，无统一 `TriggerCriteria` |
| 待办定期盘点 | **任务书主动引入的空转源，与第八十六条直接冲突** |
| 长平稳心跳 | **宪法有、任务书零命中**（幽灵需求：架构规划 §7.1 与测试规范 §6 都提"巡检"二字，但无任何模块/任务/场景定义它） |
| 心跳的机械方便度闸门 | **完全缺失** |
| Token 空转风险 | **严重。三个空转源叠加，且无任何运行时预算对象可拦截** |

## 4. 逐项审查（3）：上下文管理与真人老友响应延迟 —— **零 Issue，长对话模块无法工作**

**核对结论：现有任务书中没有任何一个 Issue 负责"后台流式萃取"或"前台活跃窗口组装"。不是"写得不够细"，是这两个组件在整个工程体系里不存在。**

### 4.1 命中矩阵

对【总工任务书】全文检索 `滑动窗口` / `Rolling Window` / `流式萃取` / `增量切片` / `1500`：**全部 0 命中**。
检索 `首字` / `延迟` / `latency` / `TTFT` / `1 秒`：**全部 0 命中**。
检索 `上下文`/`prompt` 的命中全部是 M2-009 §B"模型不应每次从空白 prompt 开始"与【架构规划】C10"上下文接续"这类**跨会话接续**语义，**不是同一会话内的窗口管理**。

### 4.2 现有 Issue 实际覆盖的是什么

| Issue | 实际做的事 | 与第八十五条的关系 |
|---|---|---|
| M2-009 `workspace.open` | 组装唤醒初始工作包（摘要 + 索引入口） | 对应宪法第八十五条之 3 的**第二层"工作状态层"**，但**无 token 预算** |
| M2-011 Session 快照/Checkpoint | `snapshot_world_revision` + 已提交操作 + 未决问题 + 下一步；中断恢复 | 对应**跨会话**接续（R1-10/W12），**不是同会话内的长对话流水线** |
| M2-012 AI Worker 工具循环 | 首包 `workspace.open` → 模型多轮 tool calls → 达预算 checkpoint | 唯一提到"预算"的地方，但**预算未定义、未量化、无对象承载** |
| M1-012 世界搜索 | `world.search` + `follow_links` | 对应**第三层"主动检索记忆层"**的召回入口，但是**串行多跳**（见 §5） |

**第八十五条的三层里：第一层（前台活跃滑动窗口）零覆盖、第二层（后台增量流式萃取）零覆盖、第三层（按需联想回捞）只有串行搜索入口。** 四层上下文组装架构（触发指针层 / 工作状态层 / 主动检索记忆层 / 近期对话缓冲层）**没有任何 Issue 负责把它组装起来并施加预算**。

### 4.3 没有这些 Issue，长对话模块能不能工作？—— **不能，且失败方式很难看**

宪法第八十五条自己承诺的场景是"连续聊了 50 轮、上万字"。按现有任务书实施，实际会发生：

1. **上下文单调增长直到溢出**：M2-012 的循环是"首包 workspace.open + 模型多轮 tool calls"。**没有任何组件负责裁剪历史轮次**。50 轮 × 每轮工具返回的 refs/coverage/warnings = 上下文线性膨胀。唯一的刹车是 M2-012 §C 那句"达到预算时 checkpoint"——**但预算不存在**（无 `ComputeBudget` 对象、`BUDGET_EXHAUSTED` 无人抛出）。
2. **checkpoint 不是解决方案**：M2-011 的 checkpoint 保存的是"已提交 refs / pending operations / tasks created / unresolved questions"——**这是给中断恢复用的，不是给上下文裁剪用的**。它保存的是操作事实，不是对话语义。用它续接会话，AI 恢复的是"我做过什么"，**不是"我们聊到哪了"**。
3. **于是只剩两条路，两条都违宪**：
   - (a) 让上下文涨到模型上限 → **违反第八十五条"日常会话严禁盲目灌入全量长上下文"**，且 1 秒首字彻底不可能（prefill 随长度线性增长）；
   - (b) 让模型自己截断 → **就是宪法痛骂的"5 轮金鱼记忆的弱智"**，且违反第一百一十四条"AI 操作可回放"（截断不可回放）。
4. **后台萃取缺失的二阶后果**：即使前台窗口做了，没有后台增量萃取，**聊过的内容不会沉淀成 Claim 和 EventAnchor**。宪法第八十五条要求"绝不积压到对话结束"。积压的后果是：一次 50 轮对话结束后要做一次巨型萃取（数万 token 单次调用），**而这正好落在用户下一次开口的 1 秒响应窗口里**。

### 4.4 一个任务书与宪法都没看见的竞态

即使把两个 Issue 都补上，还有一个**结构性竞态**：前台只留 5~8 轮，后台"每隔几轮或话题切换时"异步萃取。**用户在第 12 轮引用第 3 轮的内容，而萃取器还没处理到第 3 轮** → 前台窗口里没有、后台还没落库、联想召回查不到 → **金鱼脑**。

修法（配套报告已给）：① **原始滚动缓冲区必须长于语义窗口**（原始 30 轮 / 语义 5~8 轮），召回可先查未萃取的原始缓冲；② **萃取必须幂等 + 带 watermark**（`session_id + turn_index + content_hash`），复用已有的 `idempotency_key` 机制。**这两条在四份文档中都不存在。**

### 4.5 裁定

**完全缺失（零 Issue）。这是 7 项审查中缺口最彻底的一项——不是设计落后，是设计不存在。**

## 5. 逐项审查（4）：世界检索引擎 —— **旧设计无法支撑复合语义定位，且实测会静默返回 0 命中**

**核对结论：M1-012 / M1-010~013 确实是"单关键词 + 逐步过滤"设计，与第八十九条正面冲突；更严重的是它指定的技术栈（SQLite FTS5）对中文 2 字词实测 0 命中，而它的验收测试恰好全是 2 字词。**

### 5.1 设计层冲突：任务书要求"分阶段"，宪法禁止"分阶段"

【总工任务书】M1-012 §A：**"建立关键词/实体/事件/关系/概念的横向搜索入口，支持逐步缩小范围"**
§G 必须编写的测试：**"搜索'妈妈'返回实体候选+文本命中；'妈妈+生日+礼物+近3年'**逐步过滤**"**
【工作台规格】§5.3：**"复杂查询必须支持**分阶段扩大召回**。例如先按人物与关系找事件，再补充关键词、时间和原话。"**
【总工任务书】M2-010 §G 测试：**"AI 可从'生日'搜索 → 妈妈实体 → 历年事件 → 礼物 → 财务维度"**（**4 跳串行链**）

【V3宪法】第八十九条之 1：**"**严禁把复合意图割裂为多次低效的单词检索**"；"系统原生支持多关键词联合共现检索"；"检索引擎通过全局世界超链接拓扑网络，**直接计算多关键词在实体、事件与 Claim 节点上的交集与共振密集区**"**

**这是正面对撞**：任务书与工作台规格把"分阶段/逐步过滤/多跳串行"写成**必须实现的验收测试**，宪法把同一行为写成**严禁**。而且宪法第九十一条要求的原子操作 `world.co_search(keywords=[...])`、`world.navigate(pointer)`、`world.focus(entity_id)` **在任务书 M1-012 §F 与 M2-010 §C 的接口清单里全部不存在**（只有 `world.search`、`world.follow_links`、`entity.expand`）。

**后果量化**：M2-010 的 4 跳串行链 = 4 次工具往返。按配套报告实测的延迟预算，每次检索 150~600 ms，4 跳 = **600~2400 ms，单这一项就吃光或超过 1 秒首字预算**。而 `co_search` 单次交集 = 1 次往返。

### 5.2 技术层硬失效：指定的技术栈对中文不工作

M1-012 §D 技术指导原文：**"第一版 SQLite FTS5 + Entity alias index；语义向量作为可替换适配器，不是 M1 阻塞项。"**
M1-014 §D：**"SQLite FTS5/普通 B-tree；提供 rebuild CLI。"**

**我对真实数据实测（SQLite 3.40.1，1,000,000 行，975 MB）**：

| 索引方案 | 建索引 | `MATCH "妈妈"` | `MATCH "妈妈" AND "生日" AND "礼物"` | `MATCH "按摩仪"`(3字) |
|---|---|---|---|---|
| `tokenize='unicode61'`（FTS5 默认） | 11.6 s / +262 MB | **0 命中** | **0 命中** | **0 命中** |
| `tokenize='trigram'` | 18.6 s / +452 MB | **0 命中** | **0 命中** | 857,142 命中 / 27.9 ms |
| `LIKE '%妈妈%'` 地面真值 | — | **892,857 命中** | 892,857 命中（3.36 s 全扫） | — |

**根因**：`unicode61` 按空白/标点切词，连续汉字整段成为**一个 token**，任何子串查询 0 命中；`trigram` 需要 **≥3 字符**查询。

**而 M1-012 §G 的验收测试用的关键词是"妈妈"、"生日"、"礼物"——全部 2 字。宪法第八十九条举的三个例子 `[妈妈,生日,礼物]`、`[老王,借钱,争执]`、`[加班,熬夜,心悸]`——9 个关键词全部 2 字。** 这不是边缘情况，**这是中文的常态**。业界已反复记录同类静默失效，并有 issue 明确验证"trigram 下 3 字以上 CJK 可匹配，**但 2 字查询仍返回 0**，而 2 字词是中文的常见情形（会议、文档、配置、要求、方案）"[2](https://github.com/openclaw/openclaw/issues/140736)[1](https://github.com/thedotmack/claude-mem/issues/3801)。

**最危险的地方在于它会"部分通过"**：M1-012 的索引是 **FTS5 + Entity alias index** 两路。`Entity.canonical_name` / `aliases`（**冻结契约里已有这两个字段**）走的是 alias 精确匹配，**"妈妈"作为实体别名会命中**。于是验收测试"搜索'妈妈'返回实体候选 + 文本命中"会显示：实体候选 ✅ 有、文本命中 ❌ 空。**评审者极可能把"实体候选有了"当成通过，而文本检索通道其实是死的。** 等到 M4 用户说"我最近老是喘不上气"而历史里存的是"胸闷/气短"时，**两路都空**（alias 不匹配、FTS 不匹配、向量被 M1-012 明确降级为"不是 M1 阻塞项"），AI 才会表现出金鱼脑——**而那时已经是 M4，回溯定位会指向 M1-012，但 M1-012 的 gate 早就 PASS 了**。

### 5.3 M1-014 是唯一提到索引治理的 Issue，但它恰好漏掉了唯一致命的那一项

M1-014「索引水位、重建与 STALE_INDEX」设计得很好：每类索引保存 `last_world_revision`、查询返回 `index_watermark`、落后且 `strict_freshness` 则返回 `STALE_INDEX` 或回退主库、提供 rebuild CLI、§I 禁止"把向量索引当唯一真相存储"。**这是一份专业的索引治理设计。**

**但它治理的是"索引是否新鲜"，完全没有治理"索引是否有能力回答这个查询"。** 一个 CJK 分词失败的 FTS5 索引，其 `index_watermark` 会显示完全新鲜、rebuild 会成功、`STALE_INDEX` 永远不触发——**它只是永远返回 0 命中**。

**这正是必须补进契约的一条铁律**：检索接口必须区分 `NO_MATCH`（确实没有）与 `INDEX_INCAPABLE`（本索引结构上无法回答）。【工作台规格】§4 已经写了 **"空结果必须区分'确实没有记录'和'查询未完成/来源缺失'"** —— **这条原则完全正确，但它的两个枚举里没有"索引无能力"这一类**，而且它没有对应的验收项。**把这句已有的正确原则扩一个枚举值 + 加一条验收，就能堵掉整个 B3 级事故。这是全审计中性价比最高的一处修改。**

## 6. 逐项审查（5）：端侧边缘数据轻量化摄入 —— **完全缺失，且 M1-001 的验收标准与宪法正面冲突**

**核对结论：【架构规划】C01 与【总工任务书】M1-001 不只是"漏掉了"降噪与声纹淘汰，它们的设计方向与宪法第三十三条相反。**

### 6.1 职责层：没有任何模块负责"轻量化"

【架构规划】§3 C01 的职责定义原文：**"接收多源资料，校验时间、单位、来源、重复包，生成 Observation"**，边界是"不判断情绪、关系、人生事件"。

**C01 的四项职责是：时间校验、单位校验、来源校验、去重。没有一项是"降采样 / 特征提炼 / 语义化 / 冷热淘汰"。** 宪法第三十三条要求的四类端侧处理——① IMU 特征提炼 ② 心率时段均值压缩 ③ 图像语义化 ④ 声纹指纹与淘汰——**在 14 个 C 模块的职责表中无处安放**。C02（存储）不管摄入语义，C05（事件认知总结）在下游，C06（查询）在下游。**这是一个模块级的责任真空。**

### 6.2 任务层：M1-001 的设计方向相反

【总工任务书】M1-001 §A：**"把虚拟 GPS、心率、IMU、文本、App数据**统一写入 Observation**，并支持来源消息去重"**
§C：**"接入只做**格式、单位、时间、数据质量**清洗，不做语义判断"**
§H 验收标准：**"**10k 条模拟心率可批量写入**且不触发 AI"**

**宪法第三十三条之 1 原文**：**"IMU … 绝对不得作为 50Hz/100Hz 高频时序数值直接记入数据库。系统在端侧仅提取宏观运动状态（静止、平缓走动、剧烈跑动、疑似摔倒撞击）及显著运动波形特征"**；**"心率传感器在平稳无波动的长周期（如持续 2 小时无剧烈波动）内，仅压缩记录一个时段平均值点；仅当出现影响健康的重大异常波动时，才作为独立 Observation 写入时间轴"**。

**M1-001 的验收标准要求"10k 条模拟心率可批量写入"——按宪法，2 小时平稳心率应该只产生 1 个 Observation，10k 条（≈50Hz × 200 秒）根本不应该存在。** 这条验收标准**把宪法明令禁止的行为写成了通过条件**。而且它是 M1 的验收，意味着**违宪行为会在 M1 就被固化成"已通过的基线"**，M7-002 再来测存储增长时，数据已经按错误方式写进去了。

### 6.3 多模态：整条管线不存在，连测试数据都没有生产者

| 宪法要求 | 出处 | 任务书落点 | 状态 |
|---|---|---|---|
| 图像端侧语义化（场景描述、关键物品、人物关系、OCR） | 第三十三条之 2 | 无 | **零 Issue。`图片语义化/抓拍/OCR` 在任务书 0 命中** |
| 录音转文本 | 第三十三条之 3 | 无 | **零 Issue。模拟器不产音频** |
| 声纹指纹提取 + 未知实体绑定 | 第三十三条之 3 | 仅叙述性提及 | **`声纹` 在任务书 2 处命中，全部是散文**：M1-002 §B "声纹 A 后来知道是妈妈时，历史事件要自然变清楚"；M2-007 §G "新声纹证据命中验证任务"。**没有任何 Issue 负责产生声纹** |
| 声纹 6 个月冷热淘汰 | 第三十三条之 3 | 无 | **零 Issue** |
| 手机聊天记录/相册/日历摄入 + 垃圾过滤 | 第三十三条之 4 | 部分 | M1-001 有"文本、App数据"，**但"自动剔除短信验证码、营销广告、群聊刷屏"的入口过滤规则零命中** |
| 每日大模型清洗提纯 | 第三十三条之 5 | 无 | **零 Issue**（且该条与第一百一十六条一票否决冲突，见配套报告 B1） |

**最致命的是最后一环**：M2-014「一天虚拟人和观测生成器」§C 是 **"Truth layer 定义事件/因果/偏好；Observation generator 只按可见时间产出数据；支持噪声、延迟、缺失、重复"**。§J 交付物是"一天生成器、3 个基础虚拟人、隔离测试"。【测试规范】§3 的虚拟人构成里数据渠道是 **"对话、教育记录、位置、支付、模拟传感器"**。

**没有音频通道，没有图像通道。** M1-016 的贯穿案例输入写的是"GPS学校、操场**视觉文本**、加油**录音**、心率/IMU"——但"视觉文本"是**已经语义化好的文本**，"加油录音"在宪法第四十七条的示例里落地为 `V219 "加油！加油！"`（**也是文本**）。**也就是说：模拟器生成的是"已经完成端侧处理之后的结果"，端侧处理本身既没有实现、也没有测试数据、也没有验收。**

**后果**：宪法第三十三条的全部内容**无法被实现，也无法被测试**。第一百一十三条说"场景是验证工具"——**没有生产者，就没有场景，就没有验证**。

### 6.4 按旧方案存，手环存储和带宽会不会崩塌？—— **会，而且崩塌点比想象的早**

按实测 1.0 KB/行、4.53 KB/对象的内存放大系数：

| 摄入档 | obs/日 | 1 年对象数 | 1 年 DB | 3 年 DB | 一次全量快照 RAM |
|---|---|---|---|---|---|
| **L 轻**（第三十三条真正生效） | 300 | 239,148 | **0.24 GB** | 0.7 GB | 1.08 GB（勉强） |
| **M 中**（M1-001 的"统一写入"方案 + 手机记录 + 全天转写） | 4,500 | 3,587,220 | **3.59 GB** | 10.8 GB | **16.3 GB → OOM** |
| **H 重**（全向麦全天候 + 抓拍 + IMU 原始特征） | 30,000 | 23,914,800 | **23.9 GB** | 71.7 GB | **108 GB → OOM** |

**L 档与 M 档差 15 倍。这个 15 倍完全由"第三十三条是否被实现"决定。** 而 M1-001 的验收标准站在 M 档那一边。**【测试规范】§5 的 1 年档位是"70 万~360 万条"，正好落在 M 档——也就是说测试规范要求的规模，就是旧摄入方案会产生的规模，也正是快照 OOM 的规模。三份文档在这里形成了一个自洽的错误闭环。**

**带宽侧**：如果图像不做端侧语义化而回传原图，一张 1080p JPEG ≈ 300 KB；一天 50 张抓拍 = 15 MB/日 = **450 MB/月 上行**。手环级蜂窝/蓝牙回传预算下这是不可行的。语义化后一条文本 Observation ≈ 650 B，同样 50 张 = **32 KB/日**，**降低 460 倍**。**这一条宪法写对了，但没人实现。**

### 6.5 裁定

**完全缺失 + 逻辑冲突。这是 7 项中"方向性错误"最严重的一项：不是没做，是验收标准鼓励了宪法禁止的行为。**

## 7. 逐项审查（6）：穿戴物理形态与交互状态机 —— **全部界面按 PC 桌面浏览器设计，零穿戴任务**

**核对结论：是的，现有【工作台规格】与【总工任务书】把所有界面都当成了 PC 桌面浏览器端。穿戴端三层 UI 契约与马达 FSM 状态机的开发任务数量为 0。**

### 7.1 证据

【架构规划】§4「第一版实现形态」原文：**"**控制台：浏览器界面**，展示同一套工作台接口与操作轨迹"**；部署单元四个：Core / AI Worker / **控制台** / Simulator-Evaluator。**没有任何穿戴端部署单元。**

【工作台规格】§2「界面布局」是一张 **PC 三栏多面板 ASCII 图**：顶部"虚拟时间｜当前用户｜世界版本｜会话状态｜暂停/步进/回放"，第二行"紧急事项条"，中间三栏"本次唤醒 / 当前世界 / AI自身当前状态"+"任务面板 / 世界浏览区 / 证据与主张区"，底部"操作轨迹｜世界修改｜行动收据｜结果｜待接续工作"。§5 全篇是 **"人类按钮/操作 ↔ AI 接口"** 的映射表（"打开当前面板"、"选择时间范围"、"放大/缩小"、"搜索世界"、"展开事件"…）。

**这是一份优秀的开发者调试控制台规格**，而且宪法第八十六条之 4 本来就要求这么一个东西：**"开发阶段必须实现一个可视化的'认知调试控制台'…此控制台供开发者和自动化测试系统使用，**不面向最终用户**"**。**所以【工作台规格】作为调试控制台是完全合格的，它的问题只是——它是唯一的一份 UI 规格。**

【总工任务书】M1-015「开发者控制台最小版」是唯一的 UI 类 Issue。**`马达`/`震动`/`骨传导`/`FSM`/`误触`/`柔性`/`三层 UI`/`插件`/`态势画布`/`23cm` 在 86 个 Issue 中命中数全部为 0。**

### 7.2 由此产生的四个具体架构死角

**死角 1：交付通道（Capability）没有物理形态契约。**
【架构规划】C11「能力与交互」= "教育工具、模拟行动、消息、回执、结果追踪"；M2-008 的 executor "第一阶段只模拟发送消息、提醒、教育动作"。**"发送消息"在 PC 调试台是弹一个面板；在手环是"微震 → 5~10 秒窗口 → 抬手看屏 / 按耳听骨传导 / 超时消失"。这是完全不同的状态机，而 `Action` 契约里没有任何通道语义字段**（冻结的 `Action` = `execution_id / action_type / action_status / task_ref / payload / expected_outcome`，**没有 channel、没有 haptic_pattern、没有 window_timeout**）。

**死角 2：投递黑洞 —— AI 人格层的诚实性事故。**
宪法第九十八条之一的 FSM 通道 C 是"超时/忽略 → 窗口销毁，重回静默休眠"。**消息就这样消失了。** 没有投递账本、没有重投、没有升级路径。
**M2-008 其实已经走到了一半**：它区分"AI决定做 / 动作已提交 / 动作已执行 / 现实结果如何"，§G 测试有 **"消息送达但用户无回应 outcome 分开"**，§H 验收"重复执行率 0；unknown 路径正确"，`OUTCOME_UNKNOWN` 已在契约中。**这是很好的基础。**
**但它缺的是最关键的一环**：M2-008 把"已送达"当作 Action 完成。而在 FSM 下，**"已振动"≠"已送达"≠"已被感知"**。振动窗口超时销毁后，用户什么都没收到，而系统会记录 `action_status=completed`。**后果直接命中 AI 世界**：`DIM_AI_PROMISES` 会写下"我答应提醒他妈妈生日 → 已完成"，**AI 会真诚地相信自己守约了，而用户永远没收到提醒**。对一个把"承诺与内疚清单"当人格支柱（宪法第十九条之二、第三十二条）的系统，**这是人格层面的事故，比功能失效严重得多**。

**死角 3：紧急通道与四步序没有旁路约定。**
【架构规划】§8 有 **"安全旁路：模拟安全流程不等待普通模型推理完成"**，【工作台规格】§9 有完整的紧急事项状态机（`NEW → ACKNOWLEDGED → CHECKING → HANDLING/ESCALATED → RESOLVED/FALSE_ALARM`），M2-004 有"普通会话中安全 Wake 抢占"，宪法第七十八条之 4 规定摔倒报警"绝对不依赖云端大模型推理，亦不依赖网络连接"。**这一套是对齐的，质量也不错。**
**但没有任何一处规定：安全 Wake 是否豁免第八十四条的四步序。** 按四步序字面执行，用户说"我胸口好疼"时，AI 要先照镜子、校准羁绊、定语调，**在不知道这是急性胸痛的情况下就把姿态和语气定死了**——可能用调侃语气回应心梗。**必须补：Wake 携带 `safety_critical` 标记时，四步序压缩为"底线 → 直取触发源 → 事后补羁绊与语调"。**

**死角 4：三层 UI 的"共享单一灵魂"约束没有承载点。**
宪法第一百零四条之一的核心禁令是 **"严禁数据孤岛与人格分裂：插件绝无独立模型与独立记忆库，必须全量共享 AIOS Core 的统一时间轴、全局认知与关系羁绊"**。
**好消息**：M6-001「AppManifest 与 Capability Registry 最小协议」+【架构规划】§3 结尾"App 通过 C01 输入资料，通过 C06 读取允许的信息，通过 C11 提供工具，并使用 C08 管理任务。**App 不拥有独立的用户记忆库或 AI 人格**" + M6-004「跨 App 认知迁移实验」——**这条禁令在 App 层面是有承载的，而且承载得不错**。
**缺口**：宪法第一百零四条之一说的是**"技能插件以微界面卡片形式动态投射至第一层画布"**，这是一个**运行时 UI 组合协议**（谁决定投射哪个插件、卡片如何抢占 23cm 画布、任务结束如何归隐），**与 AppManifest 的静态声明协议不是一回事**。`AppManifest` 里需要新增"可投射的微界面组件清单 + 投射触发情境 + 画布优先级"，**这一层零覆盖**。

### 7.3 关于物理可行性的一条独立红旗（必须写进 gate）

宪法把"超宽频微震/骨传导马达 → 手指按耳 → 私密听音"写成**主音频通道**（FSM 通道 B）。用腕部微型 LRA/压电致动器经指-耳骨路径输出**可懂语音**，需要远超"舒适腕戴 + 电池可承受"的振动位移与力；实际结果大概率是**音量很小、可懂度差、旁人可闻（隐私泄露）、连续使用发热与耗电**。

**同时【架构规划】§1 已经明确"实体手环不进入本阶段关键路径"、宪法第一百零七条也明确当前只开发 AIOS Core**——**所以这一条在 M0~M8 阶段不构成阻塞**。但它构成 **M8-003 的 gate 风险**：宪法把未验证的硬件机制写成了既成事实（"绝对零误触"、"私密听音"），**没有"待硬件验证"标注**，下游会把它当成已确认前提继续设计。

**建议**：给第九十八条之一与第一百零四条之一加 **"待硬件台架验证"** 标注，并在 M8-003 的 gate 清单里加入"骨传导可懂度 MOS / 旁人可闻度 / 功耗 / 温升 / 柔性屏量产可行性"五项台架验证结论。**这不需要现在做硬件，只需要现在不要把它写成事实。**

## 8. 逐项审查（7）：虚拟世界测试与验收门 —— **测试规范停在 V01~V20，V21~V30 全部悬空；且任务书已经在引用不存在的场景**

**核对结论：是的，【测试规范】仍然只有 V01~V20 的基础场景，宪法第一百一十三条要求的 V21~V30 一个都没有。更严重的是【总工任务书】已经把"V01~V30覆盖"写成了必写测试——那是一条永远无法验证的悬空验收。**

### 8.1 场景覆盖缺口

【测试规范】§10 的矩阵是 **V01~V20**，每个场景都要求"正例、近似反例和资料不足版本"（这条纪律很好，且与宪法第一百一十三条一致）。**但 V21~V30 零命中。**

宪法第一百一十三条明文要求：**"在虚拟世界基础场景（V01~V20）之上，必须全面覆盖以下 10 个进阶场景"**：

| 宪法要求 | 场景名 | 【测试规范】最接近的已有场景 | 缺口性质 |
|---|---|---|---|
| **V21** | 高频传感器持续输入但无异常 | 无（V10 是"无数据与无变化"，语义相反） | **完全缺失**。且 M2-002 §G 有"1000 条稳定心率 0 Wake"的单元测试，**但没有端到端场景** |
| **V22** | 强烈愿望/预测被表达为事实语气 | V05"用户断言未来结果：区分说过、相信、实际发生" | ⚠️ **实质覆盖，但未采用 V22 编号** → 追溯断裂 |
| **V23** | 多维区间共同支持候选事件 | 无（V03 是"身体信号与运动情境共同出现"，侧重不误判） | **缺失"区间证据 + 支持下钻 + 可被反证"的组合验证** |
| **V24** | 迟到数据改变区间认知 | §5.3 年度流程提"被迟到证据改变的旧认知"（一句话） | **有意图无场景**：无编号、无正例/反例/证据不足三版本、无判定条件 |
| **V25** | 数学/英语/编程形成学习能力 | V13"高阶学习能力判断：追溯到项目、练习和原始资料" | ⚠️ **实质覆盖，编号不同** |
| **V26** | 新维度有趣但长期无收益 | V14"新维度重复或无价值：拒绝注册、合并或结束试用" | ⚠️ **实质覆盖，编号不同** |
| **V27** | 长期目标产生多次任务 | V07"三个月后定时任务" | ⚠️ **部分覆盖**：V07 只验证单次定时，**未验证 Goal 跨多 Task 的连续性** |
| **V28** | 推断目标后来被用户否认 | 无 | **完全缺失**（对应 R2-09，而 R2-09 在任务书里也没被引用） |
| **V29** | 候选事件后被新证据否定 | V04"A 先被误认，后有身份纠正"（侧重身份，不是事件） | **部分缺失**：EventAnchor 全生命周期（CANDIDATE→ACTIVE→REVISED/REJECTED）无专属场景，**而这正是 M1-016 与 M3-003 的贯穿案例** |
| **V30** | 一个月跨尺度查询与下钻 | §5.2 一个月流程（叙述性） | **有意图无场景**：无编号、无"月→周→日→原始节点全链路穿透"的可执行判定 |

**净结果**：V21~V30 中 **3 个完全缺失（V21/V28 + V23 的组合验证）、3 个有意图无场景（V24/V29/V30）、4 个实质被 V01~V20 覆盖但编号不同（V22/V25/V26/V27）**。

**编号不同不是小事**：宪法第一百一十四条的 R2 验收表（R2-01~R2-15）是**按 V21~V30 的语义写的**（如 R2-04"区间证据不漂移"对应 V24、R2-09"推断目标与用户明确目标分离"对应 V28、R2-12"最小多尺度总结闭环"对应 V30）。**场景编号断了，验收项就失去了可执行的测试载体。**

### 8.2 悬空验收：任务书已经在引用不存在的场景

【总工任务书】第 3377 行，**M4-004「30天闭环实验与固定回放实验」§G「必须编写的测试」原文**（其 §H 验收标准为"输出配对差值和95%CI；失败案例可回放"，同样不含任何可判定的场景条件）：

> **"V01~V30 覆盖；模型失败/重试纳入日志。"**

**V21~V30 不存在于任何测试文档。** 这是一条**永远无法验证的验收标准**。在 gate 上它只有两种命运：**被忽略（则 M4 少验 10 个场景），或被伪造（则整个验收体系失去可信度）**。

同一份任务书里，M4-001 §H 验收标准是 **"符合虚拟世界规范 5.2"** —— 引用的是【测试规范】§5.2「一个月生成流程」，其中包含 **60,000~300,000 条观测**。**这正是我实测出 1,360 MB / 3.94 s（300K）与 MemoryError（1M）的读路径要处理的规模。M4-001 的验收标准，直接指向一个已实测崩溃的代码路径。**

### 8.4 1~3 句反长篇说教验收门：**零覆盖**

宪法第十四条之一（反长篇大论病）、第九条（反谄媚立场）、第十条（反居高临下与非审判立场）、第十一条（分寸感自涌现）、第十二条（AI 沟通风格进化），以及 R3-06（反谄媚硬骨气）、R3-07（分寸自适应）、V3-01（沟通风格进化）：

- 【测试规范】§11 的指标族有 5 大类（主动帮助 / 理解证据纠错 / 任务与长期连续性 / 世界操作效率 / 教育帮助效果），**没有任何输出风格、长度、语气、立场类指标**。
- §15 的三层评分里第 3 层是"语义审查：主张是否有依据、解释是否合理、**表达是否适当**"——**"表达是否适当"这六个字是唯一的钩子，但它没有定义、没有指标、没有场景、没有门槛**。
- 【工作台规格】§11 的帮助决策记录有"选择的方式、时机与强度"，**但那是记录字段，不是评分指标**。

**后果**：一个每句话 300 字、逢用户抱怨就背诵人生道理、用户说什么都附和"你说的全对"的 AI，**可以通过现有全部验收门**。而宪法第一百一十六条把"违背事实谄媚奉承"列为**一票否决**。**一票否决条款没有对应的检测方法，就等于没有这条款。**

| 测试方法论本身 | ✅ **优秀**（四层隔离、两条赛道、B0/B1/B2/O 强基线、盲测纪律、95% CI、失败归因表、LongMemEval/LoCoMo 参照）。**这是四份文档中质量最高的一份，问题只是覆盖面停在了 v2.0** |

**一个额外的讽刺发现**：【测试规范】§8 的 **B2 强混合检索记忆基线**定义是"时间/实体筛选、**关键词与向量检索**、可更新事实记忆、摘要、任务与调度"，§202 还强调 **"B2 不能故意做弱"**。

**也就是说：按现有任务书实施，AIOS 的检索能力会显著弱于它自己的对照组 B2，而 B2 还被要求不能做弱。** 实验会在 M4/M7 得出"AIOS 不敌强基线"的结论——**而这个结论反映的不是架构优劣，是 M1-012 少了一个分词器**。这是本审计中最容易造成灾难性误判的一处。
