### 0.1 本轮最重要的发现：一个 P0 缺陷（已定位 + 已修 + 已复测）

盲测撞出的**第一个真问题**不在认知层，而在**端侧冲击判据**：

| 指标（全量档位） | 修复前 | 修复后 | 变化 |
| --- | ---: | ---: | --- |
| S1 落库对象 | **461,066** | **33,238** | −92.8% |
| 其中"异常冲击波形" | **427,838（92.8%）** | **10** | −99.998% |
| S1 耗时 | 303.1 s | **121.8 s** | 2.5× 更快 |
| S1 Token | 2,766,396（**月度封套 108.7%**） | **199,428（7.81%）** | −92.8% |
| DB 体积 | 571.7 MB | **34.8 MB** | −93.9% |
| S3 全库建图 | **OOM，进程被内核杀死（3 次复现）** | 1,674.0 ms 通过 | 解锁 |
| 八阶段单进程 | **跑不完** | **130.10 s 跑完，5/5 铁律** | 解锁 |

**根因**：`AdaptiveTemporalCompressor` 的冲击判据**只看绝对值**（`peak_g ≥ 2.0`）。
而"跑步"段的基线本身就是 1.9 g（噪声 0.16 g），于是**每一次例行跑步都被判成跌倒冲击**：
4,579,518 条样本里 427,838 段被逐点搬进数据库，直接吃掉 92.8% 的存储与 Token，
并把 4 GB 机器的内存打爆（全库建图对象数 ×15）。
**修法（已落地）**：冲击判据改为**双条件** —— 绝对阈值 **且** 相对上一段基线的**起跳幅度** `impact_delta_g ≥ 1.0`
（真实跌倒的特征是"自由落体后的陡增"，不是绝对值高）；冲击波形另加**保留上限** `max_impact_samples = 32`
（与存储审计 `MAX_IMPACT_WAVEFORM_SAMPLES` **同源共用一个常量**，杜绝"压缩器保留 40 点、审计线 16 点"这类口径漂移）。
修复后：3 条真实跌倒（3.45 g）仍被判为 `FALL_SUSPECT` 并原样保留波形，例行跑步误判从 427,838 段降到 7 段。
详见诊断书 §1.5 与 §4（R9）。

## 1. 为什么这套盲测"不能自证"

任务明确禁止"自造 mock 数据自证"。本套件用四道机械闸门把这条禁令变成可执行约束：

1. **真值发生器独立于被测实现**：`adversarial_life_bench.py` 源码里**不允许出现**
   `aios_core.storage / ingest / tools / query / world / bench.blind_bench_*` 的任何 import，
   由 `tests/bench/test_adversarial_life_bench.py::test_generator_does_not_import_the_system_under_test` 逐字扫描源码强制。
2. **盲化视图**：被测系统只能拿到 `BlindedSample`（无 `role`/`story`/`evidence_key`），
   真值标签只存在于考官侧。
3. **真值边界互斥**：证据真值集合与噪声真值集合交集必须为空（同一句话不能既是必须永存的证据、又是必须删除的垃圾）。
4. **断言与生成器解耦**：所有断言只存在于 `tests/bench/`、CLI 核账与本文档，
   发生器"不知道自己会被怎么判"。

```bash

    --workdir /tmp/bb_gate_final3 --json /tmp/bb_gate_snapshot_final.json --max-rss-mb 1500

    --profile full --workdir /tmp/bb_full_final3 --json /tmp/bb_full_snapshot_final.json \
    --max-rss-mb 3000 --rss-grace-s 5

# ③ 测试套件
PYTHONPATH=src python -m pytest -q          # 1203 passed（本机 60～67 秒）
```

> 本报告的两份快照就是上面两条命令的输出（原样复制到 `evidence/`）。
> `--max-rss-mb` 是**阶段内内存看门狗**：独立线程每 200 ms 采样 `/proc/self/statm`，
> 超预算给收尾宽限期后**先写快照、再 `os._exit(4)`**，把"无证据 SIGKILL"变成"有尸检报告的主动熔断"。
> 本轮两次正式运行都**没有触发**熔断（GATE 峰值 432.9 MB / FULL 峰值 638.9 MB，均低于预算）。

## 6. 极限压测：从"翻车现场"到"全流程通过"

### 6.1 翻车现场（修复前，三次复现，证据保留）

全量档位（461,066 条落库对象）**单进程**跑八阶段会撞内存墙：

1. 第一次：S1（305,223 ms）、S2（22,557 ms）完成后，进程在 **S3** 被内核 OOM 杀掉 ——
   `Out of memory: Killed process (python) total-vm:3959332kB, anon-rss:3881692kB`（机器 4,034,452 kB）。
2. 第二次（`--stages 1,2,3 --max-rss-mb 2400`，阶段内看门狗版本）：
   S1（286,231.5 ms）、S2（21,236.7 ms）通过；进入 S3 后被内核 SIGKILL（退出码 137）。
3. 第三次（`--stages 1,2`，本轮被保留为对照证据）：S1 **303,122.6 ms**、S2 23,619.6 ms，
   落库 **461,066** 条，其中 `wearable_imu_impact` **427,838** 条（92.8%），
   DB **571.7 MB**，Token **2,775,156**（月度封套 **108.7%**）——
   这就是 `evidence/full_snapshot_prefix_461k.json` 记录的口径。

同时暴露两个审计信号：`raw_scan_violations = 2`（两条冲击波形超过当时的 16 点上限）、
S1 每次 4 万样本批次耗时 **16,915 ms**（GATE 同口径只有 2,315 ms）。

### 6.2 定位：假冲击浪涌

把 427,838 条"冲击波形"按日展开后发现它们**不是跌倒**，而是**跑步**：
发生器里 `run` 段的 z 轴基线 1.9 g、噪声 σ=0.16 g，而压缩器的冲击判据只看
`peak_g ≥ impact_threshold_g = 2.0` —— 例行跑步**必然**越线。
`max_segment_span_s = 30 s` 意味着一次 24 秒跑步会被切成上百段，**每段都升格成一条独立 Observation**：
一次跑步 → 上百条"跌倒嫌疑"记录 → 逐点波形入库 → 存储/CPU/内存三线爆掉。

一句话：**判据混淆了"绝对幅度"与"相对冲击"，把"运动"当成了"事故"。**

### 6.3 修法（已落地并复测）

| 修改 | 位置 | 效果 |
| --- | --- | --- |
| 冲击判据改**双条件**：`peak_g ≥ impact_threshold_g` **且** `peak_g − 上一段基线 ≥ impact_delta_g`（默认 1.0 g） | `tools/adaptive_temporal_compressor.py` | 例行跑步 427,838 段 → 7 段 |
| 冲击后**基线重估**（`baseline = max(段均值, 阈值/2)`），绝不拿"跌倒那一跳"当新常态 | 同上 | 避免连锁误判 |
| 冲击波形**保留上限** `max_impact_samples = 32`，只留峰值附近窗口 | 同上 | 单条波形有界，杜绝"整段搬库" |
| 保留上限导出为**唯一常量** `MAX_IMPACT_WAVEFORM_SAMPLES`，存储审计 import 同一常量 | `bench/blind_bench_harness.py` | 压缩口径与审计口径不再漂移（旧版本正是 40 点 vs 16 点打架，审计报 2 例违例） |

修复后：FULL 档 3,285 段 IMU 输入 → **10 条冲击波形**（3 条 `FALL_SUSPECT` 3.45 g 真实跌倒 + 7 条跑步尖峰，后者**没有被升级为跌倒**）；
`motion_compression_ratio` 从 813×（虚高，因为分母是假冲击）变为 **1,790.47×**（真实水平），
`hr_compression_ratio = 23.39×`。

## 9. 已知边界与诚实声明

1. **7 条"跑步尖峰"仍被记为 `IMPACT`（非 FALL）**：FULL 档 10 条冲击波形里有 7 条来自跑步段的
   相对起跳（2.37～2.54 g），它们没有被升级为 `FALL_SUSPECT`，也未触发 P0。
   这是双条件判据在"只留真事故"与"宁可多留可疑"之间的取舍，代价是 7 行存储；
   如需进一步降噪，可引入横向（三轴）冲击方向判据 —— 列为下一轮观测项，不装作已解决。
2. **全量档位 ingest 仍有 3.12× 非线性**：每 4 万样本批次 2,406 ms（GATE）→ 7,496 ms（FULL）。
   单批原始子样本量本身是 1.75×（FULL 每日子样本更多），剩余 ≈1.8× 仍未定位
   （候选：内存压力下的 GC、`_pending` 缓冲、SQLite WAL 增长）。已列为 P1 观测项。
3. **本盲测未接真实大模型**：所有 Token 由本地估算并如实记账，LLM 调用数恒 0。
   因此本报告只能证明**机械护栏、数据链路、内存/延迟/存储行为**；
   **建议是否真"硬核"、人设是否真不爹味等语义质量，未在真机联调前不作结论。**
4. **沙箱环境为 4 GB 内存 / 4 vCPU**，所有数字只在此环境下可比；跨机型请以分位表口径重跑复现。
5. **本轮的"修复前/修复后"对照**来自同一台机器、同一份发生器（`seed = 20260916`），
