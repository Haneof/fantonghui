# AIOS 系统认知统一 · 提交协议

> **文件编号**：COG-PROTOCOL-001
> **日期**：2026-09-18
> **性质**：流程规约（PROCESS）。本文件不裁决任何技术问题，只规定"怎么提交、怎么比对、谁裁决"。
> **目的**：在讨论架构之前，先让所有参与者对"AIOS 到底是什么"形成可验证的统一认知。

---

## 一、为什么要有这道工序

### 1.1 已被实测的问题

| 实验 | 结果 |
|---|---|
| 三个模型执行"逐字合并宪法"（最不需要理解力的任务） | 交出三份不同结果：一份未改、一份篡改了"生效日期→编纂日期"、一份自行改判条款编号 |
| 宪法自我审查（ADJ 裁决集） | 发现 6 处条款互斥，其中 ADJ-004 定性为"宪法允许另一条宪法违宪" |
| 工程对齐审查（Gap Audit） | M2-012 技术指导与宪法第 84 条"逐字相逆"，判词：M2 断崖式卡死 |
| 代码实证（本轮） | `Reinterpretation` 与 `RetrospectiveAnnotation` **两个对象同时存在于代码中**，承载同一语义 |

> **结论：分歧不是态度问题，是文本真的没说清楚。两个认真的读者得出相反结论，缺陷在文本。**

### 1.2 本工序要解决的具体困难

项目所有者的原话：

> "我不懂代码，你们各自理解各自的、各自出各自的方案，我都完全不知道谁对谁错。"

**因此本协议的第一设计目标不是"收集观点"，而是"让分歧自动显形、让裁决不需要技术背景"。**

### 1.3 禁止散文

若每个 Agent 各交一篇自由格式的理解文章，结果必然是：
五篇都说得头头是道，分歧藏在措辞差异里，所有者依然无法比较。

**故本协议强制结构化提交：绝大多数题目是单选，答案可机械对比，分歧自动计算得出。**

## 二、参与与产出

### 2.1 角色

| 角色 | 职责 |
|---|---|
| **应答 Agent**（N ≥ 3） | 通读法统全文，独立填写《认知答卷》，**互不参阅** |
| **汇总方** | 机械比对全部答卷，产出《分歧报告》，**不得表态** |
| **裁决者**（项目所有者） | 仅对分歧项做选择，**不需要技术背景** |

### 2.2 必读材料（唯一指定范围）

1. `docs/constitution/AIOS_Constitution_v3.0_FINAL.md`（合卷本，含全部现行法统）
2. `governance/normative_versions/registry.md`（生效状态与冲突规则）
3. `docs/architecture/00_AS_IS_现状架构测绘报告.md`（代码现状事实）

> 不得参阅其他 Agent 的答卷；不得参阅未签核的 R4 正文作为结论依据（可作为"分歧来源"引用）。

### 2.3 提交物

- 路径：`docs/cognition/answers/<agent-id>.md`
- 格式：严格复制 `docs/cognition/01_认知答卷_模板.md`，逐题作答
- 纪律：**只允许填写答案，不得修改题目、不得增删题号**

## 三、答卷的强制结构

答卷分五部分，合计 32 题。

| 部分 | 题数 | 题型 | 考察 |
|---|---|---|---|
| A 本质认知 | 6 | 单选 + 一句话 | AIOS 是什么、不是什么 |
| B 系统边界 | 7 | 清单 + 单选 | 输入面、输出面、负面清单 |
| C 核心概念 | 9 | 单选 | 22 个对象的语义边界 |
| D 行为判定 | 8 | **具体情景单选** | 同一场景下系统该做什么 |
| E 已知冲突 | 2 | 单选 + 理由 | 对宪法自相矛盾处的取舍 |

### 3.1 核心机制：D 部分是判据

A/B/C 考的是"你怎么理解"，容易形成表面共识。
**D 部分考的是"那么系统到底该做什么"——同一个具体场景，只能有一个答案。**

> 例：`用户凌晨两点摔倒。系统的第一个动作是什么？`
> - (1) 调用大模型判断严重程度
> - (2) 先触发硬件安全动作，零模型调用
> - (3) 先查用户历史健康数据
> - (4) 先判断此刻是否方便打扰

**A/B/C 一致但 D 分叉 = 认知并未真正统一，只是措辞趋同。**
这是本协议最重要的检测能力。

### 3.2 每题必答两栏

| 栏 | 要求 |
|---|---|
| **答案** | 选项编号（单选题必须唯一） |
| **法源** | 支持该答案的条款/裁决编号；**若法统无明文，必须写 `无明文`** |

> `无明文` 是极有价值的信号：它标记出"需要立法而非解释"的位置。

## 四、分歧计算规则（机械执行，无主观判断）

汇总方对每道题统计答案分布，按下表定级：

| 等级 | 判据 | 处置 |
|---|---|---|
| **CONSENSUS** | 全体一致，且法源一致 | 登记为共识，进入《统一认知基线》 |
| **WEAK** | 答案一致，但法源不同或含 `无明文` | 登记为"结论对、依据虚"，需补立法 |
| **SPLIT** | 答案分叉 | **升级为裁决项，提交所有者** |
| **BLOCKER** | 答案分叉 且 位于 D 部分（行为判定） | **最高优先级裁决项**，架构讨论在此项裁决前不得启动 |

### 4.1 分歧报告格式

每个 SPLIT / BLOCKER 项，汇总方必须产出：

```
题号：D-03
题目：<原文照抄>
分布：选项(2) × 3 票 ｜ 选项(1) × 2 票
各方法源：
  选(2)：registry §6.5、ADJ-001 Step-0
  选(1)：第 46 条、第 106 条
所有者需要做的选择：
  A. 摔倒时先动硬件，事后再让 AI 研判
  B. 摔倒时先让 AI 判断严重程度，再决定动作
（不需要理解技术细节，只需选择你要哪一种行为）
```

> **裁决项必须翻译成"两种具体行为"供选择，禁止用技术术语描述选项。**

---

## 五、裁决与固化

1. 所有者对每个 SPLIT / BLOCKER 选择其一（可附一句话理由，也可选"两个都不对"并口述期望）
2. 裁决结果写入 `docs/cognition/02_统一认知基线.md`，标记为 ACTIVE
3. **每条裁决必须配一个二值验收场景**，否则不得结案：

```
裁决：摔倒时先动硬件，事后 AI 研判
场景：首个硬件安全动作发生前，LLM 调用次数 == 0
判定：二值，进 CI
```

4. 统一认知基线生效后，**才允许启动架构讨论**

---

## 六、本协议的边界

1. 本协议**不产出架构**，只产出"大家对系统的一致理解"
2. 本协议**不修改任何现行法统**；发现的冲突登记为裁决项，走第 115 条治理程序
3. 认知基线**不替代宪法**：宪法仍是意图法源，基线是"我们一致同意宪法在这些点上是什么意思"

---

## 七、执行顺序

```
① 发布协议与模板（本文件 + 模板）
② N 个 Agent 独立作答，互不参阅        ← 当前所处阶段
③ 汇总方机械比对，产出分歧报告
④ 所有者逐项裁决（只做选择题）
⑤ 固化为统一认知基线 + 二值验收场景
⑥ 【此时才开始】架构讨论
```
