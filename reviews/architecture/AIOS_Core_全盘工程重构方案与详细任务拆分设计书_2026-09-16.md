# 一、独立诊断与重构主张

## 1.1 最致命的断层：不是"漏了功能"，是**类型系统里根本没有承载对象**

我把断层按"能不能靠加任务修好"分成三层，越往下越致命：

### 第一层（可加任务修）：机制无 Issue
v3.0 的三个强制机制在 82 个 Issue 里的对应实现数：

| v3.0 机制 | 条款 | 旧任务书对应 Issue | 实测关键词命中（任务书 4262 行全文） |
|---|---|---|---|
| Single-Shot Cockpit + 心智四步序 | 第八十四条 | **0** | `四步`=0、`照镜子`=0、`看板`=1（伪命中：项目经理看板） |
| 条件驱动任务执行（杜绝 Token 空转） | 第八十六条 | **0** | `time_reached`/`context_matched`/`event_occurred`/`dependency_ready`=**全 0** |
| 三级流式心智流水线（1500 窗口 + 后台萃取 + 按需回捞） | 第八十五条 | **0** | `流式`=0、`萃取`=0、`1500`=0、`滑动窗口`=0 |
| 多关键词共现检索 | 第八十九条 | **0**（M1-012 只有"逐步过滤"） | `共现`=0、`co_search`=0、`多关键词`=0 |

这一层最好修：加 Issue 就行。

### 第二层（必须改契约）：**三个一等对象在代码里不存在**

这是本文最重要的一条诊断，也是所有并行审查都没打到代码层的一条：

```text
宪法第 71 条（实测 22 行对象表） vs 代码实测：
  ObjectType 枚举值总数        = 19
  registry 映射项              = 19
  hasattr(ObjectType,'PREDICTION')              -> False
  hasattr(ObjectType,'LIFE_CHAPTER')            -> False
  hasattr(ObjectType,'COMMUNICATION_EXPERIENCE')-> False
```

`Prediction`（预测证伪闭环的载体，第 51 条）、`LifeChapter`（人生章节相变，M4 一月闭环的叙事骨架）、`CommunicationExperience`（v3.0 新增，1~3 句反说教与语调学习的唯一数据载体）**连枚举值都没有**。

后果不是"晚点补"：
- 第 51 条的"预测—证伪"闭环没有对象可写 → M8 消融实验无法裁决该机制有无独立收益；
- `CommunicationExperience` 不存在 → 第 114 条的 1~3 句反长篇验收门**没有任何数据来源**，测试规范永远测不了"机械 Chatbot 退化"；
- M0 的契约冻结一旦放行，`ObjectType` 枚举加值是**破坏性变更**（已冻结的 `object_revisions.object_type` 文本列 + `extra="forbid"` 的 Pydantic 契约），需要走第一百一十五条三级修宪，成本从"加 3 个类"变成"改冻结契约"。

**同时已冻结的错误码 `BUDGET_EXHAUSTED` 与 `STALE_INDEX`（`contracts/enums.py`，实测存在）——错误有出口，机制无入口。** 一个只能被抛出、永远没有产生者的错误码，是冻结过早的确凿证据。

### 第三层（最阴险）：**验收编号 A01~A09 在两份文档里完全错位，验收条款本身二义**

实测比对：

| 编号 | 宪法第 114 条 | 旧规划 §12（第 315~323 行） |
|---|---|---|
| A01 | 用户世界和 AI 世界共享时间轴 | 同一基础资料可被多个维度引用 |
| A02 | 多维世界可挂载不同数据形态 | **用户世界与 AI 世界使用同一时间和对象机制**（≈ 宪法 A01） |
| A07 | **时间缩放可用** | **无用户提问时能够触发、调查、决策、任务化** |
| A08 | **AI 操作可回放** | **用户接受、执行成功、目标改善三个结果分别记录** |
| A09 | **任务系统可用** | **所有关键修改和外部模拟动作具有可回放轨迹**（≈ 宪法 A08） |

而旧任务书 **第 2668 行**（M2-015 端到端验收）原文是：

> `R1-09/R1-10/W10/A07/A08/A09 同时通过。`

**这条验收在两套编号下指向完全不同的能力**：按宪法读，M2 端到端要验"时间缩放 + 操作回放 + 任务系统"；按旧规划读，要验"无提问自主闭环 + 三结果分记 + 可回放轨迹"。两名合规工程师会写出两个完全不同的 M2-015 测试，并且**都认为自己通过了验收**。

这不是文档瑕疵，是**验收系统失效**。它比任何单个功能缺失都致命，因为它让"通过 Gate"这件事本身失去意义。

## 1.2 如果不改直接开工，第一个崩溃点在哪里？

我的判断与"卡在 M2"的直觉不同：**第一个崩溃点在 M1，而且是静默崩溃。**

| 顺序 | 崩溃点 | 为什么是它 | 静默还是显性 |
|---|---|---|---|
| **1** | **M1-012 世界搜索**（第 89 条） | `object_revisions` 实测只有 3 个 B-tree 索引、**无 FTS5、无倒排表**。多关键词共现只能退化为全表 `LIKE` 扫描。我的实测：50 万行三词 AND = **319 ms**，100 万行 = **654 ms**（严格线性 2.05×），外推 500 万行 ≈ **3.3 s**；连续中文在 FTS5 `unicode61` 下 **命中 0 行**（`probe_cjk_tokenizer.py`）。而第 89 条要求"毫秒级" | **静默**：M1 验收用几百条测试数据，`LIKE` 毫秒返回，W01~W12 全绿。到 M4（一月）/M7（一年）规模上来才爆，此时改索引 = 全量重建 + 回归 |
| **2** | **M2-005/006 任务中心**（第 86 条） | 无条件过滤引擎 → 每次 Wake 只能全量遍历 Task 交给模型判断。工作台规格 §7 更把这件事**制度化**：待办任务"**必须进入定期任务盘点**或相关情境唤醒" | **显性硬卡死**：Token 消耗随 Task 数线性增长，M2-015 的"无提问主动闭环"演示会变成"每次醒来读一遍全部待办" |
| **3** | **M2-009 工作包**（第 84 条） | `workspace.open` 现状是"初始工作包 + M2-012 模型可多轮 tool calls"，没有 Cockpit 分档预算、没有四步序契约、没有 ContextSnapshot 落库 | 显性，但**不算违宪**：v3.0 第 84.1 禁的是元对话往返（"系统发提示词→AI说好的→再发下一段"），**工具循环本身合法**（第 91 条自己给了 30+ 原子工具）。缺的是预算、姿态与回放载体 |
| **4** | **M4 一月闭环** | M4 只有 **4 个 Issue**，却要扛"任务、关系、Goal、AI 自身世界跨日延续"。会话层（第 85 条）、羁绊数据（`DIM_AI_RAPPORT`）、预算账本三样全无 | 显性崩塌：跑得到第 30 天，但"真人老友"表象无从产生 |

**结论判词：**

> **按现有三份文档直接开工，项目不会在 M2 "停下来"，而是会在 M1 静默偏航、在 M2 机制性空转、在 M4 功能性崩塌。**
> M1 的偏航最危险，因为它**通过验收**；M2 的空转最贵，因为它**烧 Token**；M4 的崩塌最难挽回，因为它是**第一个对外可见的成果**。
> 而这一切的总根源只有一句话：**三份工程文档的上位依据是宪法 2.0，不是 v3.0**（旧规划依据栏明写"《AIOS核心系统宪法v2.0》"，且比 v3.0 早一天定稿）。

## 1.3 我的总体重构战略：三条铁律

### 铁律一：单一上位基线 + 编号唯一持有权（治理，先于代码）

- 所有工程文档 header 的"依据"必须写成 `《AIOS核心系统宪法v3.0.md》 @ <commit>`，并带**机器可校验的指纹行**；
- **验收编号 A/R/V/W 由宪法唯一持有**。架构规划、任务书、工作台、测试规范只能**引用**，不得**重定义**。冲突时宪法胜，且必须在 CI 里失败；
- 落地为一个 CI 脚本（新增 Issue `M0-027`）：扫描 5 份文档的编号定义块，检测同一编号出现两套语义即 fail。

这条不写代码，但它决定了后面所有 Issue 的编号能不能被信任。**我会先做这一条，因为 A07 二义这种事只要再发生一次，整个 Gate 体系就废了。**

### 铁律二：契约先行，但**区分"领域对象"与"控制面对象"**

M0 的实质不是"冻结 19 个对象"，而是"冻结 22 个领域对象 + 3 个控制面对象，且两类分表"：

- **领域对象**（进第 71 条表、进 `ObjectType` 枚举、进 `object_revisions`）：22 个，补 `Prediction` / `LifeChapter` / `CommunicationExperience`；
- **控制面对象**（**不进**第 71 条、**不进** `ObjectType`、单独 `control_plane_*` 表）：`BudgetLedger`（预算账本）、`ContextSnapshot`（会话上下文快照）、`TriggerExpression`（条件表达式）。

理由：控制面对象是**运行时可审计记录**，不是世界认知的一部分。把它们塞进第 71 条会污染"世界是什么"的语义边界，也会让时间金字塔、维度挂载这些机制误把它们当认知对象处理。**能力必须有，身份不必升格。**

### 铁律三：虚拟优先，但**穿戴契约从 M2 就存在**（同构，不是延后）

当前唯一目标是 Linux 上跑通虚拟闭环。但宪法第 98 条之一 / 第 104 条之一 的 FSM 与三层 UI 是**交互契约**，不是硬件驱动。

我的做法：**M2 就实现 FSM 状态机与三层 UI 契约，用虚拟执行器打桩**（`VirtualHapticActuator` 记录震动语义序列，`VirtualBoneConduction` 记录通断电时刻）。M8 换真实驱动时只替换适配器，状态机与验收用例一行不改。

**绝不允许"等 M8 有硬件了再写 FSM"**——那时状态机的边界条件（抢占、超时、断电恢复）已经无法回溯验证，而 FSM 恰恰是"零误触"这个产品命脉的唯一保证。

### B. M1-018 + M1-019 检索内核与共现引擎（静默崩溃点的解药）

**为什么必须现在做**：`object_revisions` 实测无 FTS、无倒排，三词共现只能全表 LIKE。实测 50 万行 319 ms → 100 万行 654 ms（线性），外推 500 万行 ≈ 3.3 s；FTS5 `unicode61` 对连续中文**命中 0 行**。

```sql
CREATE TABLE IF NOT EXISTS term_postings (
    term         TEXT    NOT NULL,
    object_id    TEXT    NOT NULL,
    object_type  TEXT    NOT NULL,
    field_path   TEXT    NOT NULL,          -- 'statement' / 'text' / 'title'
```

**共现检索算法（M1-019）**

```text
co_search(keywords: list[str], window: TemporalExtent, k: int = 20) -> list[SearchHit]

1. 归一：每个 keyword 经 term_aliases 映射到 term_key，展开同义词集合 T_i
2. 预裁剪：按 window 把每个 T_i 的候选集限制在时间窗内（走 idx_postings_term_time）
3. 交集：
     若 |T_i| 均较小 -> 直接对 object_id 集合求交（哈希集）
     若某 term 为超节点（postings > SUPER_NODE_THRESHOLD=50_000）
        -> 不用它做交集主体，改为"先交集其余 term，再用超节点做过滤"
4. 共振打分（三因子，min-max 归一后加权）：
     score = 0.45 * co_density          # 该对象上多 term 共现密度
           + 0.30 * recency_decay       # exp(-Δdays / 90)
           + 0.25 * importance          # 对象类型的先验权重（Claim/EventAnchor > Observation）
5. 排序取 top-k，返回**指针**（object_id + revision + field_path + snippet_offset）
   —— 绝不返回全文，AI 凭指针按需 world.focus 加载
6. 预算：单次 co_search 扫描 postings 行数上限 = 200_000；超限则收窄时间窗并置
   hit.budget_truncated = True（不得静默截断）
```

| 三词共现 p95（100 万行） | ≤ 200 ms | 实测倒排三词 31.3 ms（50 万行），留 6× 余量 |
| 中文召回@10 | ≥ 0.8 | 分词器 + 别名表；FTS5 兜底 |
| 单 term 内存驻留 | 不驻留 | postings 走 SQLite，进程内只缓存 top-200 热点 term 的 LRU（≤ 8 MB） |
| 索引水位 | 复用 M1-014 的 `STALE_INDEX` | 增量更新走 watermark，不全量重建 |

**验收标准**
- `M1-023` 规模门：100 万行合成数据，三词共现 p95 ≤ 200 ms，中文召回@10 ≥ 0.8，**连续中文查询命中数 > 0**（硬断言，`probe_cjk_tokenizer.py` 入 CI）；
- 超节点场景（单 term postings > 5 万）不出现 > 1 s 查询；
- 结果全部带 `source_refs` + `revision` + `coverage`。

**绝对禁止**
- 禁止把"全文搜索命中"当作事实成立（旧任务书 M1-012 已禁，保留）；
- 禁止用 `unicode61` 直接索引连续中文并宣称支持中文检索；
- 禁止返回全文而非指针（第 89.2 条：AI 凭指针按需加载）；
- 禁止静默截断：预算触顶必须置 `budget_truncated`。

**调度算法（三值求值 + 事件驱动就绪）**

```text
# 编译期（Task 创建/修订时，一次）
compile(task) ->
  for clause in task.trigger.clauses:
      match clause.kind:
        time_reached      -> insert trigger_time_due(due_at, task_id)
        event_occurred    -> for k in expand_event_keys(clause): insert trigger_subscriptions(k, ...)
        context_matched   -> for d in clause.dimensions: insert trigger_subscriptions('dim:'+d, ...)
        dependency_ready  -> for d in clause.dependency_ids: insert trigger_subscriptions('dep:'+d, ...)
  subscribed_terms = 上述所有 sub_key

# 运行期（事件到达时，O(命中订阅数)，不是 O(全量 Task)）
on_commit(world_revision, changed_objects):
  keys = union(event_keys(obj) for obj in changed_objects)
        ∪ union('dim:'+d for d in touched_dimensions)
        ∪ union('dep:'+dep_id for dep_id in resolved_dependencies)
  candidates = SELECT task_id FROM trigger_subscriptions WHERE sub_key IN keys
  for task_id in candidates:
      state = evaluate(task.trigger, world)     # 三值：TRUE / FALSE / UNKNOWN
      if state is TRUE and task.ready_state == 'dormant':
          task.ready_state = 'ready'; insert task_ready_queue(now, task_id, priority)
      # FALSE / UNKNOWN -> 保持 dormant，静默休眠，不进看板，不占上下文

# 唤醒时（Cockpit 组装，M2-017）
ready_tasks = SELECT * FROM task_ready_queue
              WHERE ready_at <= now ORDER BY priority, ready_at LIMIT budget.max_tasks
# 看板只挂 ready_tasks。dormant 任务一个都不出现。
```

**三值求值的必要性**：`UNKNOWN`（证据不足）不得当作 `FALSE` 丢弃，也不得当作 `TRUE` 唤醒。`UNKNOWN` 保持休眠并记录 `last_evaluated_at`，由 M2-007 的观察任务负责补证据——这正好把第 86 条与 V20（证据不足且允许多种解释）接起来。

**开销分析**

| 场景 | 旧方案（无脑遍历） | 新方案 |
|---|---|---|
| 1000 个待办任务、每次唤醒 | 1000 条 Task 进上下文 ≈ **25k~40k token** | 只挂 ready（典型 0~5 条）≈ **≤ 1.2k token** |
| 每次 commit 的调度开销 | 0（但把成本推给模型） | `O(命中订阅数)`，典型 < 20 行索引查找，**< 1 ms** |
| 一天 200 次唤醒的 token 差 | ≈ **5M~8M token/日** | ≈ **≤ 240k token/日** |

**验收标准**
- 创建无 `trigger` 的 Task → 契约校验失败（`extra="forbid"` + 必填）；
- 1000 个 dormant Task 场景下，Cockpit Manifest 的 task 区块 token 数 ≤ 1200（可测：统计序列化后 token）；
- 事件 commit 到 ready 入队的延迟 p95 ≤ 5 ms；
- `UNKNOWN` 不产生 Wake（断言：注入证据不足的观察，Wake 计数为 0）；
- TTL 到期的条件任务自动 `expired`，不产生"永久悬挂任务"（V07 三个月定时任务的机械化）。

**绝对禁止**
- **禁止"定期任务盘点"**：工作台规格 §7 该句必须删除。任何"每 N 小时把所有待办读一遍"的实现都属违宪；
- 禁止把 dormant 任务写进看板"以防遗漏"（这正是第 86 条禁止的挤占上下文）；
- 禁止用自然语言条件（`"当用户看起来心情不好时"`）作为 `predicate`——必须机械可判定；
- 禁止在 `evaluate` 里调用大模型（条件求值必须是纯机械的，第 79 条框架）。

### D. M2-017 Cockpit Manifest 组装与四步序契约

**为什么必须现在做**：M2-009 的 `workspace.open` 没有预算、没有段序、没有快照。第 84 条要求单次看盘 + 四步序不可颠倒；第 86.1 条要求严禁逐项复述看板。

**数据契约**

```python
class CockpitTier(StrEnum):
    SAFETY = "safety"      # 紧急高危
    ROUTINE = "routine"    # 日常
    REVIEW = "review"      # 复盘/深度调查

TIER_TOKEN_BUDGET: dict[CockpitTier, int] = {
    CockpitTier.SAFETY: 512,
    CockpitTier.ROUTINE: 2048,
    CockpitTier.REVIEW: 8192,
}

class ManifestSection(BaseModel):
    model_config = ConfigDict(extra="forbid")
    step: Literal[1, 2, 3, 4]            # 四步序段序，不可重排
    name: Literal["self_slice", "rapport_model", "stance_tone", "wake_and_world"]
    tokens: int = Field(ge=0)
    payload: dict[str, Any]
    refs: list[str] = Field(default_factory=list)
    stale_fields: list[str] = Field(default_factory=list)   # 过期地点等必须标 stale

# 段序与段名的绑定关系。只校验 step 编号是无效的——把 stance_tone 标成 step 1
# 同样能通过 [1,2,3,4] 检查，而那恰恰是第 84 条要防的"语调先于事实"。
STEP_NAMES: dict[int, str] = {
    1: "self_slice",        # 照镜子
    2: "rapport_model",     # 校准羁绊
    3: "stance_tone",       # 确立姿态与语调
    4: "wake_and_world",    # 审视世界与触发源
}

class CockpitManifest(BaseModel):
    model_config = ConfigDict(extra="forbid", validate_assignment=True)
    manifest_id: str
    session_id: str
    wake_id: str
    tier: CockpitTier
    sections: list[ManifestSection] = Field(min_length=4, max_length=4)
    ready_task_ids: list[str] = Field(default_factory=list)
    capability_registry: list[str] = Field(default_factory=list)
    total_tokens: int = Field(ge=0)
    budget_truncated: bool = False
    assembled_at: datetime

    @model_validator(mode="after")
    def validate_step_order(self) -> "CockpitManifest":
        # 必须同时校验"编号连续"与"编号↔段名绑定"，否则把 stance_tone 写成 step 1
        # 也能通过 [1,2,3,4] 检查（本方案的验证脚本曾因此漏过一次，已修正）。
        expected = [(i, STEP_NAMES[i]) for i in (1, 2, 3, 4)]
        got = [(s.step, s.name) for s in self.sections]
        if got != expected:
            raise ValueError(f"四步序段序不可颠倒：期望 {expected}，实得 {got}")
        limit = TIER_TOKEN_BUDGET[self.tier]
        if self.total_tokens > limit and not self.budget_truncated:
            raise ValueError(f"超出 {self.tier} 档预算 {limit} 却未标记截断")
        return self
```

**组装算法（并行取数 + 段序拼装，单次交付）**

```text
assemble_cockpit(wake, tier) -> CockpitManifest
1. 并行取数（四路并发，总超时 = min(300ms, tier_budget_ms)）：
     P1 self_slice      : AI 记忆树 + 上次介入停留状态 + 立场底线     (step 1)
     P2 rapport_model   : DIM_AI_RAPPORT 当前厚度 + 近期冲突/冷战标记  (step 2)
     P3 stance_tone     : 由 P1+P2 机械推导姿态基调指令（不调模型）    (step 3)
     P4 wake_and_world  : Wake Reason（第一任务指针）+ 现场切片 + 5D 概要
                          + ready_tasks（来自 task_ready_queue）      (step 4)
   任一路超时 -> 该 section 置 stale_fields 并降级为指针，不阻塞其余路
2. 预算裁剪（按优先级保序）：
     保留顺序 = step1 身份底线 > step4 Wake Reason 与 ready_tasks
              > step2 羁绊 > step3 姿态 > 其余概要
     被裁内容写入 omitted_json（指针，可按需回捞）
     若裁剪后仍超预算 -> 降档（REVIEW->ROUTINE->SAFETY）并记 degrade 事件
3. 拼装单 Prompt：四段按 1,2,3,4 顺序拼接为一个 prompt 字符串
4. 落库 context_snapshots（含 omitted），供 M2-024 高保真回放与 7 向归因
5. 返回 manifest；模型只被调用一次（此后是合法工具循环）
```

**四步序的落地裁决（写入任务书，避免再次误读）**

> **四步序 = 单 Prompt 内的段落组装顺序 + 四个必备决策因子，不是四次串行模型往返。**
> v3.0 第 84.1 条禁止的是**元对话往返**（"系统发提示词 → AI 说好的我知道了 → 再发下一段"）；第 91 条自身提供 30+ 原子工具，**工具循环合法**。
> 段序不可颠倒的工程含义：`stance_tone` 的输入必须包含 `self_slice` 与 `rapport_model`，因此**语调不得先于事实裁决**；`ManifestSection.step` 的校验器就是这个约束的机械化。

**验收标准**
- `ROUTINE` 档 manifest `total_tokens ≤ 2048`（p95），`SAFETY` 档 ≤ 512；
- 四路并行取数总耗时 p95 ≤ 300 ms（不含模型调用）；
- 段序校验器：人为把 `stance_tone` 放到 step 1 → 校验失败；
- 每次会话必有一条 `context_snapshots`，且 `omitted_json` 可据此重建"当时模型看到了什么"（V17 中断恢复 + 7 向归因的数据源）；
- 无认知增量时不写"本次无新反思"占位（第 86.4 条）。

**绝对禁止**
- 禁止要求模型对看板逐项复述或发表空洞分析（第 86.1 条）；
- 禁止用多次模型往返实现四步序；
- 禁止 `stance_tone` 在 `rapport_model` 之前生成；
- 禁止预算超支时静默截断（必须置 `budget_truncated` 并记 degrade）；
- 禁止把自然语言大摘要作为唯一入口（沿用 M2-009 原禁令）。

```text
on_user_turn(text):

    while window.tokens > 1500:
        evicted = window.pop_oldest()
        enqueue_extraction(evicted)          # 交后台，不阻塞前台

run_extraction(job):
    if idempotency.exists(job.idempotency_key): return      # 幂等
```

**验收标准**
- 连续 50 轮对话，前台窗口 token 始终 ≤ 1500，且第 50 轮仍能正确引用第 3 轮的事实（经 RecallLink 或萃取 Summary）；

- 禁止在前台路径上做萃取（会把首字延迟拖到秒级以上）；
- 禁止把萃取 Summary 自动全量灌回上下文（只能经 RecallLink 按需加载，第 15 条"禁止总结替代原始"）；
- 禁止无 watermark 的萃取（无法幂等，重跑必产生重复认知）；

```sql
    tokens_used   INTEGER NOT NULL DEFAULT 0,
    calls_used    INTEGER NOT NULL DEFAULT 0,
    tokens_budget INTEGER NOT NULL,
    calls_budget  INTEGER NOT NULL,
    degrade_level INTEGER NOT NULL DEFAULT 0,   -- 0=正常 1=降级 2=仅安全
    updated_at    TEXT NOT NULL,
    UNIQUE(scope, scope_key, period_start)
);
```

记账点：每次模型调用后由 C13 写账；超 80% → `degrade_level=1`（REVIEW 档降 ROUTINE）；超 100% → 抛 `BUDGET_EXHAUSTED` 并只保 SAFETY。**禁止**：禁止在业务代码里 try/except 吞掉 `BUDGET_EXHAUSTED`；禁止无账本的预算判断。

**M1-017 端侧轻量化摄入**：四类模态各自一条降采样管线 + `retention_class`（`hot`/`warm`/`tombstone`）+ `DeletionLog`（谁在何时依据什么删了什么，永久保留）。声纹走 M1-022 的**墓碑 + 回归重识别**：模板可淘汰，但 Speaker 稳定 ID 与墓碑永久保留，同一人再次出现时经重识别协议挂回原 ID，**不得聚成新编号**（第 35 条身份连续性）。
