# AIOS 法统与架构分层重构总纲

> **文件编号**：ARCH-PLAN-001
> **日期**：2026-09-18
> **性质**：方案提议（PROPOSAL），待项目所有者裁定后生效
> **提出背景**：现行法统缺少"完整系统架构"这一层。宪法条款各自描述一个想象中整体的局部，
> 导致不同读者拼出不同的系统。本文提出补齐该层的完整路径。
> **依据**：`00_AS_IS_现状架构测绘报告.md` 所列 8 项事实

---

## 一、问题定位

### 1.1 当前的链路

```
直觉（"这里需要这样，那里需要那样"）
  → 宪法 116 条
  → ❌ 缺失：完整系统架构
  → 代码（26 个包）
```

宪法在描述一个系统，但**那个系统从未被完整画出来过**。
于是每条宪法都在描述"整体的某个局部"，而每个读者想象的整体都不同。

### 1.2 这不是文笔问题

已被三次实测证明：

1. **ADJ 裁决集**：宪法自己和自己打架 6 处，其中 ADJ-004 的定性是"宪法允许另一条宪法违宪"
2. **Gap Audit**：M2-012 技术指导与宪法第 84 条"逐字相逆"，判词为 M2 断崖式卡死
3. **三模型整合实验**：最简单的"逐字合并"任务，三个模型交出三份不同结果（含日期语义篡改、条款编号改判）

> **两个认真的读者得出相反结论，说明缺陷在文本，不在读者。**

### 1.3 根因

`ADJ-004（永存）` 与 `第 33.5 条（物理删除）` 打架的根本原因，
不是措辞问题，而是**从未先确定"数据在这个系统里怎么流动、谁有权动它"**——
在没有地图的情况下，分别规定了两个路口的交规。

**架构就是那张地图。有了地图，大量"条文冲突"会自动降级为"模块边界划在哪"的具体问题。**

## 二、目标分层

| 层 | 名称 | 回答什么 | 可否证伪 | 变更成本 |
|---|---|---|---|---|
| L0 | **系统边界** | 输入什么、输出什么、绝不做什么 | 是 | 极高（动则重做） |
| L1 | **概念定义** | 22 个对象各是什么，一句话无歧义 | 是 | 高 |
| L2 | **数据流** | 一条 Observation 到"AI 说话"，怎么走 | 是 | 高 |
| L3 | **模块架构** | 系统由哪些模块组成，边界在哪 | 是 | 中 |
| L4 | **模块宪法** | 每个模块的输入/输出/禁止事项 | 是 | 中 |
| L5 | **工程/测试/验收方案** | 每个模块怎么做、怎么验 | 是 | 低 |
| L6 | **总项目方案** | 里程碑、依赖顺序、闸门 | 是 | 低 |
| **L∞** | **意图法源（现行宪法）** | **为什么、绝不允许什么** | **否（也不该）** | **最高** |

### 2.1 关键设计：宪法不废，而是分家

现行 116 条是**唯一记录项目所有者真实意图的东西**。
"反谄媚"、"黑盒零 UI"、"事是过客人是真理"——这些是项目的全部价值来源，
**架构可以重画，这些不能**。

正确处理：

- **宪法降级为"意图法源"**：回答"为什么"和"绝不允许什么"
- **架构升级为"实现法源"**：回答"是什么"和"怎么组成"

每条宪法条款挂到具体模块上。挂不上的，两种情况：
1. 它是**纯意图** → 保留，明确标注，不要求可执行
2. 它**缺模块** → 补架构

> 这个挂接过程本身，就会把现存全部冲突暴露成具体的架构问题。

### 2.2 三类条款必须分开写

现行宪法把三种不能混的东西写成了同一种句式（都是"第 X 条：……"）：

| 类别 | 例子 | 真假判定方式 | 归属层 |
|---|---|---|---|
| **意图** | "事是过客，人是真理" | 无法证伪，也不该证伪 | L∞ |
| **契约** | 22 个对象、字段、引用语义 | 机器可检 | L1/L4 |
| **阈值** | p95 ≤ 50ms、3~5 小时、1~3 句 | 压测 | L4/L5 |

AI 读到一句话时，第一个动作是**猜这是哪一类**。猜错就走偏：
- 把"1~3 句"当硬上限去截断输出 → R6 后来专门立法否定
- 把"四步序顺序绝不可颠倒"当成四次串行调用 → ADJ-001 后来专门澄清是排版顺序

**R6 已经对"规则与参数"做过这件事（Hard Boundary / Engineering Parameter / Cognitive Policy），
但从未对整部宪法做。本方案要求对 116 条逐条打标签。**

## 三、执行顺序

> 项目所有者提出的顺序：定义 → 架构 → 调整 → 最终架构 → 分模块宪法 → 工程/测试/验收 → 总项目方案。
> 本方案在其前面**增加 L0（系统边界）**，理由见 3.1。

### 阶段 0：系统边界（新增，1 页）

**为什么必须在最前面**：

现行宪法以"帮助用户"为最高目标，却**从未定义"帮助"以什么形式离开系统**。
第 98 条之一写了手环 FSM、第 85 条写了 1 秒首字、registry §6 写了 P0 安全动作——
全是**局部**。全系统的输出面从未被完整枚举。

**输出面不定，架构无法收敛**：无法判断一个模块是否必要。

**交付物**：

1. 输入源完整清单（传感器 / IM / 相册 / 用户直接输入 / 系统内生）
2. 输出面完整清单（震动 / 语音 / 屏幕 / 静默 / 对外能力调用 / 写回世界）
3. 明确不做的事（负面清单）
4. 系统与外部的信任边界

**验收**：项目所有者能逐条确认"对，这就是我要的边界"。

### 阶段 1：概念定义

22 个一等对象，每个一句话，**无歧义**。

判定标准：**同题分读测试**——让 3~5 个 AI 各自根据该定义回答一个具体行为问题，
答案一致 → 定义清楚；答案分叉 → 定义有缺陷，分叉点即待裁决项。

> 现状（见 AS-IS §3）：契约层 22/22 完备，但"谁负责其生命周期"不清楚。
> 本阶段要解决的正是后者。

### 阶段 2：数据流（关键，且所有者可亲自验收）

一条 Observation 从传感器进入，到 AI 说出一句话，**完整走一遍**：
经过哪些模块、在哪里落库、在哪里被判断、在哪里可能被丢弃、在哪里产生副作用。

**这一步不需要懂代码就能验收**——数据流讲不讲得通，是常识判断。

至少覆盖 4 条主干流：
- 正常感知流（传感器 → 认知 → 沉默或回应）
- 用户对话流（输入 → 召回 → 回应 → 写回双世界）
- P0 安全流（硬信号 → 首个硬件动作 → 事后认知研判）
- 维护流（总结重算 / 归档 / 索引重建，且**不得产生 Wake**）

### 阶段 3：模块划分（由数据流倒推）

**先有数据流，再有模块**，而不是先拍编号。
模块 = 数据流上职责内聚的一段。

同时终结 AS-IS F-3/F-4 记录的编号三账本并存问题：
产出**唯一**一份模块表，废止其余全部编号映射。

### 阶段 4：架构调整与定稿

用 4 条主干流回放新模块表，检查：
- 有无模块无人负责（如当前 C01/C13 无定义）
- 有无两个模块干同一件事
- 有无依赖方向违规（如当前 `ingest → bench`）

### 阶段 5：分模块宪法（L4）

每个模块一份，固定结构：

```
模块名 / 唯一编号
├─ 职责（一句话）
├─ 输入契约（来自哪些模块、什么对象）
├─ 输出契约（产出什么、谁消费）
├─ 禁止事项（红线，fail-closed）
├─ 继承的意图条款（挂接到 L∞ 的哪几条）
├─ 可调参数（按 R6 三分法标注 class + mutable_by_ai）
└─ 验收场景（二值，进 CI）
```

### 阶段 6：工程 / 测试 / 验收方案

每模块一套，与 L4 契约一一对应。

### 阶段 7：总项目方案

里程碑、模块依赖顺序、Gate 判据。此时才有资格排期——
因为到这一步，"做出来是什么东西"才第一次有确定答案。

## 四、防漂移机制：唯一支点是可执行场景

### 4.1 传话游戏问题

```
宪法 → 架构 → 任务书 → 代码
```

每一跳都是散文翻译散文，每跳损耗一点。
**散文之间无法固定，因为散文没有真假。**

### 4.2 唯一能固定的东西

```
"凌晨两点摔倒 → 首个硬件安全动作发生前，LLM 调用次数必须为 0"
```

这句话是**二值**的。代码要么通过要么不通过，没有第三种理解。

> registry §6 第 5 条已经这么写了 P0 硬约束——那是现行文档里为数不多真正**锁死**了的东西。

### 4.3 因此本方案的核心主张

> **宪法的价值不在于它有多完整，而在于每一条能不能落到一个二值场景上。**
>
> - 落不到的 → 它是意图（这没问题，标清楚即可）
> - 落得到的 → 它才是规格，必须进 CI

L4 每个模块的"验收场景"进 CI 后：
- 宪法改了但场景没改 → 红灯
- 代码漂了 → 红灯

**这才是能回答"做出来是什么东西"的机制——因为场景就是答案本身。**

## 五、所有者需要做的事（不需要懂代码）

整个流程中，只有四件事**必须**由项目所有者决定，且都不需要技术背景：

| 阶段 | 需要你做的判断 | 形式 |
|---|---|---|
| 0 | 系统边界对不对 | 逐条确认清单 |
| 2 | 数据流讲不讲得通 | 常识判断 |
| 1/3 | 同题分读的分叉点选哪个 | **在两个具体行为之间选一个** |
| 5 | 红线认不认 | 逐条确认 |

其余全部是执行。

> 分叉点裁决是最关键的一项：AI 可以把分歧找出来、摆清楚，
> 但"我到底要哪个"只有你能回答。
