## 一、哪个环节最消耗 Token？

**看板之外的隐性全量物化**（不是"检索"本身）。

- 倒排共现 `co_search` 正确地只返回命中 `SearchPage.hits`（指针级），这是省 Token 的
  做得对的地方。
- 真正的 Token 黑洞在**驾驶舱组装前的证据二次物化**：`CockpitPipeline.assemble_cockpit`
  把活动窗口 + 争议证据**全量文本**逐字拼进 prompt。窗口小（5~8 轮）时代价可忽略；
  一旦检索半径扩大（用户问"三年前那件事"），证据摘要会被整段复制进 1500 Token
  封套，**封套内的自我截断发生在 CPU 端**，但送审前已经为"被截断的段落"花掉了
  前序大模型的一轮 prefill。
- 结论：**Token 上限是 $\sim O(窗口+证据)$，且截断发生在正确性代价之上**（截断 ≠
  免费，前面的推理已消耗）。出口＝TLP-C02 的指针优先投影 + 争议点摘要化（只送
  `(object_id, sha256, excerpt)`，物化只在被问到时发生）。

## 二、哪个查询最消耗 I/O？

**写路径 commit 的引用校验点查**（$O(\text{对象数} \times \text{引用数})$）。

- 实测：500 obs/批 → P50 880ms / P95 1069ms。239 批共用 260 秒里的大头。
- 根因：`SQLiteWorldStore.commit` 中 `_collect_refs` + `_reference_exists` 对每条对象
  做 SQLite 点查，且**同一批内重复引用同一实体时不会复用已见的 pending 对**——
  虽然已有 `pending_objects` 缓存，但 `pending_pairs` 的查找发生在对象循环复走。
- 读路径 `co_search` P99 9.5s 尖刺 = **请求路径上的同步 `catch_up()` 重建投影**（
  `WorldSearchIndex.catch_up(max_rows=50_000)`）。这不是 bug 而是纪律换取的正确性
  退化——strict 模式下宁可回 `stale_index`，adaptive 才追。但"追"的时机不该在
  用户请求上。
- 结论：**I/O 瓶颈 = 写路径点查放大 + 读路径同步追赶**。

## 三、哪个认知抽象最容易失真？

**"误把邻接当因果"的跨维度共振边界**。

- `derive_dimension()` 靠 `source_kind` 字符串 + 若干关键词探针把对象推向
  dim_health / dim_finance / dim_social / dim_work。这是**启发式**，不是证据学——
  同一条文本"老王说再借一笔就能翻盘"会被健康/金融两个维度同时命中，但**没有任何
  边只标注它是"金融维度的主张、健康维度只是上下文"**。
- 后果：`search_mind` 的四维原生检索在召回上没问题，但在**可解释性**上把
  "共现"与"共振"混为一个分数，极易在复盘时失真成"AI 认为早搏和借贷有因果"。
- 出口：事件锚点 `EventAnchor` 已在契约里有 `primary_claim_refs` 与
  `evidence_set_refs` 之分——**应强制"共振合成必须锚定 EventAnchor，不许让裸文本
  直接升维"**（本盲测阶段三已按此纪律走了版本化流转）。

## 四、为什么现有实现还不够完美？（不粉饰的三条）

1. **批内重复引用无去重**：commit 对同实体多对象复用 pending 时仍各查一遍，
   在 x10 密度上非线性放大（见 §二）。
2. **投影追赶在请求路径**：`co_search` 的 `catch_up` 属于同步热路径；正确性之上
   的可用性缺口（P50/P95 完美、P99 崩）恰恰是"只在极端处崩"最危险的一种。
3. **极简护栏与证据引用割裂**：BrevityGuard 保证 1~3 句，但没说这 3 句**必须**带
   从世界日志里可校验的 `evidence_refs`——"有分寸"仍停在字数上，未上升到
   "每句立场有出处"。runtime_policy 已经写了 `stance_origin_must_be_traceable`，
   但执行层尚无机械校验。

## 五、一处 GAP-003 契约缺陷（如实点名）

`ToolProposal` 契约字段 `capability_gap / expected_benefit / use_cases` **没有
min_length 强校验**；`ToolProposalPipeline.submit_proposal` 只做状态归一
（DRAFT→SUBMITTED），未落地 GAP-003 原文要求的"严格校验能力缺口说明与预期收益"。
空能力缺口的提案可以被提交。盲测结论已落测试
`tests/tools/test_tool_proposals_arena.py::test_tool_proposal_capability_gap_is_plain_field_not_validated`，
供 GAP-003 负责方收紧（涉及 `contracts/models.py` 生产契约，本测试组遵守
"生产文件未获授权不动"纪律，只记录不擅改）。
