# 交付物 ② · 全生命周期心智瓶颈与缺陷诊断书

> 诊断对象：AIOS 3.0 八阶段全生命周期（S1 摄入 → S8 驾驶舱/硬旁路）。
> 诊断方法：由**独立对抗数据发生器**驱动八阶段盲测，取真实度量
> （`evidence/gate_snapshot.json` = 1,147,788 条原始样本；`evidence/full_snapshot.json` = 4,579,518 条），
> 并在 ALL-SQL 落库产物上做二次统计（GATE 22,357 条结构化 Observation / 22,414 个修订 / 1,095 天；
> FULL 33,238 条 / 33,295 个修订）。
> 全文不引用任何"设计意图"，只引用**跑出来的数字**；对"修复前"的口径单独标注证据文件。

## 1. 瓶颈一：Token 花在哪 —— S1 吃掉 92.7% ～ 95.0%，且花在"数量"而不是"信息"上

### 1.1 实测分布（修复后口径）

| 阶段 | GATE Token | 占比 | FULL Token | 占比 |
| --- | ---: | ---: | ---: | ---: |
| S1 摄入提纯 | 134,142 | **92.72%** | 199,428 | **94.98%** |
| S2 金字塔/晶格 | 8,760 | 6.06% | 8,760 | 4.17% |
| S3 召回/共振/事件 | 24 | 0.02% | 24 | 0.01% |
| S4 认知导数/维度闸 | 112 | 0.08% | 112 | 0.05% |
| S5 回溯/单跳/双镜 | 64 | 0.04% | 64 | 0.03% |
| S6 共生决策 | 209 | 0.14% | 209 | 0.10% |
| S7 沟通博弈/人设 | 124 | 0.09% | 124 | 0.06% |
| S8 驾驶舱/硬旁路/对话 | 1,236 | 0.85% | 1,236 | 0.59% |
| **合计（月度封套 2,554,000 的占比）** | **144,671（5.66%）** | 100% | **209,957（8.22%）** | 100% |

> S1 的 Token 计费口径是**每个落库对象 6 token + 1 次调用**（`S1.edge_purifier`，calls = 落库行数）。
> 也就是说：**Token 花在"行数"上**——一次三年全量摄入（4,579,518 条原始样本）折算 33,238 行 ⇒ 199,428 token。

### 1.2 行数结构（FULL 档 33,238 条落库对象）

| 数据类型 | 行数 | 占比 | 是否携带新信息 |
| --- | ---: | ---: | --- |
| `wearable_camera_caption`（图像 Caption） | 17,520 | 52.7% | 否（例行，同一厨房反复出现） |
| `wearable_ppg`（稳定期区间均值） | 13,463 | 40.5% | 否（例行） |
| `wearable_imu`（宏观运动状态） | 2,193 | 6.6% | 否（例行） |
| `wearable_ppg_anomaly`（心率突变波形） | 20 | 0.06% | **是** |
| `phone_message`（对话/短信证据） | 18 | 0.05% | **是** |
| `wearable_mic_asr`（语音证据） | 12 | 0.04% | **是** |
| `wearable_imu_impact`（异常冲击波形） | 10 | 0.03% | **是** |
| `phone_gps`（位置状态变更） | 2 | 0.01% | 是（稀疏） |
| **合计** | **33,238** | 100% | 证据行仅 **30 行 = 0.090%** |

GATE 档同口径（22,357 条）：照片 8,760（39.2%）、心率均值 12,468（55.8%）、运动状态 1,074（4.8%），
证据行同样 **30 行 = 0.134%**。

**结论**：Token 的 **99.9%** 花在"例行行"上；真正的信息（30 条证据行）只值 180 token。
这不是"钱花多了"，而是**计费口径与信息量脱钩** —— 一个抽象层的设计缺陷。

### 1.3 已完成的收敛（本轮修复带来的变化）

| 口径 | FULL S1 Token | 月度封套占比 | 说明 |
| --- | ---: | ---: | --- |
| 修复前 | 2,766,396 | **108.7%**（当场透支） | 假冲击把行数抬了 13.9× |
| **修复后** | **199,428** | **7.81%** | 同样的原始数据、同样的发生器种子 |

> 诚实说明：**"三年回灌必然透支月度封套"这个结论只在修复前成立**，它是假冲击缺陷的并发症。
> 修掉缺陷后，一次三年全量摄入只占月度封套的 8.22%（含 S2~S8 全部认知开销）。

### 1.4 根因与修法（仍未做的那一半）

- **根因**：抽取/结算链路以"每条 Observation 一次 LLM 抽取"计费（`calls = durable_row_count`），
  而例行行的语义增量恒为 0（稳定心率区间均值、同一厨房的重复 Caption）。
- **修法（P0，预计再降 10～20×）**：
  1. **机械先行**：例行行只做机械结算（区间均值/状态聚合），**0 token**；
  2. **信息门**：只有满足任一条才进入抽取 —— 变化点检测命中、跨域共现、异常阈值、用户语义事件；
  3. **封套护栏**：把"每千行最多 N 次抽取"写进 `runtime_policy.json`，超限走 `defer`。
- **预期收益**：GATE 档 S1 从 134,142 → **≈ 700 token**（30 信息行 × 6 + 少量变化点）；
  FULL 档从 199,428 → **< 20,000**（占月度封套 <1%）。
- **验证方式**：盲测新增断言 `S1.tokens ≤ 信息行数 × 常数`；`pytest` 加一条"例行行零计费"用例。

### 1.5 本轮 P0 缺陷 #0：冲击判据只看绝对值 → 例行跑步被当成跌倒

**现象**（修复前全量档，证据 `evidence/full_snapshot_prefix_461k.json`）：

| 指标 | 数值 | 备注 |
| --- | ---: | --- |
| S1 落库对象 | 461,066 | 其中 `wearable_imu_impact` **427,838 = 92.8%** |
| S1 耗时 | 303,122.6 ms | 同口径修复后 121,848.3 ms（2.5× 更快） |
| S1 Token | 2,766,396 | 月度封套 108.7% |
| DB 体积 | 571.7 MB | 修复后 34.8 MB |
| 峰值 RSS | 744.2 MB（仅 S1+S2 段） | 修复后全八阶段 638.9 MB |
| S3 | **三次被内核 OOM/SIGKILL 杀死** | 修复后 1,674.0 ms 通过 |

**根因链**（逐环可复核）：

1. 发生器 `run` 段的 z 轴基线 **1.9 g**、噪声 σ=0.16 g（`adversarial_life_bench._imu_samples`）；
2. 压缩器的冲击判据是 `peak_g ≥ impact_threshold_g (默认 2.0)` —— **只看绝对值、不看基线**；
3. `max_segment_span_s = 30 s`，而一次跑步 24 秒 1,200 点 ⇒ 被切成上百段；
4. 每段一旦 `peak ≥ 2.0` 就升格为 `ImpactWaveform` 并**逐点入库**（`_observation(kind="impact_waveform")`）；
5. 4,579,518 条原始样本 ⇒ 427,838 条"假跌倒" Observation ⇒ 存储、Token、内存三线同时爆掉，
   全库建图对象数 ×13.9 后把 4 GB 机器打爆。

**修法（已落地）**：

| 修改 | 语义 |
| --- | --- |
| 判据双条件：`peak_g ≥ impact_threshold_g` **且** `peak_g − 上一段基线 ≥ impact_delta_g`（默认 1.0 g） | 真实跌倒的特征是**自由落体后的陡增**，不是"绝对值高" |
| 冲击后**基线重估** `baseline = max(段均值, 阈值/2)` | 不拿"跌倒那一跳"当新的常态 |
| 冲击波形保留上限 `max_impact_samples = 32`（只留峰值附近窗口） | 单条有界，杜绝"整段波形搬库" |
| 上限导出为唯一常量 `MAX_IMPACT_WAVEFORM_SAMPLES`，与存储审计共用 | 消灭"压缩器留 40 点 / 审计线 16 点"的口径漂移（旧版正是它报出 2 例越线） |

**复测**：427,838 段假冲击 → **7 段跑步尖峰（记为 `IMPACT`，不升级为 `FALL_SUSPECT`）**；
3 条真实跌倒（3.45 g）仍被准确判为 `FALL_SUSPECT` 并原样保留波形；
`motion_compression_ratio` 由虚高的 813× 回到真实值 **1,790.47×**。

**机制级教训（已写进代码注释）**：物理量判据必须**成对**给出（绝对阈值 + 相对变化），
否则任何"基线本身很高"的常态活动都会被判成异常。这条规则同样适用于心率、声压、光照等所有端侧阈值。

## 2. 瓶颈二：I/O 花在哪 —— "全库建图"是唯一随历史线性膨胀的操作

### 2.1 实测排行（修复后）

| 操作 | 档位 | 调用/样本 | P50 | 说明 |
| --- | --- | ---: | ---: | --- |
| `S1.ingest_batch_ms`（4 万样本/批） | GATE / FULL | 7 / 16 | **2,405.78 / 7,496.20 ms** | 纯 CPU 端侧提纯（不含写盘） |
| `S1.commit_batch_ms`（4,000 行/批） | GATE / FULL | 7 / 16 | **779.45 / 515.01 ms** | SQLite 追加式落库（≈0.19 / 0.13 ms/行） |
| `S3.traverser_build_ms`（**全库建图**） | GATE / FULL | 1 / 1 | **766.95 / 1,065.61 ms** | 22,367 / 33,248 节点，全库扫描 |
| `S5`（台账 + 隔离 + 双镜） | GATE / FULL | 1 / 1 | ≈3,007 / 4,356 ms | 其中台账落账为 O(N)，N = 22,357 / 33,238 |
| `S3.traverser_query_ms`（四级穿透） | GATE / FULL | 1 / 1 | **0.266 / 0.265 ms** | **成本与图规模无关**（结论成立） |
| `S2.pyramid_rollup_ms` | GATE / FULL | 3 / 3 | 4.37 / 3.83 ms | 金字塔逐级汇总很便宜 |
| `S2.drill_down_ms`（无损穿透） | GATE / FULL | 5 / 5 | 0.031 / 0.031 ms | 下钻几乎免费 |
| `S3.cooccurrence_bus_ms` | GATE / FULL | 1 / 1 | 0.150 / 0.128 ms | 召回总线亚毫秒 |
| `S3.exact_intersection_ms` | GATE / FULL | 1 / 1 | 0.188 / 0.234 ms | 精确倒排（0 命中） |
| `S8.p0_bypass_ms` | GATE / FULL | 200 / 200 | **0.0052 / 0.0046 ms** | 硬旁路（P99 0.0262 / 0.0123；MAX 0.055 / 0.024） |
| `common.commit_ms`（世界对象提交） | GATE / FULL | 16 / 16 | 3.70 / 3.43 ms | 单对象短事务 |

### 2.2 事故证据：建图线性膨胀 + 假冲击放大 = 4 GB 机器被打死

- **修复前**：全量档位单进程八阶段 ⇒ S1（305,223 ms）+ S2（22,557 ms）后，进程在 **S3**
  被内核 OOM 杀掉（`total-vm:3959332kB, anon-rss:3881692kB`，机器 `MemTotal 4,034,452 kB`）；
  另外两次复现分别是 SIGKILL 退出码 137 与 `--stages 1,2` 分段落跑（461,066 条落库，571.7 MB DB）。
- **放大因子**：假冲击把对象数从 33,238 抬到 461,066（**13.9×**），而 `build_from_store` 是**全量重建式**建图。
- **修复后**：同样单进程、同样 4 GB 机器 ⇒ S3 **1,674.0 ms**、阶段内存增量 **181.4 MB**、八阶段全部通过。
- **结论**：`build_from_store` 仍是**唯一随历史线性膨胀**的操作（22,367 节点 767.0 ms → 33,248 节点 1,065.6 ms，
  基本线性），它同时也是"老王案不重算历史"精神的反面：**每次唤醒都重建全图，等于每天都在全量重算**。
  本轮它不再是阻塞项，但仍是架构缺口。

### 2.3 根因与修法（工具 #11，建议下一轮立项）

- **根因**：图索引没有增量维护能力，只有"从存储全量重建"一条路；且重建产物常驻内存。
- **修法（P1，新增工具 #11）**：
  1. 以 `entity_id → anchor/observation` 的**持久化邻接表**替代内存重建（SQLite 侧已有 `cjk_inverted_index` 先例）；
  2. 写入路径登记边（对象提交时增量更新），读取路径只做局部展开；
  3. 对"必须全量"的运维动作加显式配额与流式游标（禁止整体载入）。
- **预期收益**：S3 建图从 O(全库) 降为 O(增量)；FULL 档 S3 内存从 181 MB 降到 **< 50 MB**，
  `build_ms` 与历史规模脱钩。
- **验证方式**：断言 `build_ms` 在 10× 历史规模下增长 < 2×；`--profile full` 单进程跑通（**已达成**，作为回归基线）。

## 3. 瓶颈三：认知抽象失真排行

### 3.1 冠军：日结晶四轴密度投影（失真最严重）

实现口径：`x = min(1, 生理点/60)`、`y = min(1, 社交点/40)`、`z = min(1, 财务点/5)`、`r = min(1, 证据数/4)`。
对 1,095 天逐日统计（真实落库产物，`blind_bench_gate.db` 二次统计，已在新旧两次构建上复算，结论一致）：

| 轴 | 均值 | 中位 | 最大 | 为 0 的天数占比 | 触顶天数 |
| --- | ---: | ---: | ---: | ---: | ---: |
| x 生理/60 | **0.3400** | 0.3333 | 0.4000 | 0.0% | 0 |
| y 社交/40 | 0.0007 | 0.0000 | 0.0500 | **97.5%** | 0 |
| z 财务/5 | 0.0004 | 0.0000 | 0.4000 | **99.9%** | 0 |
| r 证据/4 | 0.0068 | 0.0000 | 0.5000 | **97.5%** | 0 |

三个失真：

1. **单轴支配**：x 轴几乎恒定（0.34，三年波动 ±0.06），整个"人生密度"被传感器条数主导；
   真正的事件（吵架、判决、住院、搬家）在 y/z/r 上表现为**几乎全零**，等于被抽象层抹平。
2. **权重错配**：x 轴统计"所有 `wearable_*` 行"，于是 **8,760 张厨房照片 Caption（占 x 轴 39.2%）
   与 20 条心率突变波形同权**。一卷饺子皮 = 一次室性早搏。
3. **永不触顶**：四轴都没触顶 ⇒ 归一化分母（60/40/5/4）与真实分布严重不匹配，
   阈值型判断（"今天密度异常"）在这套坐标下**永远不会触发**。

**修法**：把密度轴换成"语义类别计权"——证据/事件/异常权重 1.0，例行传感 0.05，Caption 计 context 不计 health；
或直接改为两轴（事件密度 + 证据密度）并把归一化分位数改为**滚动分位**而不是拍脑袋常数。
**验证**：断言三年中"事件日"与"例行日"在该投影上的可分性（如 ARI / 简单阈值召回率）≥ 0.8。

### 3.2 亚军：维度曲线导数的**单位失真**

`DimensionCurveTracker` 的一阶/二阶差分以"单位/秒"计算，而《身心耗竭》是**月度**维度：

```
detect_trend("dim_burnout").velocity_avg     = 6.411765785398406e-09
detect_trend("dim_burnout").acceleration_avg = -8.429657304903644e-17
```

数值上等价于 0 —— **任何基于该导数的阈值永远打不到**，拐点/熔断只能靠 `trend` 标签的启发式。
盲测不得不在认知层另加"月度一阶/二阶差分"口径，才得到可执行的结论：
`月加速度 +0.0080/月²、速度 +0.0720/月 ⇒ 建议在 2025-09 前熔断通宵加班`。

**修法**：曲线按 `granularity` 归一（"单位/月""单位/周"），或提供 `detect_trend(..., normalize=True)`；
并规定**阈值必须带单位**（宪法第五编"参数也是法律"的精神）。

### 3.3 季军：摘要层的"证据连接"是偶然成立的

第一次实现里，晶格从 `YEAR→QUARTER→MONTH→DAY` 下钻后机械取"第 0 条原始事件"取引文，结果**取到空**——
因为 1,095 天里只有 27 天带证据，月初那天通常只有例行数据。
修复后（取"第一条真正挂证据引文的事件"），晶格路径与金字塔路径**命中同一条原始引文**。

**教训（机制级）**：只要摘要节点不显式携带"证据引用集合"，所谓"无损穿透"就只是**运气**。
本次已把该约束写成断言：`crystal_drill_text == drill_chain_text`（两条独立路径必须命中同一条引文）。

### 3.4 其他可疑失真（观测到但未量化到可判决）

- **晶格 `scale_counts()` 语义**：GATE 档位 DAY/WEEK 计数为 0（由下钻现算、不常驻），容易被误读为"覆盖不全"。
  已加注释与文档说明；建议未来统一为 `materialized` / `computable` 两个字段。
- **日摘要 `evidence_ids[:16]` 截断**：本数据集单日证据 ≤2 条，**截断未触发**，
  但属潜在失真（证据多的日子会被静默丢弃尾部引用）。建议改为"必留 + 抽样"策略并记录截断计数。
- **心率压缩"均值化"的信息损失未量化**：`hr_episode_mean` 只留区间均值（13,483 条），
  区间内的变异/趋势被丢弃；`AnomalyWaveform` 只捕获越阈段的突变（20 条）。
  当前无指标衡量"均值是否吃掉了缓慢漂移"，列为下一轮观测项。

## 4. 为什么"现在的实现"不完美（根因归并）

| # | 根因 | 表现 | 层级 |
| --- | --- | --- | --- |
| **R9** | **阈值判据只看绝对幅度、不看相对基线** | 例行跑步被判成跌倒冲击：427,838 条假冲击、92.8% 存储与 Token、S3 OOM | **端侧算法（本轮已修）** |

### 关于 FULL 档 ingest 非线性的诚实说明（本轮更新）

同一套代码，每 4 万样本批次的耗时从 GATE **2,405.78 ms** 涨到 FULL **7,496.20 ms**（**3.12×**）。
其中一部分是**真实的量**：单批原始子样本量 = 286,220（FULL）vs 163,969（GATE），即 **1.75×**。
剩余 **≈1.8×** 仍未定位。已排除的候选：批大小（相同）、写盘（提交已单列计时，FULL 反而更快）。
**仍未被证实**的怀疑：① 内存压力下的 GC（FULL 常在 120～240 MB 段波动）；② SQLite WAL 增长；
③ 文本/Caption 链路的正则开销。
**对比修复前**：同口径曾是 FULL **16,915.19 ms** / 同期 GATE **2,103.57 ms**（**8.04×**）——
  也就是说，**一半以上的"非线性"其实是假冲击写的账**。
**下一步**：在 purifier 内按通道打点（`imu_ms`/`hr_ms`/`image_ms`/`text_ms`），一次 FULL 跑就能定位。

## 6. 未解问题（留给下一轮，不装作已解决）

1. **7 条跑步尖峰仍被记为 `IMPACT`**（FULL 档）：双条件判据下它们满足"相对起跳 ≥1.0 g"，
   未被升级为 `FALL_SUSPECT`，但仍是 7 行存储。要不要引入**三轴方向性判据**（跌倒的自由落体方向特征），
   需要总工裁决（涉及"宁可多留可疑"与"存储宝贵"的取舍）。
2. **语义质量**（建议是否真"硬核"、人设是否真不爹味）只过了机械护栏，**未接真实大模型**。
3. **抽取计费解耦尚未落地**：S1 仍按行计费，是当前最大的 Token 浪费点（99.9% 花在例行行）。
4. 召回总线的种子扩展表目前是内置词元表，**尚未由 `OperationExperience` 自动演化**（接口已留）。
5. 声纹 180 天淘汰在盲测里是"到期即墓碑化"，**跨设备重绑场景未覆盖**。
6. `LifeChapter` 相变只验了"封旧开新 + 基线重置"，**相变后的敏感规范差异**未做端到端断言。
7. **增量图索引未落地**：S3 仍是全量重建建图，只是本轮规模回到真实量级后不再爆内存。
