# 《全生命周期心智瓶颈与缺陷诊断书》

**归档线**：MEGA-PIPELINE-001（与 01 号压测报告同锅实测）

## 一、第一瓶颈：S3 多维检索——索引全量重建（P50 ≈ 5.4s @ 20k）

**病灶**：`SearchIndexWorker.rebuild()` 在 `ensure_fresh=True` 语义下对 20k
对象做**全量重建**——每次查询前的“保鲜”= 推倒重铺。实测单次 5.408s
（P95 5.424s），是 8 阶段中唯一秒级环节，且随对象数线性恶化。

**为什么现有实现还不够完美**：因为有新鲜的途径而不走快速路。
水位增量（catch_up 语义）本就可以只铺 delta（rev 水位差），同一进程内的
`MultidimensionalSearchEngine`（M5 志愿跑道，`query/search_m5.py`）已用
`catch_up()` 证明了幂等增量路能跑通且水位诚实（lag 明示）；CoSearch 这条
canonical 快速路却把“新鲜”与“全量重建”焊死在一起。

**处方**：`rebuild()` 唯一公开入口保留，内部改走
`revisions_after(watermark)` 增量铺面 + 全量兜底开关；词典版本指纹不变，
行为面零回归（词典与 postings 都是物化视图，重建与增量的结果函数等价）。

## 二、第二瓶颈：S5 历史指纹——python 级全量 stringify（wall 4.5s）

**病灶**：20k 行 `json.dumps(sort_keys)` 全量哈希。审计面正确，
但复杂度可以 O(Δ)：对象级 hash 链（per-revision chained digest）落
`world_meta`，回放期只算差。

**为什么还不够完美**：铁律 2 的审计是对的，但审计器本身在
N 面前退化遍证；hash-chain 把“全量再证一次”压成“O(1) 夺顶”。

## 三、第三瓶颈：S1 读面全扫（wall 1.1s，主体是 20k 行 list_payloads）

噪声/证据扫面仍是 python 循环。检索面（`search_m5` / FTS）应该把这类
布尔分类下推到 SQL `LIKE/FTS` 谓词；边缘提纯的算子（TP-001）本体 23ms
已证：不是算子慢，是读面粗。

## 四、I/O 最贵查询排名

1. `SearchIndexWorker.rebuild()` 全量物化（20k 对象逐行重算 postings）；
2. `list_payloads()` 全量行出（S1/S5 双阶段重复支付，未缓存复用）；
3. FTS/BM25 词典包 `build_pack`（每次 CoSearchEngine 构造的重复铺面）。

## 五、最容易失真的认知抽象

**维度扣分制静态化**：`DynamicRapportModel` 在我们的 quick-lane 实现里
走纯积分阈值；人的关系真实曲线非线性（危机共渡权重应随时间衰减又随
复盘再生）。本次 bench 里的分数门槛是按治理表走的——诚实，但粗。
处方：羁绊曲线加“危机事件半衰期 + 复盘复权”二项；治理件照常走变更。

## 六、缺陷总账

- CoSearch 无增量索引合并（01 报唯一秒级，主欠账）；
- 历史审计无 chained digest（O(N) 重复支付）；
- 读面无缓存复用（同阶段两次全导出）；
- 羁绊/分数模型为治理静态比（非失真但简化）；
- 边缘噪声判定仍需真实 LLM 复盘环（本次以确定性判废替代，流程已通，
  语义判定供给待接入）。
