## 1. 审查范围

M0-012 只冻结 EventAnchor 数据契约和事件状态转换语义，不实现 M1 Event 服务，也不实现 M3 依赖传播/纠错引擎。

依据任务书与 R2，本任务必须证明：Event 是对现实的解释锚点而非底层事实；CANDIDATE/ACTIVE/RESOLVED/REVISED/REJECTED/MERGED/SPLIT 可表示认知演化；旧 Event revision 不被覆盖；修订、合并、拆分保留可下钻引用；Event 不复制完整 Observation。

## 2. 最终契约

EventAnchor 保留既有字段并增加/冻结：

- `primary_claim_refs`
- `evidence_set_refs`（兼容既有通用证据引用）
- `support_evidence_set_refs`
- `counter_evidence_set_refs`
- `supersedes_refs`
- `merged_into_ref`
- `split_from_ref`
- `split_child_refs`
- `revision_reason`

证据、Claim 与事件历史 provenance 引用必须 pinned。participant_refs 仍允许 floating，以保持稳定 Entity ID 的身份导航语义；这不改变证据历史冻结规则。

REVISED 必须有 supersedes_refs；MERGED 必须有 merged_into_ref；SPLIT 必须有 split_child_refs；REVISED/REJECTED/MERGED/SPLIT 必须记录非空 revision_reason。

## 3. 状态机

现有 `services/state_machines.py` 已满足本任务规定的关键转换，因此没有为通过任务而改写状态机：

- CANDIDATE -> ACTIVE：允许
- CANDIDATE -> REJECTED：允许
- ACTIVE -> REVISED：允许
- ACTIVE -> RESOLVED：允许
- MERGED：终态
- SPLIT：终态
- CANDIDATE -> RESOLVED：拒绝

## 4. 关键回放证明

测试以同一稳定 Event ID 建立三版历史：

1. rev1 CANDIDATE：`可能是体育活动`
2. rev2 ACTIVE：`学校运动会`
3. rev3 REVISED：`校内田径测试`

rev3 明确 supersedes rev2，并记录“用户明确说明活动性质，修正先前运动会解释”。按 object revision 与 world revision 查询均能回放 rev1/rev2/rev3，因此“当时为什么猜错”和“后来为何修正”不会因新 title 覆盖历史而消失。
