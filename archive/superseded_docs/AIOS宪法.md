## 第一章：AIOS 是什么

### 1.1 一句话定义与本质

> **AIOS 是 AI 大模型的底座世界，在这个世界里，AI从头到位的认识了一个人，然后建立了自己的认知，在这个认知下，主动 或者被动，或者事件触发，来给用户带来帮助，不论是生活 工作 技能 兴趣 爱好 学习等等全方位的帮助。**
> 
> **最终愿景：把 AI 的能力，变成用户在现实世界中的能力。**

### 1.2 AIOS 不是什么

| AIOS 不是 | AIOS 是 |
|---|---|
| 聊天机器人 | 持续运行的认知系统 |
| AI 助手 App | 操作系统级的 AI 运行时 |
| 功能集合 | 一套基础设施，功能是插件 |
| 某个大模型的客户端 | 模型无关的 AI 内核，模型只是算力供应商 |
| 一次性工具（问完即走） | 长期陪伴系统（越用越懂你） |

### 1.3 AIOS 与传统 OS 的关系

```
【手镯设备 · AIOS 本体】                【手机 · 数据器官】       【云端 · 算力器官】
┌──────────────────────────┐     ┌──────────────────┐   ┌──────────────┐
│ Sensor Hub（RTOS 反射世界）│     │  Android / iOS   │   │  大模型 API   │
│       ↕ 事件流 / 租约      │     │  伴侣 App（授权   │←──→│ 最小充分上下文 │
│ 主 SoC · Linux            │←同步──▶  导入/增量同步）   │   │  进 · 出      │
│ ┌──────────────────────┐ │     └──────────────────┘   └──────────────┘
│ │  AIOS（九大内核系统）  │ │
│ └──────────────────────┘ │
└──────────────────────────┘
                 ↓
               用户
```

- AIOS 直接运行在手镯的 Linux 之上——Android/iOS 不是 AIOS 的宿主层；手机是平级协作器官，不是 AIOS 之下的一层
- 手机器官：经伴侣 App 授权，为 AIOS 供数字世界数据（聊天/日程/消费/通知），并承担紧急通信备份
- 云端器官：只收最小充分上下文，只回结构化决策
- AIOS 主要用于智能手镯这样的穿戴设备，比手机的数据获取更广——所有人体数据（心率/血氧/体温/姿态/微振动）只有手镯能采

### 1.4 核心产品哲学与第一天冷启动（AI“活了”）

**传统 AI 产品：** 用户主动找 AI → AI 回答。而且每个模型完全不知道用户发生过什么，只会基于当前的和以往的聊天记录进行回复，更别提主动找用户了。

**AIOS：** 
我们要做到的是，用户第一天戴上读取了用户的以往聊天记录，各种消费记录等，作为初步记忆，建立第一认知，用户没有感觉。
晚上了，AI 突然问用户前几天谁谁谁和你说的事情怎么样了，你心里有没有什么想法决策。
用户肯定会被这突如其来的关心**惊艳**！从这个 AI 主动说出第一句关心的话，**用户就觉得这个 AI 活了！这就是我们产品的魅力！**

```
第一天：冷启动流程

用户戴上手环
    ↓
【授权前置宣示】：
1. 告知：所有数据仅用于构建属于你自己的 AI 认知。
2. 承诺：原始私密数据绝不上云，绝不用于商业化或广告。
3. 控制：每一项授权随时可撤销，数据随时可物理抹除。
    ↓
授权读取：
├── 微信聊天记录
├── 短信
├── 通讯录
├── 消费记录（支付宝/微信支付）
├── 日历
├── 相册（只做描述，不存图）
├── 搜索历史
├── App 使用记录
    ↓
AI 在后台静默处理：
├── 建立初步社交关系图谱
├── 识别重要的人
├── 发现未完成的承诺
├── 识别最近的重要事件
├── 建立消费习惯基线
├── 推断用户的兴趣和关注点
    ↓
不打扰用户。用户感觉什么都没发生。（静默指授权之后的处理过程不打扰，采集前的告知与授权早已完成）
    ↓
晚上，AI 自然地开口：

"你前天答应小王帮他看方案，他昨天又提了一次。
 你要不要今晚抽时间看看？你心里有没有什么想法决策？"
```

## 第二章：四条最高原则（宪法核心）

> 以下四条原则是 AIOS 的根基。
> 所有架构设计、模块开发、功能扩展，都不得违反这四条原则。
> 如果发现某个设计违反了其中任何一条，该设计必须被修改或否决。

### 原则一：AIOS 的生命是一个永不停歇的循环

AIOS 不是"用户问一句，AI 答一句"的工具。
它是一个**持续运行的认知系统**，永远在执行以下循环：

```
感知 → 注意 → 理解上下文 → 理解自己 + 理解世界 → 认知
→ 决策 → 行动（或沉默）→ 观察结果 → 反思 → 进化 → 继续
```

**这个循环永远不停。** 即使用户没有主动和 AI 对话，AI 也在感知、思考、学习。

每转一圈，AI 多理解用户一点。
每转一圈，AI 的判断更准一点。
每转一圈，AI 犯的错更少一点。
每转一圈，用户对 AI 的信任更多一点。

**这个循环就是 AIOS 的飞轮。没有飞轮，一切都是静态功能。**

### 原则二：AIOS 的知识是三棵分离的树

AIOS 内部必须严格维护三棵独立的知识树：

```
三棵树
│
├── 🌳 用户人生树（Memory Tree）
│      记录：客观上发生了什么
│      性质：事实、不可改变
│      例：2026/09/01 和张总谈了合同，报价100万
│
├── 🌳 AI 认知树（Cognitive Tree）
│      记录：AI 认为世界是什么样的
│      性质：推断、可更新、有置信度
│      例：AI 认为张总更在意交付而非价格（置信度 72%）
│
└── 🌳 AI 成长树（Growth Tree）
       记录：AI 从经验中学到了什么
       性质：反思、教训、策略调整
       例：上次判断张总在意价格，结果错了。
           更新：这类客户优先考虑风险而非成本。
```

**三棵树绝对不能混合。**

原因：如果混在一起，AI 自己猜的东西会随着时间变成"事实"，最终导致系统越用越蠢。

- 事实归事实（Memory Tree）
- 想法归想法（Cognitive Tree）
- 经验归经验（Growth Tree）

### 原则三：AIOS 必须知道自己不知道什么

AI 的认知必须有五种明确状态：

| 状态 | 含义 | 例子 | AI 应该怎么做 |
|------|------|------|--------------|
| **KNOWN** | 确定知道 | "张总是我们的客户" | 直接使用 |
| **INFERRED** | 推断出来的 | "他可能对价格不满意" | 使用但标注不确定 |
| **HYPOTHESIS** | 假设 | "他背后可能有竞争对手" | 继续观察验证 |
| **UNKNOWN** | 明确不知道 | "他的真实预算是多少？" | 在合适的时候问用户 |
| **CONFLICT** | 证据矛盾 | "他说不在意价格，但一直砍价" | 寻找更多证据 |

**核心要求：AI 永远不把 INFERRED / HYPOTHESIS 当作 KNOWN 使用。**

当 AI 处于 UNKNOWN 或 CONFLICT 状态时，它不应该自己瞎猜——
它应该在合适的时机，用自然的方式，主动从用户那里获取缺失的信息。

> 现实世界里最危险的错误，不是 AI 不知道，而是 AI 不知道自己不知道。

### 原则四：穿透表层行为，触达人类内心世界（主动陪伴与深度理解）

聊天记录、消费流水、运动步数等客观数据，都只是一个人**表层的行为表现**，无法直接代表用户的真实心智。
- **举例：** 用户平时每餐只花 10 元，今天突然一个人去吃了 100 元的一顿饭。
  - 传统数据/AI 只会标记：`消费异常偏高`。
  - 但表层数据完全无法得知真实原因：是因为大病初愈犒劳自己？是因为受挫后自我抚慰？还是突然看透了人生决定对自己好一点？
- **核心法则：**
  AI 不能只做冷冰冰的外部观察者。AI 必须在日常中以**真诚的陪伴者**身份，时不时主动找用户谈心、交流、关怀，在温暖无压力的互动中获取用户内心最真实的想法、价值观与情感状态。
  **内心世界的数据，才是一个人真正的灵魂数据。**

AIOS 永远在执行的 11 步循环：

```
                    ┌─────────────────────┐
                    │     现实世界         │
                    └──────────┬──────────┘
                               │
                    ┌──────────▼──────────┐

                    │  值得关注吗？        │

                               │
                    ┌──────────▼──────────┐
              ③    │       上下文         │
                    │  现在是什么场景？    │

                 ┌─────────────┼─────────────┐

                    ┌──────────────────────┐
              ⑥    │       认知           │
                    │                      │
                    │  AI 怎么理解这件事？  │
                    │  事实 / 推断 / 假设   │
                    │  置信度多少？         │
                    │  还有什么不知道？     │
                    └──────────┬───────────┘
                               ↓
                    ┌──────────────────────┐
              ⑦    │       决策           │
                    │                      │
                    │  该不该管？           │
                    │  什么时候管？         │

                    └──────────┬───────────┘
                               ↓
                    ┌──────────────────────┐
              ⑧    │       行动           │
                    │                      │
                    │  告诉用户 / 帮用户做  │
                    │  建议 / 提醒 / 执行   │

                    │  判断对了还是错了？   │

                    │  更新对用户的理解     │
                    │  更新对世界的理解     │
                    │  更新自己的行为策略   │

```

### 关键说明

- **步骤 ①~③** 属于"输入侧"——把现实世界变成 AI 能处理的信息
- **步骤 ④~⑤** 属于"理解侧"——结合用户和世界的全部信息
- **步骤 ⑥~⑧** 属于"输出侧"——AI 做判断并采取行动
- **步骤 ⑨~⑪** 属于"学习侧"——AI 从结果中成长
- **步骤 ⑧ 包含"保持沉默"**——这是一个有意识的选择，不是不行动

> 真正聪明的 AI，不只知道什么时候说话，还知道什么时候闭嘴。

### 4.2 各层职责边界

| 层级 | 职责 | 不负责 |
|------|------|--------|
| 领域层 | 提供领域专业知识、结构化 UI、进度追踪 | 不拥有独立 AI，不独立存储记忆 |
| 领域路由器 | 判断当前领域，加载对应知识 | 不做认知判断 |
| 横跨层 | 提供全局上下文、安全保障、注意力筛选 | 不做具体功能 |
| 内核层 | 9 大基础设施，所有功能的底层支撑 | 不关心具体业务逻辑 |
| AI 算力层 | 提供推理能力 | 不拥有身份、记忆或认知 |
| 设备层 | 提供传感器数据和物理交互 | 不做任何智能判断 |

## 第五章：横跨层详细定义

横跨层不属于任何一个内核系统，而是横跨所有系统的全局机制。

### 5.1 MODE 引擎

**职责：** 判断用户当前处于什么生活场景，为所有系统提供上下文。

**为什么 MODE 是横跨层？** 因为同一个事件，在不同 MODE 下含义完全不同。MODE 影响的不是某一个系统，而是所有系统的判断逻辑。

```
基本 MODE 类型：

├── 工作模式    （优先工作相关信息，减少非工作打扰）
├── 社交模式    （关注人际关系，记录社交信息）
├── 驾驶模式    （安全优先，最低打扰）
├── 睡眠模式    （环境控制，健康监测，紧急事件除外不打扰）
├── 运动模式    （身体监测，训练指导）
├── 学习模式    （专注，减少打扰，学习辅助）
├── 休闲模式    （降低紧迫感，陪伴为主）
├── 紧急模式    （安全 > 一切，所有规则改变）
└── 未知模式    （判定条件不足时：保守处理，最低打扰 + 安全优先）

（列表可扩展：新增模式只需注册触发规则，不修改内核）
```

**MODE 的确定方式：**
- **快速通道（本地规则引擎）：** 基于明确的传感器/时间/位置触发极低延迟的硬规则切换（例如：蓝牙连车=驾驶模式，静息心率+卧姿=睡眠模式）。
- **AI 推断（低频修正）：** AI 不参与实时秒级判定，仅在后台低频分析长时行为后提出模式修正建议（需用户确认）。
- 用户手动切换

**MODE 切换规则：**
- 紧急模式可以随时强制进入，不需要用户确认
- 其他模式之间的切换，AI 可以建议，但用户有最终决定权

### 5.2 Safety 内核

**职责：** 在用户的人身安全和重大财产安全受到威胁时，**可以中断任何系统，接管控制。**

**Safety 分为两部分：**

```
Safety
├── Guardian（守护者）——  已经出事
│     车祸 / 跌倒 / 心率异常 / 长时间无响应
│     → 立即响应
│     → 联系紧急联系人
│     → 提供位置信息
│
└── Prevention（预防者）——  快要出事
      健康趋势恶化 / 财务风险 / 关系恶化 / 可疑诈骗
      → 提前发现
      → 评估风险
      → 提醒用户
```

**Safety 的最高优先级原则：**

> **安全 > 隐私 > 舒适 > 其他一切**

当 Safety 内核判定存在紧急安全威胁时：
- 可以无视 MODE（即使是睡眠模式也会唤醒）
- 可以无视介入预算（即使"不打扰"也会打扰）
- 可以突破常规隐私限制，但仅限：向预设紧急联系人共享最小必要信息（位置 + 体征），且事后必须告知用户

### 5.3 Attention 引擎

**职责：** 在海量信息中，筛选出"当前值得 AIOS 关注的事件"。

**为什么需要 Attention？** 现实世界每一秒都在产生大量信息——手机消息、环境声音、身体数据、位置变化。AIOS 不可能全部处理。Attention 引擎在信息到达内核之前，先做一层筛选。

```
所有输入
    ↓
Attention 引擎
    ↓
筛选标准与算力租约发放（Deep Blue 机制）：
├── 安全事件？ → 签发最高优先级租约
├── 与用户相关吗？
├── 与当前 MODE 相关吗？
├── 是否偏离预期？
├── 历史上类似事件是否重要？
    ↓
只有通过 Attention 筛选的事件，才会向内核发放有限时长的“算力租约”，准许其调用认知或大模型资源进入后续处理。无租约的事件仅静默落盘。
其他事件被记录但不触发认知
```

## 第六章：九大内核系统详细定义

### 6.1 ① 感知系统（Perception System）

**职责：** 把现实世界发生的原始信息，变成 AIOS 能理解的标准化"事件"。

**输入：** 传感器原始数据、手机通知、聊天消息、语音、图像等
**输出：** 标准化事件对象

```
感知系统的工作：

麦克风原始音频    →  "有人用英语问路"
加速度计数据      →  "用户摔倒"
手机微信通知      →  "张三发来消息：明天能见面吗？"
心率传感器        →  "心率从 72 升到 110"
GPS 坐标变化      →  "用户到达张总办公室"
用户主动说话      →  "我准备去谈合同"
```

**标准事件格式：**

```
Event {
    id:           唯一标识
    timestamp:    发生时间
    source:       来源（哪个传感器/输入通道）
    type:         事件类型
    content:      具体内容
    entities:     涉及的实体（人/地/物）
    confidence:   感知置信度
    raw_data:     原始数据引用（可选）
}
```

**扩展原则：** 未来增加新的传感器或输入通道（如摄像头、脑机接口），只需要为感知系统增加一个新的"输入适配器"，将新数据源转换为标准事件格式即可。内核其他系统不需要任何修改。

---

### 6.2 ② 实体系统（Entity System）

**职责：** 维护 AIOS 世界里"存在的所有东西"——人、地点、物品、组织，以及它们之间的关系。

```
实体类型：

├── Person（人）
│     名字、身份、与用户的关系、历史互动、性格特征
│     例：张总 — 客户 — 合作3年 — 强势 — 重视交付
│
├── Place（地点）
│     名称、类型、坐标、关联记忆
│     例：星巴克万达店 — 常去 — 和客户谈过3次
│
├── Object（物品）
│     名称、类型、状态
│     例：我的车 — 特斯拉 — 停在公司楼下
│
├── Organization（组织）
│     名称、类型、关联的人
│     例：张总的公司 — 合作方 — 主要联系人张总和李经理
│
└── Relationship（关系）
      实体A ←→ 实体B — 关系类型 — 关系强度 — 历史
      例：我 ←→ 张总 — 客户关系 — 重要 — 7次合作
```

**关键设计：** 实体系统不存储"AI 怎么理解这个实体"。那属于认知系统。实体系统只存客观信息。

---

### 6.3 ③ 状态系统（State System）

**职责：** 维护"此刻的世界是什么样"——当前快照。

```
World State {
    time:          当前时间
    location:      当前位置
    mode:          当前 MODE（由 MODE 引擎提供）
    user_state: {
        activity:     正在做什么
        physical:     身体状态（心率/疲劳/睡眠）
        emotional:    情绪状态（AI 推断，有置信度）
        availability: 是否可被打扰
    }
    environment: {
        people:       周围有谁
        noise:        环境噪音
        situation:    当前情境描述
    }
    active_events:   当前正在发生的事件
    pending_tasks:   待处理的任务
}
```

**状态系统 vs 记忆系统：**
- 状态系统 = "现在是什么样"（实时，不断覆盖更新）
- 记忆系统 = "以前发生过什么"（历史，永久保存）

---

### 6.4 ④ 记忆系统（Memory System）

**职责：** 保存用户的所有人生经历，构建由底至顶的完整记忆结构，支持多维度关联检索与时间钻取。

**这是三棵树中的"用户人生树"的核心基础设施。**

#### 6.4.1 核心思想与三层记忆架构

> **关于用户的记忆树，必须是时间、地点、环境（多维度持续拓展）。时间轴从检测到说话开始，用语音转文字（STT）变成文字记录，包括环境（用照片拍照小模型描述记录删除图片）、事件、社交消息、消费记录、搜索记录、看的书名、电影、干的事儿等（全维度覆盖、密度分级）。逐级压缩：每小时总结、每天总结、每星期总结、每月总结、每季度总结、每半年总结、每年总结、每3年总结作为记忆树。我们既可以一眼看到你去年干了什么、赚了多少、花了多少，也可以深入到某年某月某日几点几分你说过什么话。**

```
┌─────────────────────────────────────────────────────────────┐
│ 第三层：多维主题树（社交关系/能力成长/健康/财务/目标/兴趣/工作/决策等）│
├─────────────────────────────────────────────────────────────┤
│ 第二层：分层压缩摘要（小时 → 天 → 周 → 月 → 季 → 半年 → 年 → 3年）│
├─────────────────────────────────────────────────────────────┤
│ 第一层：原始生命日志（以秒为基础，全方位客观流水记录）          │
└─────────────────────────────────────────────────────────────┘
```

#### 6.4.2 第一层：原始生命日志（秒级时间戳 · 全维度覆盖 · 密度分级）
以秒为时间戳精度的客观事件流水记录：
- **无事件不记录：** 没有检测到声音、动作或数据变化的时段，不产生任何日志条目——时间轴上的沉默自然为空，绝不生成"某某秒无输入"类占位记录。
- **原始音频即转即删：** 语音仅为转写而短暂缓存，转写成文字后立即删除音频本体，任何存储介质不长期保存原始录音。
- **时间轴与对话记录（秒级时间戳）：** 从检测到说话开始，结合 **IMU 辅助说话检测（区分自己开口还是环境声音，属辅助信号，准确率待真机实测）**，用语音转文字（STT）变成文字记录，并打上精确到秒的时间戳。
- **异步人物绑定：** 对方身份初始记录为“未知人”，随后系统通过声纹与上下文在后台进行**异步人物绑定**。该绑定作为推断可随时被纠正，不篡改原始事实日志。
- **环境感知与隐私保护：** 包含时间、地点、环境。环境用照片拍照小模型描述记录后**立即删除图片**，仅保留文字描述。
- **全方位生命行为记录：** 事件、社交消息、消费记录、搜索记录、看的书名、看过的电影、干的事儿等全方位客观数据。
- **生理体征与身心状态：** 心率、运动、姿态、睡眠阶段与日常活动。

#### 6.4.3 第二层：分层周期压缩记忆树（时间钻取）
- **每小时总结**
- **每天总结**
- **每星期总结**
- **每月总结**
- **每季度总结**
- **每半年总结**
- **每年总结**
- **每3年总结**
> 价值：既可以一眼看到你去年干了什么、赚了多少、花了多少，也可以随时深入钻取到某年某月某日几点几分你说过什么话。

#### 6.4.4 第三层：多维主题树（从原始日志中提取、持续更新）

```
主题树（从原始日志中提取、持续更新）
│
├── 🌳 社交关系树
│     每个人 → 什么关系 → 互动频率 → 聊过什么
│     → 答应过什么 → 关系变化趋势 → 重要事件
│
├── 🌳 能力成长树
│     用户会什么 → 什么水平 → 什么时候学的
│     → 进步速度 → 薄弱点 → 长期趋势
│
├── 🌳 健康树
│     睡眠趋势 → 运动趋势 → 心率基线
│     → 体重变化 → 异常记录 → 生病记录
│
├── 🌳 财务树
│     收入趋势 → 支出分类 → 资产变化
│     → 消费习惯 → 大额支出 → 财务目标进度
│
├── 🌳 目标树
│     设过什么目标 → 完成了哪些 → 放弃了哪些
│     → 为什么放弃 → 当前活跃目标 → 长期人生方向
│
├── 🌳 兴趣树
│     喜欢什么 → 投入多少时间 → 热情变化
│     → 相关的人 → 相关消费 → 技能水平
│
├── 🌳 工作/事业树
│     项目 → 客户 → 同事 → 成就
│     → 收入来源 → 职业轨迹 → 行业知识积累
│
├── 🌳 知识树
│     学过什么 → 读过什么 → 知识领域分布
│     → 什么记住了 → 什么忘了 → 知识缺口
│
└── 🌳 决策树
      做过什么重大决策 → 当时为什么这么决定
      → 结果如何 → 后悔了吗 → 学到了什么
```

```
Memory Entry {
    id:           唯一标识
    timestamp:    发生时间（精确到秒）
    level:        RAW_LOG / HOURLY / DAILY / WEEKLY / MONTHLY / QUARTERLY / HALF_YEARLY / YEARLY / 3YEAR
    location:     发生地点
    entities:     涉及的人/物/机构
    domain:       所属领域（工作/学习/社交/健康/生活...）
    type:         记忆类型（事件/对话/决定/承诺/内心表达/消费...）
    content:      具体内容或摘要
    importance:   重要程度权重
    tags:         标签索引
    linked_memories: 关联的其他记忆 ID
}
```

**跨领域访问：** 记忆系统全局打通共享。任何领域的 AI 均可秒级调阅所有维度的记忆树与摘要，实现真正的多维立体认知。

---

### 6.5 ⑤ 认知系统（Cognition System）

**职责：** 管理 AI 对世界的理解——不是原始数据，而是 AI 自己的"想法"。

**这是三棵树中"AI 认知树"的基础设施。**

```
认知对象类型：

├── Belief（信念）
│     AI 目前相信什么
│     {
│         conclusion: "张总更在意交付而非价格"
│         confidence: 0.72
│         evidence: ["他连续三次提到交付周期"]
│         counter_evidence: ["他也提到了价格"]
│         last_verified: "2026-09-08"
│         status: ACTIVE / REVISED / INVALIDATED
│     }
│
├── Hypothesis（假设）
│     AI 怀疑什么但还不确定
│     {
│         hypothesis: "用户最近情绪低落可能与工作压力有关"
│         confidence: 0.45
│         supporting_evidence: [...]
│         tests: ["继续观察一周"]
│     }
│
├── Prediction（预测）
│     AI 认为接下来可能发生什么
│     {
│         prediction: "张总下周可能会再次砍价"
│         confidence: 0.58
│         basis: ["过去类似情况的行为模式"]
│         expiry: "2026-09-15"
│     }
│
└── Unknown（未知）
      AI 明确知道自己不知道什么
      {
          question: "张总背后是否有其他供应商在竞争？"
          importance: HIGH
          strategy: "在下次对话中自然地了解"
      }
```

**认知系统的核心规则：**
1. 每条认知必须有置信度
2. 每条认知必须有证据来源
3. 认知可以被新证据更新或推翻
4. 认知和事实（记忆）严格分离
5. 矛盾的证据必须被标记为 CONFLICT，不能被静默忽略

---

### 6.6 ⑥ 决策系统（Decision System）

**职责：** 判断"该不该管"、"什么时候管"、"怎么管"。

```
决策流程：

触发事件
    ↓
结合认知系统的理解
    ↓
预测：如果不干预会怎样？
    ↓
预测：如果干预会怎样？
    ↓
评估：
├── 重要性（对用户多重要？）
├── 紧迫性（能不能等？）
├── 置信度（AI 多确定？）
├── 打扰成本（现在打扰合适吗？）
├── 用户当前状态（MODE）
├── 历史经验（类似情况以前怎么处理的？）
    ↓
决定：
├── 不干预（保持沉默，继续观察）
├── 延后干预（记录下来，等合适的时机）
├── 建议（告诉用户，但由用户决定）
├── 主动提醒（AI 认为必须告诉用户）
└── 直接执行（用户已授权的自动操作）
```

**决策系统的子模块：**

| 子模块 | 职责 |
|--------|------|
| 预测引擎 | 推测不同选择的可能结果 |
| 反事实推演 | "如果我什么都不做会怎样？" |
| 介入预算 | 控制打扰频率，防止 AI 过度干预 |
| 价值评估 | 综合收益、风险、时间、成本等因素做权衡 |

---

### 6.7 ⑦ 能力系统（Capability System）

**职责：** 管理 AI 能做的所有具体动作。能力以插件形式存在，随时可增加。

```
能力分类：

├── 信息类能力
│     搜索 / 翻译 / 解释 / 总结 / 分析
│
├── 表达类能力
│     写作 / 回复消息 / 生成报告 / 沟通建议
│
├── 执行类能力
│     发送消息 / 设置提醒 / 下单 / 预约
│
├── 设备控制能力
│     控制灯光 / 调整空调 / 播放音乐
│
├── 感知增强能力
│     实时翻译 / 行业术语解释 / 表情分析
│
└── 专业领域能力
      教学 / 训练指导 / 财务分析 / 法律咨询
```

**能力系统的接口标准：**

```
Capability {
    id:           能力标识
    name:         能力名称
    type:         能力类型
    description:  能力描述
    inputs:       需要什么输入
    outputs:      产生什么输出
    permissions:  需要什么权限
    dependencies: 依赖什么其他能力或系统
}
```

**扩展原则：** 新能力只需要实现标准接口，注册到能力系统即可。不需要修改内核。

---

### 6.8 ⑧ 交互系统（Interaction System）

**职责：** 管理 AI 和用户之间的所有通信。

**核心原则：**
- AI 决定"说什么"
- 交互系统决定"怎么提醒"
- 用户决定"怎么接收"

```
完整交互流程：

AI 产生消息
    ↓
消息进入队列
    ↓
根据优先级和 MODE 决定提醒方式
    ↓
振动语义提醒
    ↓
五级介入通道（严格遵循最低打扰原则）：
    ├── 0. SILENT_WATCH: 不介入，仅记录（默认基线）
    ├── 1. VISUAL: 静默视觉提示屏幕
    ├── 2. HAPTIC: 触觉振动语义提醒
    ├── 3. BONE_CONDUCTION: 骨传导私密语音
    └── 4. EXECUTE: AI 强受控自动执行

用户是否接入（响应振动/视觉）？
    ├── 否 → 消息等待，降级回 SILENT_WATCH
    └── 是 → 根据配置和通道选择进入 Interaction Session (看屏幕 / 滑动 / 抬腕贴耳·骨传导)
```

**振动语义标准：**

| 振动模式 | 含义 |
|----------|------|
| 短一下 | 普通信息 |
| 两下 | 有事情需要看 |
| 较长/明显 | 着急 |
| 连续强提醒 | 很急 |
| 特殊高频 | 极其重要 / 安全事件 |

**关键设计：** 用户可以自定义振动语义。长期使用后，用户和 AIOS 会形成独特的"触觉语言"。

---

### 6.9 ⑨ 进化系统（Evolution System）

**职责：** 管理 AI 从经验中学习和成长的机制。

**这是三棵树中"AI 成长树"的基础设施。**

```
进化闭环：

AI 做了一个判断
    ↓
用户反应 / 现实结果
    ↓
判断对了还是错了？用户接纳还是拒绝了介入？
    ↓
【Intervention Regret（介入反馈）】：如果被忽略或拒绝，系统即时降档，即刻提高此类事件下一次触发打扰的阈值。
    ↓
如果错了：为什么？（进入深层策略进化）
    ↓
更新认知（修改 Belief 的置信度）
    ↓
更新行为策略
    ↓
下次类似情况，采用新策略
```

**进化系统记录的对象：**

```
Growth Entry {
    situation:        当时的情况
    ai_judgment:      AI 做了什么判断
    ai_action:        AI 采取了什么行动
    user_feedback:    用户怎么反应
    actual_result:    实际结果是什么
    was_correct:      判断是否正确
    error_analysis:   如果错了，为什么？
    lesson:           学到了什么
    strategy_update:  行为策略如何调整
    confidence:       对这个教训的确信程度
}
```

**进化的安全机制：**

1. **不能基于单次事件永久改变行为** —— 必须有多次验证
2. **行为实验系统** —— AI 可以小范围尝试新策略，观察效果后再决定是否采纳
3. **进化必须可回溯** —— 如果新策略效果更差，可以回退
4. **进化有边界** —— AI 的核心身份和安全规则不受进化影响

---

## 第七章：领域层（应用层）

### 7.1 领域的定义

AIOS 上的"应用"不是传统意义上的 App。
它是 AI 和用户在某个人生领域的**长期专注空间**。

**核心区别：**

| 传统 App | AIOS 领域 |
|----------|-----------|
| 有自己独立的 AI（或没有 AI） | 共享同一个 AI 大脑 |
| 有自己独立的数据 | 共享同一份记忆 |
| 和其他 App 隔离 | 所有领域互通 |
| 装了才有，卸了就没 | AI 的认知不会因为"关闭领域"而消失 |

### 7.2 领域的标准结构

```
Domain（领域）{

    ① 领域身份
       name:         "编程学习"
       type:         "学习类"
       description:  "帮助用户系统性学习编程"

    ② 领域专业知识
       knowledge:    [Python教程, 算法题库, 项目模板, ...]
       strategies:   [教学方法, 评估标准, 难度分级, ...]

    ③ 领域结构
       goals:        大目标 → 阶段 → 任务 → 每日计划
       progress:     完成了什么，卡在哪里
       capability_map: 用户在这个领域的能力分布

    ④ 领域记忆（标签）
       所有记忆存在共享记忆系统中
       通过 domain 标签标记为"属于这个领域"
       但不隔离——AI 随时可以跨领域读取

    ⑤ 领域 UI
       进度面板 / 任务列表 / 学习界面 / 能力图谱

    ⑥ 领域对 AI 的指令
       "在这个领域里，你扮演教师角色"
       "优先教用户薄弱的部分"
       "不要一次给太多内容"
       "每个知识点要通过实践验证"
}
```

### 7.3 跨领域联动机制

领域之间的联动**不需要任何特殊设计**。因为：

1. AI 是同一个 —— 它本身就拥有所有领域的认知
2. 记忆是共享的 —— 任何领域都可以查询任何记忆
3. 状态是统一的 —— 所有领域看到的用户状态是同一个

**示例：**

```
学习领域的 AI 发现：最近学习效率下降
    ↓
AI 查询其他领域的记忆和状态：
    ↓
├── 健身领域：最近训练强度增加
├── 状态系统：最近连续三天睡眠不足
├── 工作领域：本周有两个项目截止
    ↓
AI 综合判断：
    效率下降不是因为学习方法问题
    而是因为身体疲劳 + 工作压力
    ↓
AI 决策：
    "这周先暂停新内容，复习已学的就好。等工作压力过去再继续。"
```

**没有人写过"健身影响学习"的逻辑。AI 自己发现的。**

### 7.4 新领域的添加

添加一个新领域，只需要：

1. 定义领域身份和描述
2. 提供领域专业知识包
3. 定义领域结构（目标/任务/进度模板）
4. 设计领域 UI
5. 编写领域对 AI 的指令

**不需要修改内核的任何部分。**

## 第八章：AI 算力层

### 8.1 核心原则：模型不是 AIOS

```
AIOS 的身份、记忆、认知、经验、判断方式 → 属于 AIOS
模型（GPT/Claude/Gemini/本地模型）       → 只是算力供应商
```

未来模型可以更换、升级、甚至混用。但 AIOS 的人格不会因此改变。

> **产权注释（V1.2 新增）：** "AI 算力层不拥有身份、记忆或认知"指的是产权归属，不是记忆缺失。用户眼中的 AI = AIOS 整体，拥有完整记忆——三棵树就是它的记忆层。每次模型调用：AIOS 组装工作包（身份指令、世界快照、事件链、检索记忆）喂给模型；调用结束，模型输出经系统审核后按类型分流写入三棵树（事实→人生树、推断→认知树、教训→成长树）。记忆写入权归系统三个守护进程（memoryd / cognitiond / evolutiond），模型只有建议权。由此保证四件事：换模型不失忆、模型错误不入账、用户对每条记忆可查可改可删、记忆永远存在用户控制的设备里。

### 8.2 模型路由器

```
Model Router {

    任务类型               推荐模型
    ─────────────         ──────────
    简单状态判断           本地小模型（快速、免费）
    日常对话               中等模型
    复杂推理/深度分析       强推理模型（GPT/Claude）
    视觉理解               视觉模型
    语音处理               语音模型
    专业领域               领域专业模型
}
```

**路由器的决策因素：**
- 任务复杂度
- 响应时间要求
- 成本预算
- 网络状态（无网络时使用本地模型）
- 隐私需求（高隐私数据使用本地模型）

**默认序：** 隐私敏感数据与简单判定默认本地处理；无网络时自动降级为本地能力 + 未解决事件队列，联网恢复后续处理。

## 第九章：设备层

### 9.1 核心理念

所有设备不是不同的产品。它们是同一个 AIOS 的不同"身体器官"。

```
AIOS（同一个大脑）
│
├── 手环/手镯  —— 身体感知器官 + 私密交互器官
├── 手机       —— 数字世界器官（App/消息/支付/GPS）：冷启动与日常增量数据经手机伴侣 App 授权导入，紧急通信备份
├── 耳机       —— 听觉器官 + 语音交互器官
├── 眼镜       —— 视觉增强器官（未来）
├── 汽车       —— 出行器官（未来）
└── 家庭设备   —— 环境控制器官（未来）
```

### 9.2 设备接口标准

每个设备对 AIOS 来说，只是一个"输入/输出通道"：

```
Device Interface {
    inputs:    这个设备能提供什么数据（传感器/位置/...）
    outputs:   这个设备能输出什么（屏幕/振动/声音/...）
    always_on: 是否持续连接
    priority:  数据优先级
}
```

## 第十章：标准接口规范

### 10.1 核心原则

> **系统之间不能直接"伸手进去拿东西"。所有通信通过标准接口。**

这是保证未来可以无限扩展而不推倒重来的根本保障。

### 10.2 标准事件总线

所有系统之间的通信，通过一条统一的"事件总线"传递：

```
                    标准事件总线
    ┌──────────────────────────────────────┐
    │                                      │
    │  所有系统通过这条总线通信              │
    │  不直接互相调用内部逻辑               │
    │                                      │
    ├──┬──┬──┬──┬──┬──┬──┬──┬──┬──────────┤
    │  │  │  │  │  │  │  │  │  │          │
    ①  ②  ③  ④  ⑤  ⑥  ⑦  ⑧  ⑨   ⑩ 未来系统
    感  实  状  记  认  决  能  交  进       │
    知  体  态  忆  知  策  力  互  化       │
                                           │
                               只需接入总线
                               即可与所有系统通信
```

### 10.3 标准数据格式

系统间传递的所有数据，必须使用标准格式：

```
标准事件：    Event    { id, timestamp, source, type, content, entities, confidence }
标准实体：    Entity   { id, type, name, attributes, relationships }
标准记忆：    Memory   { id, timestamp, location, entities, domain, content, importance }
标准认知：    Cognition { id, type, conclusion, confidence, evidence, status }
标准决策：    Decision  { id, trigger, judgment, action, reasoning, confidence }
标准消息：    Message   { id, content, priority, source_domain, requires_response }
```

### 10.4 扩展规则

**增加新的内核系统：**
1. 定义系统职责和边界
2. 定义系统的标准接口（输入/输出）
3. 接入事件总线
4. 不修改任何已有系统的内部逻辑

**增加新的领域：**
1. 实现领域标准结构（见第七章）
2. 注册到领域路由器
3. 不修改内核

**增加新的能力：**
1. 实现能力标准接口
2. 注册到能力系统
3. 不修改内核

**增加新的设备：**
1. 实现设备接口标准
2. 为感知系统增加输入适配器
3. 为交互系统增加输出适配器
4. 不修改内核

## 第十二章：数据主权与隐私

**12.1 核心原则**
AIOS 是用户的绝对数字资产。没有任何企业、模型厂商或第三方可以不经授权获取、窃取、或利用这些数据训练商业模型。

**12.2 隐私守卫管道（Privacy Daemon）**
所有脱离手镯或手机本地计算节点、需要“上云”调用大模型的请求，必须经过系统级的隐私脱敏管道：
1. **身份脱敏**：人名替换为内部代号（如联系人A）。
2. **位置脱敏**：抹除绝对经纬度坐标，替换为逻辑地点（如：常去餐厅）。
3. **录音不落盘**：原始录音在本地转写后必须立刻物理销毁，云端绝不接触原始音频包。
4. **图像即抛**：摄像头捕获的画面，由本地极小模型生成环境文本描述后，原图瞬间物理删除。

**12.3 最小充分上下文**
上云请求只携带解决当前事件所需的最小集合：事件摘要、相关短片段、人物关系标签、MODE、相关历史索引。不默认上传整段历史。云端只回结构化决策，不回原始数据。

**12.4 用户四权**
用户对本人生成的一切数据拥有完整权利：**查看**（随时调阅任何记忆与认知条目及其置信度）、**删除**（单条/分类/整体删除，含云端备份）、**导出**（机器可读格式完整导出）、**遗留继承**（生前指定继承人的数字遗产授权访问机制）。

**12.5 授权状态机**
每类数据源（麦克风转写 / 手机聊天同步 / 消费记录 / 日程 / 位置 / 生理 / 摄像头）独立授权，状态为：未授权 / 已授权 / 已暂停 / 已撤销，随时可切换。未授权数据在感知入口直接丢弃，不留内容只留丢弃计数。5.2 的紧急豁免是唯一例外，且必须事后告知。

## 附录 C：神经系统实现规范（Deep Blue 机制）

本附录是对 AIOS 运行时调度与功耗控制的约束（全称 Deep Blue 神经系统架构）：

1. **双世界划分**
   - 反射世界（Sensor Hub / RTOS）：极低功耗，永不休眠，负责信号采集、L0 动作识别与 L1 事件升级申请。
   - 认知世界（主 SoC / AIOS 内核）：接收租约后苏醒，干完活即刻休眠。
2. **算力租约发放**
   - 任何事件必须向 Attention 引擎（或系统监管进程）申请计算"租约"（如：30秒推理时间额度）。无租约，不计算。租约耗尽强制挂起。
3. **非对称阈值（三套错误成本模型）**
   - **SAFETY（生命/安全）**：漏报代价远高于误报——阈值极低，宁可多次误报也要唤醒，允许多阶段确认。
   - **SOCIAL（社交/提词）**：误报会打断谈话、造成尴尬——阈值极高，高置信度才触发，优先静默视觉。
   - **FINANCIAL（金融/支付）**：误操作造成真实财产损失——极高置信度 + 明确二次确认，高风险支付不得仅凭推断自动执行。
