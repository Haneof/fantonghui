# 一、R2 修改目的

R2 不改变 AIOS 的最高目标，不重新设计产品路线。本次修订只解决进入正式编码前必须固定的八个核心问题：

1. 明确“新基础数据”与“唤醒 AI”不是同一件事，避免高频数据造成无限唤醒。
2. 把“主张（Claim）”从简单的内容+置信度升级为能够区分事实、观点、愿望、计划、预测、推断等语义性质的正式结构。
3. 将“证据集合（EvidenceSet）”提升为一等对象，使单点、区间、多维组合证据可以稳定保存、复核和重算。
4. 将“派生维度（DimensionDerivation）”提升为一等结构，正式支持多个维度组合形成更高层认知维度。
5. 明确动态维度从候选到试用、活跃、休眠的完整登记机制，保留 AI 自主提出维度的权力，同时避免维度无界爆炸。
6. 将“目标（Goal）”提升为一等对象，使长期目标与任务、App、帮助决策、维度变化能够持续关联。
7. 为事件锚点增加认知生命周期，允许“候选事件→修正→合并→否定”等演化，而不是覆盖旧结论。
8. 第一轮允许后移完整十年级多尺度总结，但不得后移“多尺度总结机制”本身；必须先实现原始→日→周→月的最小闭环。

R2 的目的不是增加复杂度，而是保证第一版数据库、接口和运行机制不会在进入 M2/M3 后因为基础对象缺失而整体返工。

---

# 二、最高原则保持不变

以下原则继续有效，R2 不作修改：

- AIOS 的核心是**基于唯一时间轴的、可挂载多维世界认知系统**。
- 用户世界与 AI 世界共用唯一时间轴、对象和版本机制。
- 维度不等于曲线；不同维度允许使用数值、状态、事件、实体、关系、文本、认知等不同数据形态。
- 底层采集与机械规则不负责最终语义判断；事件、关系、意义、情绪、压力、原因等由大模型结合世界资料形成。
- AI 可以宏观看多年，也可以下钻到某一秒、某一句原话；观察尺度由 AI 根据任务自主决定。
- 所有高层认知必须能够向下追溯到其支持、反对和缺失证据。
- AI 生成的认知不是神谕，允许存在不确定、冲突、错误和后续修正。
- AIOS 的最终目的不是“形成更多认知”，而是越来越有效、适时地帮助用户，并允许选择沉默。
- 任务、定时、待办、跟进、观察、验证等未来工作必须进入可恢复的任务系统，不能只留在模型上下文中。
- App 是同一个 AI 和同一个用户世界进入专业领域的场所，不拥有独立长期人格或孤立用户记忆。

# 三、R2-01：基础观测不直接等于 AI 唤醒

## 3.1 修改原则

原规格中“普通唤醒允许来自新进入的基础观测”容易产生歧义。R2 明确：

> **基础观测（Observation）默认只写入世界，不直接唤醒 AI。**

高频来源可能包括心率、IMU、GPS、汽车、家庭设备、App行为等。如果每条 Observation 都产生 Wake，会让 AI 长时间处于无意义连续唤醒状态。

正确主链统一为：

```text
现实/虚拟世界产生新资料
        ↓
接入与清洗
        ↓
写入 Observation / 基础维度
        ↓
机械触发条件检查
        ↓
满足唤醒条件？ ── 否 ──→ 继续积累资料
        │
        是
        ↓
形成 Wake
        ↓
调度 AI 会话
```

## 3.2 允许直接形成 Wake 的来源

以下来源允许绕过普通变化检测直接形成 Wake：

1. 用户主动交互。
2. 已登记定时任务、截止任务、周期任务或任务恢复点到期。
3. 已登记观察/验证条件命中。
4. 人身安全高优先信号。
5. 系统恢复后发现必须处理的到期工作。

## 3.3 基础观测可以通过哪些机械机制间接唤醒

- 数值幅度变化。
- 斜率或趋势变化。
- 状态切换。
- 持续时间超过条件。
- 关键词/实体的确定性匹配。
- 数据源长时间无更新。
- 数据覆盖异常。
- 已登记 Watch 条件中的机械部分命中。
- 与任务依赖相关的新资料到达。

这些机制只负责判断“是否值得叫醒 AI 看一眼”，不得直接写入诸如“用户失恋”“用户孤独”“这是运动会”等语义结论。

## 3.4 新增去重规则

同一来源、同一主体、同一连续情境中的连续命中默认合并为同一个 Wake，保留：

- 首次命中时间；
- 最近命中时间；
- 命中次数；
- 新增证据引用；
- 峰值/最新值；
- 是否发生强度升级；
- 是否出现独立新来源。

出现显著新证据、安全等级升级或冷却结束后重新满足条件时，可以形成新的 Wake。

## 3.5 修改 Core C09

C09“触发与调度”的明确责任修改为：

> 接收基础世界更新、任务到期、观察命中、用户交互和安全信号，通过确定性规则形成、合并、延迟、抢占和恢复 Wake；**不把每条 Observation 自动转换为 Wake，不负责最终语义判断。**

# 四、R2-02：Claim（主张）语义模型升级

## 4.1 目的

AIOS 必须区分：

> “某个人说过一句话”

和

> “这句话描述的现实是真的”

也必须区分：

- 事实陈述；
- 主观看法；
- 愿望；
- 计划；
- 预测；
- 承诺；
- 推断；
- 假设。

否则长期世界会把“用户说过”“用户相信”“用户希望”“AI猜测”错误升级为现实事实。

## 4.2 Claim 必需字段

第一版 Claim 至少包含：

```text
claim_id
subject_id              # 主张关于谁/什么
claimant_id              # 谁提出/表达该主张：用户、AI、他人、外部来源
claim_type                # 主张性质
content                   # 标准化主张内容
valid_time / time_range   # 主张指向的现实时间
asserted_at               # 该主张被提出的时间
knowledge_state           # OBSERVED / REPORTED / INFERRED / HYPOTHESIS / UNKNOWN / CONFLICT
confidence                # 针对本主张本身的置信度
support_evidence_set_ids
counter_evidence_set_ids
unknown_items
source_refs
revision
status
```

## 4.3 claim_type 第一版枚举

至少支持：

- `FACT`：对现实事实的主张。
- `OPINION`：观点、评价、态度。
- `BELIEF`：某主体相信什么。
- `DESIRE`：愿望、希望。
- `INTENTION`：意图。
- `PLAN`：计划。
- `PREDICTION`：对未来的预测。
- `PROMISE`：承诺。
- `PREFERENCE`：偏好。
- `INFERENCE`：AI或其他主体的解释性推断。
- `HYPOTHESIS`：待验证假设。

允许后续扩展，但禁止把所有内容降级成一个自由文本标签。

## 4.4 示例

用户说：

> “我明天一定考上某学校。”

系统至少允许生成三项不同主张：

```text
Claim A
内容：用户今天说过“我明天一定考上某学校”
类型：FACT（关于话语发生事实）
知识状态：OBSERVED/REPORTED
置信度：高

Claim B
内容：用户相信自己明天能够考上该学校
类型：BELIEF
知识状态：INFERRED 或 REPORTED
置信度：根据上下文判断

Claim C
内容：用户明天会被该学校录取
类型：PREDICTION / FACT（未来现实尚未发生）
知识状态：UNKNOWN 或 HYPOTHESIS
置信度：不能因为用户表达强烈就自动升高
```

## 4.5 置信度规则

- 置信度属于**具体主张**，不是属于整段话。
- 同一来源可以支持多个不同主张，但每个主张的置信度独立维护。
- 用户原话对“用户说过什么”通常是强证据，但对原话涉及的未来事件、因果解释、他人内心状态并不自动构成强证据。
- 高层总结不得把低置信度主张转换成高置信度事实，除非出现新的独立依据。

# 五、R2-03：EvidenceSet（证据集合）升级为一等对象

## 5.1 定义

> **EvidenceSet 是对“一个认知、事件、关系或派生维度为什么成立/为什么被怀疑”的可复核证据集合。**

它不是简单的 `source_refs[]` 列表。

一个 EvidenceSet 可以引用：

- 单个 Observation；
- 多个节点；
- 某维度一段时间窗口；
- 某个统计区间；
- 某个事件；
- 某个 Claim；
- 某个 Summary；
- 某个关系或实体身份版本。

## 5.2 核心字段

```text
evidence_set_id
purpose                  # 该证据集合用于支持什么问题/主张
time_range
knowledge_cutoff
member_refs               # 明确成员或可重建选择器
support_refs
counter_refs
context_refs
selection_method          # 为什么选择这些证据
aggregation_method        # 如有统计/聚合，记录算法及版本
coverage                  # 覆盖率
missingness               # 缺失情况
source_quality
created_at
created_by
revision
status                    # CURRENT / STALE / PARTIAL / INVALID
```

## 5.3 区间证据

例如：

> “过去两周睡眠持续下降。”

不能只保存一个“查询过去两周睡眠”的动态查询。

必须保存：

- 当时的时间窗口；
- 当时的信息截止时间；
- 成员版本或可重建成员集合；
- 统计方法；
- 覆盖率；
- 缺失时段；
- 支持结论的原始节点。

迟到数据、身份修正、索引重建或底层 Observation 版本变化后，EvidenceSet 可进入 `STALE` 并触发依赖复核。

## 5.4 支持与反对证据必须分开

禁止只保存“支持我当前结论的东西”。

例如：

```text
候选事件：学校运动会

支持：
- GPS 在学校操场
- 心率和IMU出现持续跑动
- 环境文本“加油”

反对/削弱：
- 学校日程无正式运动会
- 用户此前提到今天有体育测试

缺失：
- 没有比赛名称
- 没有老师或同学明确提到“运动会”
```

这允许 AI 保持候选事件，而不是被迫二选一。

## 5.5 Core 对象表新增

在 C02/C05 共同数据契约中正式新增：

> `EvidenceSet`

Claim、EventAnchor、Relation、Summary、DimensionDerivation、GoalProgress 均可引用 EvidenceSet。

# 六、R2-04：DimensionDerivation（派生维度关系）升级为一等结构

## 6.1 目的

AIOS 必须正式支持：

```text
数学能力
英语能力
编程能力
   ↓
学习能力
   ↓
更高层综合能力
```

因此“多个维度组合成更高层维度”不能只依赖自然语言描述，必须有稳定结构记录其来源、适用范围和更新机制。

## 6.2 DimensionDerivation 核心字段

```text
derivation_id
output_dimension_id
input_dimension_ids
input_event_refs
input_claim_refs
input_summary_refs
evidence_set_ids
scope                    # 对哪个主体、场景、时期有效
time_window_rule
aggregation_or_reasoning_rule
created_by
created_at
confidence
limitations
counterexamples
update_policy
revision
status
```

## 6.3 派生维度不是永久真理

例如 AI 从数学、英语、编程形成“学习能力”。

后续发现该时期用户一直在照顾生病家人，原有表现下降可能反映的是可投入精力变化，而不是学习能力本身下降。

AI可以：

- 修正派生规则；
- 降低置信度；
- 限定适用时间；
- 拆分维度；
- 废弃旧派生维度；
- 建立新的“可投入学习精力”维度解释原变化。

## 6.4 派生关系必须可下钻

从高层维度必须能够：

```text
高层维度
↓
派生规则
↓
输入维度/事件/主张/总结
↓
EvidenceSet
↓
原始Observation/原话
```

## 6.5 工作台新增操作

新增或明确以下 AI 操作：

- `dimension.derivation.inspect`
- `dimension.derivation.create`
- `dimension.derivation.revise`
- `dimension.derivation.trace`

开发者界面中显示“这个维度是如何长出来的”。

# 七、R2-05：动态维度登记机制重新固定

## 7.1 基本原则

保留 R1 的核心精神：

> AI 有权自主提出维度，不能要求另一个 AI 先替它决定“这个想法有没有价值”。

同时保留最初设计中的治理原则：

> 长期维护的维度必须能够说明意义、来源、更新方式、预期帮助价值、重复性和成本。

两者统一为：

> **候选产生自由，长期激活需要验证。**

## 7.2 维度生命周期固定为

```text
CANDIDATE（候选）
   ↓
TRIAL（登记试用）
   ↓
ACTIVE（正式活跃）
   ↓
LOW_ACTIVITY（低活跃）
   ↓
DORMANT（休眠）

任意阶段可：
MERGED / SPLIT / REVISED / REJECTED / REACTIVATED
```

## 7.3 CANDIDATE 创建

AI 可以直接创建 Candidate，不需要语义审批。

候选必须记录：

- 定义；
- 主体；
- 为什么现有维度不足；
- 来源；
- 预计更新方式；
- 预计参与哪些认知/任务；
- 可能给用户带来的帮助价值；
- 与已有维度的可能重叠；
- 维护成本；
- 失效条件。

## 7.4 TRIAL 激活

进入试用只做工程性检查：

- 结构合法；
- 引用有效；
- 更新机制可执行；
- 不与现有稳定 ID 冲突；
- 资源预算允许；
- 不形成禁止的递归依赖；
- 不重复提交完全相同候选。

允许使用“维度登记评分”辅助资源调度，但该评分不能宣称维度语义真伪。

初始评分可以考虑：

- 独立性；
- 可更新性；
- 可复核性；
- 预期帮助价值；
- 维护成本；
- 与现有维度重复程度。

阈值属于可测试参数，不能写死成宪法常量。

## 7.5 TRIAL → ACTIVE

需要至少满足：

- 在真实/虚拟后续任务中被实际使用；
- 对调查、检索、判断、帮助或成本至少一项产生可测正收益；
- 未造成明显错误传播或无意义维护负担；
- 定义与更新机制在试用期内保持可解释。

如果没有独立收益，可继续试用、合并、降级或拒绝。

## 7.6 低频不等于无价值

维度不得仅因近期没有被调用就删除。

如果其关联：

- 长期承诺；
- 未完成任务；
- 重要身份；
- 稀有但高价值事件；
- 周期性场景；

则可以低频维护或休眠，但必须保留历史和引用。

# 八、R2-06：Goal（目标）升级为一等对象

## 8.1 为什么任务不能代替目标

“学会英语”“一年内减脂”“准备创业”“改善与妈妈的关系”都可能持续数月或数年。

它们会产生大量 Task，但不等于任何一个具体 Task。

因此 Goal 必须独立存在。

## 8.2 Goal 核心字段

```text
goal_id
owner_subject_id          # 用户 / AI / App / 共同目标
goal_type
content
source_type               # 用户明确提出 / AI推断 / App场景目标
source_refs
created_at
start_at
target_time
priority
status                    # PROPOSED / ACTIVE / PAUSED / ACHIEVED / ABANDONED / UNKNOWN
success_criteria
progress_refs
related_dimension_ids
related_event_refs
related_task_ids
related_app_ids
confidence                # 若目标来自推断，记录置信度
revision
```

## 8.3 目标来源必须区分

- 用户明确目标：例如“我今年要考过英语四级”。
- AI推断目标：例如根据行为推测用户正在准备考试。
- App目标：例如教育 App 当前课程目标。
- AI自身目标：例如“完成一次用户承诺的后续跟进”。

AI 推断的目标不能伪装成用户明确目标。

## 8.4 Goal 与 Task 关系

```text
Goal：达到英语日常交流能力
│
├─ Task：完成本周口语训练
├─ Task：周日复测
├─ Task：两周后检查遗忘
└─ Task：根据疲劳状态调整今天课程
```

Task 完成不自动代表 Goal 完成；Goal 完成必须由 success_criteria 或充分证据确认。

## 8.5 Goal 参与帮助决策

认知工作台的主动帮助记录必须能够关联：

- 这次帮助服务于哪个 Goal；
- 是否与当前状态或更高优先目标冲突；
- 如果没有任何 Goal 关联，是否仍有合理的安全、关心或即时价值。

# 九、R2-07：EventAnchor 增加认知生命周期

## 9.1 事件是 AI 对现实的解释锚点

EventAnchor 不是基础事实，也不是一旦创建就永远成立。

同一组底层资料可能经历：

```text
“可能是体育活动”
↓
“可能是学校运动会”
↓
“用户明确说今天参加学校运动会”
↓
后续又发现其实是校内田径测试
```

系统必须保留这一演化，而不是覆盖旧文本。

## 9.2 Event 状态

第一版至少支持：

- `CANDIDATE`：候选事件，证据尚不足。
- `ACTIVE`：当前认为事件成立或正在发生。
- `RESOLVED`：事件已结束，认知仍成立。
- `REVISED`：事件解释被修正，保留前版本。
- `REJECTED`：后续证据表明该事件解释不成立。
- `MERGED`：后续发现多个事件锚点属于同一事件。
- `SPLIT`：后续发现原事件其实包含多个独立事件。

## 9.3 EventAnchor 必需增加

```text
status
confidence
primary_claim_ids
support_evidence_set_ids
counter_evidence_set_ids
supersedes_event_id / merged_into_event_id / split_from_event_id
revision_reason
```

## 9.4 事件修正影响传播

当 Event 被 REVISED / REJECTED / MERGED / SPLIT 时：

- 依赖它的 Summary 标记待复核；
- 依赖它的 GoalProgress 标记待复核；
- 依赖它的 Task 检查是否需要暂停、修改、取消；
- 依赖它的派生维度重新检查；
- AI 世界记录本次误判和修正原因；
- 已执行行动不能通过数据库覆盖“假装没发生”，只能追加结果与补救记录。

# 十、R2-08：第一轮必须实现最小多尺度总结

## 10.1 修改 R1“完整多尺度总结可后移”的解释

允许后移的是：

- 半年；
- 年；
- 3年；
- 5年；
- 10年；
- 大规模跨多年重算优化。

**不得后移的是“同一维度存在多个时间尺度观察层”的机制本身。**

## 10.2 第一轮最低要求

在 M2/M3 结束前至少实现：

```text
原始节点
  ↓
日总结
  ↓
周总结
  ↓
月总结
```

至少选择以下三类维度做真实实现：

1. 事件维度；
2. 一个连续数值或行为频率维度；
3. 一个认知/学习类维度。

## 10.3 总结要求

每条 Summary 必须记录：

- subject；
- dimension；
- time_range；
- granularity；
- source world revision；
- evidence_set_ids；
- coverage；
- missingness；
- claims；
- 生成时间；
- 当前状态：`CURRENT / STALE / PARTIAL / MISSING`。

## 10.4 总结是新观察层，不是删除原始数据

必须支持：

```text
月总结
↓
周总结
↓
日总结
↓
事件/节点
↓
EvidenceSet
↓
原始Observation / 用户原话
```

也允许直接从月总结跳到某个重要事件或原始证据，不强制逐级展开。

## 10.5 总结失效

如果底层事件、身份或 Claim 被修正：

- 相关 Summary 标记 `STALE`；
- 生成后台维护任务；
- AI可决定何时重审；
- 在未重算前，工作台必须显示“该总结基于旧世界版本”。

# 十六、R2专项验收

以下验收在原 A01-A10、W01-W12、R1-01~R1-11 基础上新增。

## R2-01：高频基础数据不会逐条唤醒

给虚拟用户持续注入 1 小时高频心率和 IMU 数据；正常范围内不得产生每条数据一个 Wake。发生显著机械变化后，应形成合并后的有效 Wake。

## R2-02：用户说过 ≠ 现实事实

用户说“我明天一定考上某学校”。系统必须能够分别表示：

- 用户说过；
- 用户相信/预测；
- 实际结果未知。

不得因为原话语气强烈把未来结果记成高置信事实。

## R2-03：证据集合可复核

一个“运动会候选事件”必须能显示支持、反对、缺失、时间范围、覆盖率和原始成员；新增迟到数据后 EvidenceSet 可以进入 stale 并复核。

## R2-04：区间证据不漂移

“过去两周睡眠下降”的证据集合在未来再过一周后仍能重建当时那两周，而不是自动变成新的“过去两周”。

## R2-05：派生维度可追溯

“学习能力”必须能追到数学、英语、编程等输入维度以及各自 EvidenceSet；输入发生重大修正后，上层派生维度进入复核。

## R2-06：候选维度不等于正式活跃

AI可以自由创建 Candidate；未通过结构/预算检查不能进入 Trial；Trial 无后续收益时不得自动永久 Active。

## R2-07：低频高价值维度不会误清理

与一年后生日任务或长期承诺相关的维度即使数月低活跃，也只能降低维护频率或休眠，不得破坏引用或丢失历史。

## R2-08：Goal 与 Task 分离

一个长期英语目标关联多个任务。完成一次练习任务后 Goal 仍保持 Active，除非成功条件真正满足。

## R2-09：推断目标与用户明确目标分离

AI推测“用户可能想减肥”必须标明为推断 Goal，不能显示为用户亲口确认目标。

## R2-10：Event 生命周期可回放

同一事件从 CANDIDATE → ACTIVE → REVISED / REJECTED 的全过程可回放，旧版本不消失。

## R2-11：事件修正会影响下游

运动会事件被修正为体育测试后，依赖它的总结、提醒、派生维度和相关任务必须被发现并进入复核；不相关对象不得被误改。

## R2-12：最小多尺度总结闭环

至少一个月虚拟生活中能够完成：

```text
原始 → 日 → 周 → 月
```

并从月总结准确下钻到某一天的具体事件和原始证据。

## R2-13：总结不会覆盖原始历史

月总结修正或重算不得删除旧 Summary 版本及底层 Observation。

## R2-14：AI可以跳过总结层直接下钻

如果当前任务明确需要某天原话，AI允许直接通过实体/事件/关键词进入原始证据，不强制逐层读月、周、日总结。

## R2-15：认知修正不会自激无限循环

Claim/Event修正后可以创建有限复核任务，但同一修改不得无限递归产生 Wake/Task。

# 十八、开发任务拆分前的冻结条件

# 二十二、R2 最终裁决

R2 不改变项目路线，而是把已经讨论清楚但尚未完全写入数据结构的内容正式化。

确认 R2 后，AIOS Core 的第一阶段正式定义为：

> **一个运行在唯一时间轴上的多维世界内核。它接收持续基础观测但不会被每条数据直接唤醒；AI通过触发和任务进入认知工作台，自主选择时间尺度、维度、搜索和下钻路径；使用带语义性质的主张、可复核证据集合、事件生命周期、长期目标和派生维度来维护用户世界与AI世界；所有高层认知可以向下追溯，错误可以沿依赖链被修正；系统至少具备日、周、月的多尺度总结能力，并能够把未来工作转换为可恢复任务。**

第一轮实验要回答的仍然不是“系统是不是看起来很复杂”，而是：

> **在用户没有预先指出问题的情况下，这套机制是否真的让AI比强记忆基线更容易发现值得帮助的事情、更合理地调查和保持不确定、更少错误传播、更好地完成未来任务，并最终给用户带来更高的净帮助价值。**

只有实验支持的机制，才继续进入下一阶段扩展。

确认 R2 后，开发基线顺序为：

```text
《AIOS宪法2.0》
        ↓
《修改案 R1》
        ↓
《修改案 R2》
        ↓
《AIOS Core 系统架构图与开发规划》
《AIOS认知工作台功能规格》
《AIOS虚拟世界测试规范》
        ↓
M0～M3 开发Issue
        ↓
代码 / 自动测试 / 回放记录
        ↓
虚拟世界实验结果
        ↓
根据证据决定是否进入下一次修宪
```

**R2确认后，除非测试或工程事实证明基础契约存在问题，不再因为新的概念偏好随意改动核心世界模型。**
