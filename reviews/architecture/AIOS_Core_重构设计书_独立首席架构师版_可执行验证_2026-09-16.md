# 零、一句话主张

> **V3 落地的失败风险不在"缺功能"，而在旧图纸把 AIOS 设计成一条数据管道，而 V3 宪法要求它是一个受延迟与预算双重约束的闭环控制系统。**
>
> 所以本设计书的重心不是"再补 30 个 Issue"，而是补三样旧图纸里根本不存在的东西：
> **①一个控制面（Control Plane，新模块 C15）**——把预算、deadline、水位、epoch、看板快照与回执变成**运行时可读、可结算、可回放的状态**；
> **②一份读路径契约（Read-Path Contract，新模块 C16）**——规定"以什么视图、什么索引水位、什么时间口径读"，而不是只规定"写哪张表"；
> **③一套可被 CI 判定的不变量 I1~I7**——把"不得退化为机械 Chatbot"从形容词变成断言。
>
> 这三样东西的必要性不是论证出来的，是**测出来的**：本设计书自带探针在 1M 规模上证明，同一条宪法要求，旧做法与设计做法之间存在 **32.6× ~ 167,884×** 的差距，而其中两种旧做法（裸 FTS5 中文检索、遍历式任务求值）**在失败时不报错**。

# 一、独立诊断与重构主张（Core Architectural Diagnosis）

## 1.1 最致命的断层：三个"没有"

我不认为最致命的断层是"缺模块"或"缺 Issue"。旧任务书 4262 行、82 个 Issue，覆盖面其实相当扎实——它把 R2 时代的世界内核做得很好。致命的是**三个结构性缺席**，而它们都有一个共同特征：**缺席的东西不会报错，只会让系统静默地不符合宪法。**

### 断层一：没有控制面（Control Plane）

V3 的每条新机制都隐含一个"系统对自己的观察与结算"：第八十四条要求**一次性看板**（⇒ 必须有预算与 deadline 才能决定装什么）、第八十六条要求**条件就绪才挂载**（⇒ 必须有就绪状态与订阅索引）、第八十五条要求**首字 1 秒**（⇒ 必须有分段延迟遥测）、第七十六条要求**资源与维护预算**（⇒ 必须有账本）。而代码与图纸里：

| 证据 | 事实 | 后果 |
|---|---|---|
| `schemas/r2/m0_contract_snapshot.json` | `ErrorCode` 11 项**含 `BUDGET_EXHAUSTED`** | 错误码有出口，**机制无入口**：全仓没有任何对象/表/服务产生它 |
| `src/aios_core/contracts/models.py:332-339` | `Task.completion_condition / cancel_condition / recurrence` 是**无类型 `dict[str, Any]`** | 条件无法被求值、无法被索引、无法被验收 ⇒ 第八十六条的"条件驱动"在契约层就没有载体 |
| `models.py:31` | `Observation.modality: str`（**无枚举约束**） | 端侧多模态策略（第三十三条）无法按模态分派，也无法验收 |
| 旧任务书全文 | `ContextSnapshot` / `ContextReceipt` / `BudgetLedger` / `DeadlineClock` / `index_watermark` **0 次出现** | 第八十六条第 4 款"全操作过程支持高保真回放"与"7 向错误归因"**没有任何交付物** |

**这不是补一个服务能解决的**：控制面是横切的，它必须与存储、调度、模型接入同时冻结契约，否则后补时必然侵入已冻结语义（第一百一十五条第 3 款的正式架构变更）。

### 断层二：没有读路径契约（Read-Path Contract）

旧图纸与旧任务书从头到尾只回答"写什么表"，从不回答"**用什么视图、什么索引、什么时间口径读**"。而 V3 的三个招牌机制（5D 滑动条、多关键词共现、图谱穿透）**全部是读路径机制**。后果是实测可见的：

| 读法 | 同一查询的实测代价（1M 对象） | 出处 |
|---|---|---|
| `occurred_at` 时间窗，**as-built 冻结 schema**（该字段在 payload 内、无索引） | **1,201.4 ~ 1,468.6 ms**，且与窗口宽度无关 | as-built 探针 P4 |
| `learned_at` 时间窗（顶层索引列，**旧探针用的口径**） | **369 ms@100万**（B，未取证）／**4.824 ms**（本设计 schema，有索引） | 本报告探针 v3 |
| 同一窗口读**物化月桶** | **0.013 ms** | 本报告探针 v3 |
| 1 年档读**年桶** vs 日桶求和 | **0.007 ms** vs **0.661 ms**（744 个日桶），差 **94.4×** | 本报告探针 v3 |

宪法第八十七条的滑动条按语义必须切 **`occurred_at`（事情发生时间）**，不是 `learned_at`（系统得知时间）。**口径写错，同一个"最近一个月"窗口从 **4.824 ms**（`learned_at` 有索引）变成 **152.984 ms**（`occurred_at` 全扫），差 **31.7 倍**，而验收会绿灯通过**——因为两种口径都能"返回结果"。这就是"没有读路径契约"的真实代价：不是慢，是**慢得无法归因、错得无法发现**。

### 断层三：没有调度代数（Deadline Algebra）

第八十四条的四步序（照镜子 → 校准羁绊 → 确立姿态 → 审视世界）与第八十五条的 1 秒首字，在旧图纸里被写成两段互不相干的散文。实测把真相摆出来：

| 环节 | 实测 | 结论 |
|---|---|---|
| 看板**组装本身**（含就绪任务 top-8、12 条证据切片、6 个月桶、羁绊模型、能力清单） | **p95 = 0.098 ms**（本报告探针 v4）／**0.3 ms**（as-built 探针 P2b，85 行 payload） | **存储与组装根本不是瓶颈**，60 ms 预算有 **612× 余量** |
| 遍历 50 万任务求值就绪（旧做法 = M2-005/M2-006 的实现形状） | **p95 = 2014.61 ms** | 单这一步吃掉 1 s 预算的 **201%** |
| 读物化 READY 队列 top-8（设计做法） | **p95 = 0.012 ms** | 与遍历相差 **167,884×** |
| 逐条提交 fsync（`synchronous=FULL`） | **0.19 ms/次**（本探针）／**0.47 ms/次**（as-built）⇒ 1,090 行/日 = **0.21 ~ 0.51 s/日**纯 fsync | 摄入必须 group commit，否则真实闪存上是秒级 |

⇒ **四步序绝不能被实现成"四个步骤"**。它必须是**单次 Prompt 内的四个 segment**（段序），并与检索/prefill **重叠**；否则要么 4 次模型往返（每次 300~800 ms），要么 1 段长 prose 前导（按 40 token/s 解码，300 token 前导 = 7.5 s），两种都直接破产 1 s 首字。旧图纸对此**零约束**，这就是调度代数的缺席。

## 1.2 如果不予修改直接开工，系统首先崩溃在哪里

**不是某个里程碑 Gate，而是第一个用户可感知场景的第 1 秒。** 我把它精确到 `TS-001`（运动会修正 → 中文三词共搜 → 1 秒内出声）：

```text
Wake ──①就绪计算──②检索──③时间窗──④修正传播──⑤出声
      2014.61ms   280.7ms   153.0ms    1096.4ms    0.21s/日 fsync
      （遍历50万） （LIKE全表）（occurred_at）（全量入内存）（逐条提交）
      ─────────────────── 合计 > 3.5 s，预算 1 s ───────────────────
```

而**真正的危险不是慢，是崩溃形式**：

1. **②会静默零召回**。裸 FTS5 `unicode61` 对连续中文串整段成一个 token：本探针实测 `MATCH "妈妈的生日礼物"` 在 1M 行上返回 **0 命中，耗时 0.038 ms，不报错**；2 字词 `"生日"` 同样 **0 命中**（而 LIKE 真值是 **134,916** 行）。⇒ 旧任务书 M1-012 的验收"搜索'妈妈'返回实体候选+文本命中"会**以 0 命中绿灯通过**，因为它的断言只检查"没有异常"。
2. **①③④会静默超时**。它们都返回正确结果，只是慢；旧验收没有任何延迟断言 ⇒ 全部绿灯。
3. **四步序会被静默跳过**。当延迟吃紧，最"合理"的工程妥协就是砍掉前导段——而砍掉四步序不会让任何测试失败，因为**没有测试断言四步序发生过**。

> **判词（本节结论）**：按旧图纸开工，系统不会抛异常。它会在 `TS-001` 上"礼貌地慢 3.5 秒、召回为空、四步序被跳过、修正不传播"，而 M4 验收会**全部绿灯**。
> **"退化为机械 Chatbot"的工程定义就是：所有门都绿，但宪法的十条机制一条都没有真正发生。**
> 所以本设计书的第一优先级不是加功能，而是**把每条机制改写成一个可判定的断言**（§1.3 的 I1~I7 + §3.7 的 14 条门断言（G1~G12，其中 G2b 拆为两条）），并且让断言在 CI 里跑，而不是在文档里写。

## 1.3 总体重构战略：三平面 + 五铁律 + 七不变量

### (A) 三平面架构（本设计书的骨架）

```text
┌────────────────────────── CONTROL PLANE（C15，新设；在环中心，不是旁路）──────────────────────────┐
│  BudgetLedger(reserve/settle) · DeadlineClock(tier) · WatermarkRegistry(index/extraction/world)   │
│  EpochRegistry(notification/propagation) · ContextPlan → CockpitManifest → ContextReceipt(hash)   │
│  DegradationLadder(超支/超时/离线/索引陈旧的四级降级)                                            │
└───────────────▲──────────────────────────────────────────────────────────────┬──────────────────┘
                │ reserve / settle / watermark / epoch                          │ plan / receipt
┌───────────────┴──────────── COGNITION PLANE ──────────────────────────────────▼──────────────────┐
│ C01 接入清洗(SourceEnvelope/trust lane) → C02 存储(append-only/双时态) → C03 维度+派生物登记       │
│ → C04 可逆实体消解 → C05 总结/章节 → C06 查询编排 → C07 有界传播 → C08 任务+条件AST               │
│ → C09 触发+关系节奏 → C16 检索读路径(预分词/postings/时间桶/ZERO_RECALL 守卫) → C12 经验          │
└───────────────▲──────────────────────────────────────────────────────────────┬──────────────────┘
                │ typed channel + epoch                                         │ DTO(设备无关)
┌───────────────┴──────────── PROJECTION PLANE（C17，新设）─────────────────────▼──────────────────┐
│ InteractionPort{haptic, display, private_audio, speaker, button, gesture} · 穿戴 FSM(零误触)       │
│ 三层 UI 契约(体态/态势画布/挂载技能) · SimulatedInteractionPort(Linux) · PC 认知调试控制台         │
└──────────────────────────────────────────────────────────────────────────────────────────────────┘
                        C13 模型接入(分段遥测 TTFU/TTFT/TTFAudio/FinalUseful) 贯穿三平面
```

**为什么控制面必须在环中心**：因为 V3 的十条机制里有七条的验收口径是"**系统在约束下做了什么选择**"（装了什么、没装什么、为什么省略、花了多少、什么时候降级），而不是"系统算出了什么"。没有控制面状态，这些验收**在原理上不可判定**。

### (C) 七条不变量 I1~I7（全部机器可判定；I3/I4/I5 已证明可在 DDL 层强制）

| # | 不变量 | 判定方式 | 实测状态 |
|---|---|---|---|
| **I1** | **单源律**：任何派生物可由真源重建，且 `rebuild_diff = 0` | 重建 postings/桶后逐行 diff | 探针建库路径即重建路径（`insert_and_index` 可重跑） |
| **I2** | **读契约律**：任何读结果必须携带 `index_watermark` 与 `hit_reasons`；无水位的读 = 违规 | 返回结构体断言（缺字段即 fail） | `cp_index_watermark` 表已建；`state=SUSPECT_ZERO_RECALL` 可表达 |
| **I3** | **预算律**：任何模型调用前必须 `reserve`，调用后必须 `settle`；`reserved_tok < 0` 不可能存在；超支必须走降级阶梯，不得静默继续 | **DDL CHECK 约束**（`CHECK (reserved_tok >= 0)`） | ✅ 探针自证：违规写入被 `IntegrityError` 拒绝（`ENFORCED_BY_DDL`） |
| **I4** | **就绪律**：看板只挂 `READY` 任务；`WAITING`/`UNKNOWN` 出现在 manifest = 违规 | **DDL CHECK 约束**（`cp_context_receipt.waiting_task_count = 0`） | ✅ 探针自证：插入 `waiting_task_count=3` 被拒绝 |
| **I5** | **段序律**：四步序在**单次 prompt 内**以 4 个 segment 呈现，`system_filler_turns = 0`（禁止"好的我知道了"类占位轮次） | **DDL CHECK 约束** + receipt 的 `segment_order` 字段 | ✅ 探针自证：插入 `system_filler_turns=2` 被拒绝 |
| **I6** | **零误触律**：无有效 `notification_epoch` 的先导震动 ⇒ 私密音频通道不得开启 | FSM 仿真断言（穿戴 profile） | 契约见 §3.3 `RC-031`；Linux 侧由 `SimulatedInteractionPort` 打桩验证 |
| **I7** | **不静默零召回律**：任何检索路径若召回 0，必须区分"真无数据"与"分词/索引失效"，并置 `index_watermark.state = SUSPECT_ZERO_RECALL` | 双路径交叉核对（postings vs LIKE 真值 vs 预分词 FTS5） | ✅ 探针实测：裸 FTS5 = **0 命中/0.038 ms/不报错**；预分词后 = **134,916 命中**（与 LIKE 真值一致） |

> **I7 的来历值得单独记一笔**：本探针第一版自己就犯了两个静默错误——批量写入时只插入尾部 6 万条 postings（导致三词交集恒为 0）、幂等断言写反（把"重试补齐工作"误判为"重复"）。**两个错误都被自己的 G9/G11 门抓住**。这正是 I7 存在的理由：在中文检索这条链上，**0 是最容易伪装成成功的数字**。

## 1.4 如何兼顾 Linux 虚拟测试与未来穿戴端随身心智

一句话战略：**把"设备"降级为执行器与传感器，把"心智"上移为契约。** 三条具体做法：

1. **`InteractionPort` 六通道抽象 + epoch**：`haptic / display / private_audio / speaker / button / gesture`，每个通道带 `epoch`（通知纪元）与 `fault_injection` 钩子。Linux 侧 `SimulatedInteractionPort` 打桩并可注入"震动发出但用户未应答""骨传导通道故障""按键抖动"；手环侧 `WearableInteractionPort` 只换 adapter。**认知层只认 channel 与 epoch，不认设备**（I6 由此可在 Linux 上先证）。
2. **端侧 reducer 的契约在 Linux 上先行**：相机→caption/OCR、音频→ASR+数秒声纹指纹、IMU→宏观运动状态+显著波形、心率→平稳期均值点+异常独立写入（第三十三条第 1~3 款）。虚拟世界用**合成的 reducer 输出**驱动，但接口与真实端侧**完全一致**，且必须同报 `reduction_report`（压缩比、异常召回率、丢弃字节数）。⇒ 未来换真实端侧模型时，**只有 adapter 变，契约与验收不变**。
3. **双 profile，同一套门**：`profile=linux-virtual`（容器 FS、无无线约束、Mock 模型）与 `profile=wearable-target`（真实闪存 fsync、TTFU、震动/骨传导时序、离线降级）。**同一套 `ACC-*` 断言，两套默认值**；禁止把任一 profile 的数字写进宪法（第七十六条：阈值属于可测试参数）。本设计书全部实测数字均标注 `profile=linux-virtual`。

# 三、《AIOS_Core_详细开发任务拆分》增补与重构蓝图（核心重头戏）

## 3.1 里程碑结构调整：M0~M8 保留，但**三处接缝必须加门**

宪法第一百零九条的 M0~M8 是宪法级路线，**本设计书不改动它**。脱节发生在**接缝**上，因此增设 2 个子阶段门 + 6 个 Gate 检查点 + 2 条横切脊柱（§2.4）。三处最易脱节的接缝与对策：

| # | 接缝 | 脱节机制（为什么会断） | 对策（新增检查点） | 判定工件 |
|---|---|---|---|---|
| 1 | **M0 → M1** | M0 冻结的是**写侧**契约（对象、字段、版本、幂等）。M1 拿到"能写"的契约就会照着写实现，而 V3 的三大招牌机制全是**读侧**（滑动条、共现、穿透）。结果：M1 交付"能存能查"，但查一次 1.2 s、中文召回 0，而 M1 的验收里没有一条延迟/召回断言 | **G0.5 = M0.5 读路径契约门**：`ReadContract`、视图语义、`index_watermark`、**时间口径（`occurred_at` vs `learned_at`）必须显式声明**、tokenizer 与词典版本、`ZeroRecallGuard` | `RC-009`；探针 v3 的口径对照（153.0 ms vs 4.824 ms vs 0.007 ms） |
| 2 | **M2 → M3** | M2 交付"看板 + 工具循环"，但若 **manifest 与 receipt 不落库**，M3 的传播/总结与 M4 的 7 向归因就**无据可依**——出问题时无法区分是数据、触发、组装、搜索、推理、传播还是任务遗漏 | **G2.5 = M2.5 认知事务门**：一次 Wake = 一个**可回放事务**（reserve → plan → manifest → receipt(hash) → settle），任一环缺失即不放行 M3 | `RC-001~RC-003`；`cp_context_receipt` 表 + `manifest_hash` |
| 3 | **M3 → M4** | M4 的验收引用了**不存在的测试资产**：旧任务书 L3377 写 `V01~V30覆盖`，而【测试规范】§10 只定义到 **V20**；V21~V30 只存在于宪法 L1604-1619，从未下传 | **G4 = 盲测门 + 场景包重签**：`TS-001~TS-051` 一次性把宪法 V21~V30 / R3-01~07 / V3-01~03 全部映射为可执行场景，**每条带 oracle**；悬空引用清零 | `RC-032~RC-036`；registry 的 `traces_to` 字段 |

**横切脊柱（不属任何单一里程碑，贯穿全程）**：

- **SPINE-EVIDENCE**：`NUMCI-001`（编号 registry + CI 门，**先于一切派单**）+ `PROBE-CI-002`（5 支探针入 CI：A 的 3.6M、B 的三支、本设计书一支）+ "每个 Issue 先交 oracle 再交实现"。
- **SPINE-CONTROL**：控制面三段式落地——M0 冻契约（8 个控制面对象）→ M2 上运行时（reserve/settle/receipt）→ M7 做年度对账（成本-质量前沿）。

## 3.2 编号纪律：`RC-*` + `slug`（本设计书**主动放弃号位主权**）

仓库现状：**66 个 `M*-***` 号被 5 套方案重复分配**（39 个存在 ≥2 套语义、21 个单方声明待裁决），`NUMCI-001` CI 门实跑为 **RED**。若本设计书再宣布一套 `M` 号，就是第 6 套语义。因此：

1. 本设计书全部新增任务使用**临时命名空间 `RC-001~RC-041`**（ReConstruction），每条带 **`slug`（语义键）**；
2. 每条给出 `maps_to` 列，标明它在 α(D+统一母表)/β(E)/γ(F+P3)/δ(P1)/ε(P2) 五套方案里对应哪个号 ⇒ **治理方裁决时可以直接按 slug 归并，不需要再读六份文档**；
3. 裁决后由 registry 重签正式 M 号；**在此之前派单以 `slug` 匹配，`RC-*` 仅作显示**；
4. 本设计书已把 41 个 `RC-*` **标签**提交给 `governance/issue_registry/v3_issue_registry.json`（`registry_version 0.3.0-PROPOSAL`）。**提交后 CI 门立刻打回了其中 11 条**——它们与 α/P1 既有提案号**同 slug**（`A3 一号一 slug`）。这正是我要求别人遵守的纪律，所以本设计书按 `R3_alloc` 处理，而不是绕过：
   - **同语义 ⇒ 不发新号**：这 11 个 `RC-*` 降级为既有号的 **alias**（写入 owner 的 `aliases` / `source_docs` / `spec_ref`），registry 中只保留 **30 条新语义键条目**（`namespace: RC`，`status: PROPOSAL`）；
   - **门位判断不同 ⇒ 登记争议而不是私改**：`RC-017`（我主张 `Gate1`）与 `RC-028`（我主张 `Gate2`）分别写入 `M2-024` / `M2-026` 的 `gate_disputes{status: OPEN}`，附实测依据，等治理方裁决；
   - 为让这类错误**下次仍会被抓住**，我给 `NUMCI-001` 增补了四条规则：`A6`（alias 完整性）、`A7`（alias 必须在 scope_docs 中真实出现，反虚构标签）、`D1~D6`（临时命名空间完整性 + 文档定义位必须已登记）、`E1~E2`（gate 争议字段与状态合法性）。
5. **净结论（可复核）**：41 个标签 = **11 个收敛 alias + 30 个新语义键 + 2 处 gate 争议**。规则 A/B/D 全 0，规则 C 仍为 39 CONFLICT + 21 UNRATIFIED（不属本设计书权限），规则 E = 2 ⇒ **门保持 RED**。这是正确状态：门红是因为**号位尚未裁决**，不是因为没人发现问题。

### 3.5-A `RC-006` + `RC-017`：TriggerExpression 契约 + 三值求值 + 物化 READY 队列

**A-1 数据契约（Pydantic 2）**

```python
from __future__ import annotations
from datetime import datetime
from enum import StrEnum
from typing import Annotated, Literal, Union
from pydantic import BaseModel, Field, model_validator

class ConditionKind(StrEnum):
    TIME_REACHED = "TIME_REACHED"                    # 第八十六条 2.1
    EVENT_MATCHED = "EVENT_MATCHED"                  # 2.2
    CONTEXT_MATCHED = "CONTEXT_MATCHED"              # 2.3（情境：GPS/心率低谷/独处静默）
    OBSERVATION_PREDICATE = "OBSERVATION_PREDICATE"  # 2.4
    DEPENDENCY_READY = "DEPENDENCY_READY"            # 2.5
    ALL_OF = "ALL_OF"; ANY_OF = "ANY_OF"; NOT = "NOT"

class ThreeValue(StrEnum):
    TRUE = "TRUE"; FALSE = "FALSE"; UNKNOWN = "UNKNOWN"   # UNKNOWN 既不唤醒也不丢弃

class TimeReached(BaseModel):
    kind: Literal[ConditionKind.TIME_REACHED]
    at: datetime                                     # 绝对时间
    tz_policy: Literal["UTC_STORE_LOCAL_RENDER"] = "UTC_STORE_LOCAL_RENDER"
    dst_rule: Literal["SKIP_NONEXISTENT_REPEAT_AMBIGUOUS"] = "SKIP_NONEXISTENT_REPEAT_AMBIGUOUS"

class EventMatched(BaseModel):
    kind: Literal[ConditionKind.EVENT_MATCHED]
    subscription_key: str = Field(min_length=3, max_length=128)   # 无键 = 不可订阅 = 违规
    event_type: str
    match_json: dict[str, object] = Field(default_factory=dict)

class ObservationPredicate(BaseModel):
    kind: Literal[ConditionKind.OBSERVATION_PREDICATE]
    subscription_key: str
    dim_id: str
    op: Literal[">", ">=", "<", "<=", "==", "!=", "IN", "CHANGED_BY"]
    threshold: float | str | None = None
    window: str | None = None                        # ISO-8601 duration，如 "PT2H"
    hysteresis: tuple[float, float] | None = None    # (进入阈值, 退出阈值)，防抖

class DependencyReady(BaseModel):
    kind: Literal[ConditionKind.DEPENDENCY_READY]
    upstream_refs: list[str] = Field(min_length=1)   # Task/Claim/CleaningJob 的稳定 ID
    require: Literal["ALL", "ANY"] = "ALL"

class Composite(BaseModel):
    kind: Literal[ConditionKind.ALL_OF, ConditionKind.ANY_OF, ConditionKind.NOT]
    children: list["TriggerExpression"] = Field(min_length=1)

Leaf = Annotated[Union[TimeReached, EventMatched, ObservationPredicate, DependencyReady],
                 Field(discriminator="kind")]

class TriggerExpression(BaseModel):
    """任务激活条件：typed AST，可求值、可索引、可版本化、可回放。
    取代 models.py:332-339 的无类型 dict[str, Any]。"""
    expr_id: str
    task_id: str
    version: int = Field(ge=1)
    root: Union[Leaf, Composite] = Field(discriminator="kind")
    expiry_at: datetime | None = None
    manual_override: bool = False                    # 用户显式"现在就做" ⇒ 绕过就绪门但必须留痕
    subscription_keys: list[str] = Field(default_factory=list)   # 由 root 递归收集，供索引

    @model_validator(mode="after")
    def _keys_must_be_declared(self) -> "TriggerExpression":
        collected = _collect_keys(self.root)
        if set(collected) != set(self.subscription_keys):
            raise ValueError("subscription_keys 必须由 AST 递归收集得出，禁止手写不一致")
        return self
```

**A-3 求值与调度算法（伪代码）**

```text
# ---- 热路径：Wake 时只做 O(manifest) 的读，绝不做 O(tasks) 的求值 ----
on_wake(wake_id, now):
    ready = SELECT task_id, priority FROM task_queue
            WHERE state='READY' ORDER BY priority DESC LIMIT manifest_top_n   # 实测 p95 = 0.012 ms
    assert no WAITING/UNKNOWN task in ready                                   # I4（DDL 已强制 receipt 侧）
    return ready

# ---- 维护路径：事件到达 / 时间推进时**增量**更新 READY（摊还成本，不在 1 s 预算内）----
on_event(event):
    for expr in SELECT * FROM trigger_expression WHERE subscription_key = event.key:   # 走 ix_expr_subkey
        v = evaluate(expr.root, world_state)                # 三值
        if v == TRUE:  promote(expr.task_id, fire_key(expr, event))
        elif v == UNKNOWN: keep_waiting(expr.task_id); record_uncertainty(expr)   # 不当 FALSE 丢弃
        else: pass                                          # FALSE：继续休眠，零 token 成本

on_time_advance(bucket):                                    # 每分钟一跳，不逐任务轮询
    for task in SELECT task_id FROM task_queue
                WHERE state='WAITING' AND next_fire_at <= bucket.end:              # 走偏索引
        promote(task, fire_key(task))

promote(task_id, fire_key):
    INSERT OR IGNORE INTO task_occurrence(occurrence_id, task_id, fire_key, lease_until, created_at)
    if rows_affected == 0: return          # 已存在 ⇒ 重复触发被幂等键吸收（重启/迟到/DST 安全）
    UPDATE task_queue SET state='READY' WHERE task_id=? AND state='WAITING'

evaluate(node, ws) -> ThreeValue:                           # 三值 Kleene 逻辑
    match node.kind:
      TIME_REACHED          => TRUE if node.at <= ws.now else FALSE
      EVENT_MATCHED         => TRUE if ws.fired[node.subscription_key] else UNKNOWN   # 未观测 ≠ 未发生
      CONTEXT_MATCHED       => TRUE/FALSE/UNKNOWN by sensor freshness; 数据过期 ⇒ UNKNOWN
      OBSERVATION_PREDICATE => 若窗口内无数据 ⇒ UNKNOWN；有数据 ⇒ 比较 + hysteresis 判定
      DEPENDENCY_READY      => ALL/ANY over children；任一 UNKNOWN ⇒ 整体 UNKNOWN
      NOT                   => TRUE if child==FALSE; FALSE if child==TRUE; else UNKNOWN
      ALL_OF                => FALSE if any FALSE; UNKNOWN elif any UNKNOWN; else TRUE
      ANY_OF                => TRUE  if any TRUE;  UNKNOWN elif any UNKNOWN; else FALSE
```

**A-5 绝对禁止事项**

1. **禁止**在任何热路径遍历 `trigger_expression` 或 `task_queue` 全表求值（实测 2014.61 ms）。
2. **禁止**把 `UNKNOWN` 当 `FALSE` 丢弃（会静默吞掉"传感器数据过期"这类真问题），也**禁止**当 `TRUE` 唤醒（Token 空转）。
3. **禁止**非 `TIME_REACHED` 条件占用 `next_fire_at`（口径污染 ⇒ 两条求值路径结果不一致，AC-A2 会失败）。
4. **禁止**把条件存成无类型 `dict[str, Any]`（现状 `models.py:332-339`）；契约必须是 typed AST 且可版本化。
5. **禁止**用"定期盘点"替代条件求值（【工作台规格】§7.2 L227 的入口必须废黜）。
6. **禁止**在 `manual_override` 时不留痕（用户显式"现在就做"必须写入 receipt，否则 7 向归因失真）。

```text
tokenize(text, cap = PAR.max_postings_per_object = 8):
    out = []
    for w in dict_terms:                       # ① 词典词优先（含实体、别名）
        if w in text: out.append(canonical(w)) #    canonical(母亲) = 妈妈
    for bg in char_bigrams(text):              # ② 受限字符二元组兜底（未登录词召回）

        out.append(bg)
    return dedup(out)[:cap]
```

```text
co_search(terms, anchor=None, span=None, top_k=200, budget_ms=50):

    t0 = deadline_clock.remaining_ms()
    if budget_ms < t0: budget_ms = t0                       # 受 C15 deadline 约束，不自行其是
    hits = plan.execute(terms, anchor, span, top_k, budget_ms)
    if len(hits) == 0:
        # I7 不静默零召回律：必须区分"真无数据"与"索引/分词失效"

    return ReadResult(items=hits[:top_k],
                      index_watermark=cp_index_watermark.get('term_postings'),   # I2
                      hit_reasons=per_item_reasons,                               # I2
                      plan=plan.name, elapsed_ms=now()-t0)
```

```text
compile_manifest(wake_id, tier, now):
    # ① 预算先行（I3）：没有 reserve 就不允许调用模型
    reserve = budget.reserve(scope=SESSION, category=CONVERSATION,
                             amount=TIER_TOKEN_CEILING[tier])
    if reserve.denied:
        return degrade(wake_id, tier)                     # 降档，不静默继续
    dl = deadline_clock.open(wake_id, tier,
             manifest_budget_ms = PAR.manifest_budget_ms,        # 默认 60 ms
             first_token_due_ms = PAR.ttft_budget_ms)            # 默认 1000 ms

    # ② 就绪任务：读物化队列 top-N（0.012 ms），绝不遍历求值（2014.61 ms）
    ready = ready_queue.top_n(PAR.manifest_top_n)                # 默认 8

    # ③ 检索与规划：按 §3.5-B 的 QueryPlan 选择路径，受 dl 约束
    plan = context_plan(wake_reason, ready, budget_ms=dl.remaining_ms())
    slices = c16.co_search(plan.terms, anchor=plan.anchor, top_k=plan.top_k,
                           budget_ms=min(plan.retrieval_budget_ms, dl.remaining_ms()))

    # ④ 组装四个 segment（0.098 ms）；预算不足时**按段序从后往前削**并记录 omitted
    segs = [s1_self_mirror(), s2_rapport(), s3_stance(), s4_world(wake_reason, slices, ready)]
    total = sum(s.token_estimate for s in segs)
    while total > TIER_TOKEN_CEILING[tier]:
        victim = pick_least_critical(segs)               # 先削 S4 的低分切片，绝不削 S1/S2/S3
        victim.omitted.append(victim.pop_lowest_scored())
        total = recompute(segs)
    manifest = CockpitManifest(wake_id, tier, segments=segs, ready_tasks=ready,
                               capabilities=capability_registry.project(tier),
                               watermarks=c16.watermarks(), token_total=total,
                               integrity_hash=sha256(canonical_json(segs)))

    # ⑤ 与 prefill **重叠**发起模型调用（不是等组装完再开始）
    c13.call_async(manifest, prefill_start=now, on_first_token=dl.mark_ttft)

    # ⑥ 回执落库（可回放、可 7 向归因）
    receipt = ContextReceipt(receipt_id=..., wake_id=wake_id,
                             manifest_hash=manifest.integrity_hash, segment_order="1>2>3>4",
                             token_count=total, assembled_ms=elapsed, system_filler_turns=0,
                             ready_task_count=len(ready), waiting_task_count=0)
    db.insert(receipt)                                   # DDL CHECK 会拒绝任何违规值
    budget.settle(reserve.id, actual=c13.usage())        # 超支 ⇒ 下一轮降级阶梯生效
    return manifest

degrade(wake_id, tier):                                  # 四级降级阶梯
    ladder = [降档(TIER-1), 缩短窗口(ActiveWindow×0.5), 延迟非关键萃取, 只出安全提示]
    for step in ladder:
        if budget.try_reserve(step): return step.apply()
    return emit_minimal_safety_notice()                  # 最后一级：不调模型也要给用户交代
```

```text
propagate(root_object, epoch, budget = PAR.propagation_budget):    # 默认 500 节点 / 深度 2 / 50 ms
    frontier = [(root_object, 0)]; visited = {root_object}; truncated = False
    while frontier and len(visited) < budget.max_nodes and elapsed() < budget.max_ms:
        nxt = []
        for node, depth in frontier:
            if depth >= budget.max_depth: truncated = True; continue
            for dst in SELECT dst_id FROM dep_edge
                       WHERE src_id = node AND policy IN ('EAGER_ONE_HOP','LAZY_BUDGETED'):
                # RELATES_TO / policy=NONE **不传播**（普通关联不是派生依赖）
                if dst not in visited:
                    visited.add(dst); nxt.append((dst, depth+1))
        frontier = nxt
    INSERT INTO invalidation_frontier(object_id, epoch, depth, reason) FOR visited
    if truncated:
        task.create(slug='propagation-continuation', remainder=frontier, epoch=epoch)  # 续办任务
    return visited, truncated
```

```sql
    finalized   INTEGER NOT NULL DEFAULT 0,          -- 未 finalize 的 turn **不得**被萃取
    token_count INTEGER NOT NULL,
    created_at  TEXT NOT NULL,
    UNIQUE (conv_id, seq)
);
CREATE INDEX ix_turn_conv ON conv_turn(conv_id, finalized, seq);

CREATE TABLE extraction_watermark (
    conv_id            TEXT PRIMARY KEY,
    last_finalized_seq INTEGER NOT NULL,
    last_extracted_seq INTEGER NOT NULL,
    lag_tokens         INTEGER NOT NULL DEFAULT 0,   -- 前台保留未萃取原文的判据
    updated_at         TEXT NOT NULL
);
CREATE TABLE extraction_job (
    job_id   TEXT PRIMARY KEY, conv_id TEXT NOT NULL,
    span_lo  INTEGER NOT NULL, span_hi INTEGER NOT NULL,
    state    TEXT NOT NULL CHECK (state IN ('PENDING','RUNNING','DONE','DEAD')),
    idem_key TEXT NOT NULL UNIQUE,                   -- conv_id:lo-hi:extractor_version
    attempts INTEGER NOT NULL DEFAULT 0
);
CREATE TABLE extracted_claim (
    claim_id TEXT PRIMARY KEY, job_id TEXT NOT NULL, conv_id TEXT NOT NULL,
    seq INTEGER NOT NULL, text_cjk TEXT NOT NULL,
    UNIQUE (conv_id, seq, text_cjk)                  -- 第二道幂等闸
);
```

**E-2 状态机与算法（伪代码）**

```text
# 前台：活跃滑动窗口（默认 1500 token / 5~8 轮，PAR 可调）
active_window(conv_id, budget = PAR.active_window_tokens):
    turns = SELECT seq, token_count FROM conv_turn
            WHERE conv_id=? AND finalized=1 ORDER BY seq DESC
    acc, win = 0, []
    for t in turns:
        if acc + t.token_count > budget: break
        win.append(t); acc += t.token_count
    # 水位滞后超阈值时，**前台保留未萃取原文**（宁可变长，不可丢事实）
    if watermark.lag_tokens > PAR.lag_token_alarm: win.extend(unextracted_finalized_turns())
    return win

# 后台：增量萃取（话题跃迁或每 N 轮触发；静默产出 Claim/EventAnchor）
on_turn_finalized(conv_id, seq):
    advance(last_finalized_seq)
    if topic_shift(conv_id) or (seq - last_extracted_seq) >= PAR.extract_every_n_turns:
        lo, hi = last_extracted_seq + 1, last_finalized_seq
        idem = f"{conv_id}:{lo}-{hi}:{PAR.extractor_version}"
        try: job = INSERT extraction_job(..., state='RUNNING', idem_key=idem)
        except UNIQUE violation: job = existing_job(idem)      # 重放被吸收，不重复萃取
        claims = extractor.run(span=(lo, hi))                  # 只读 finalized span
        for c in claims: INSERT OR IGNORE extracted_claim(...)  # 第二道幂等闸
        if crash_before_commit: ROLLBACK; retry_later(same idem)   # 重试补齐，不重复
        UPDATE extraction_job SET state='DONE' WHERE idem_key=idem
        UPSERT extraction_watermark(last_extracted_seq=hi, lag_tokens=recompute())
    if job.attempts > PAR.max_attempts: state='DEAD'; dead_letter(job)   # 背压与死信

# 按需回捞：用户突然提起旧事 ⇒ 用**指针**调入当时原话切片（不重萃取、不通读全史）
recall(conv_id, hint_entities, span):
    return c16.co_search(hint_entities, span=span, top_k=PAR.recall_top_k)   # RecallLink 指针
```

**E-4 绝对禁止事项**

1. **禁止**萃取未 finalize 的 turn（半句会被当成事实沉淀）。
2. **禁止**无 `idem_key` 的萃取任务（crash/retry 必然产生重复 Claim）。
3. **禁止**"全量重萃取"替代增量（成本随会话长度线性爆炸，且会覆盖已修正的 Claim）。
4. **禁止**回捞时重新通读用户全部历史（第九十条：凭指针按需加载）。
5. **禁止**无认知增量时写入"本次无新反思"占位内容（第八十六条第 4 款）。
6. **禁止**让后台萃取阻塞前台首字（必须异步 + 背压 + 死信）。

但这也说明 4.68% 离 5% 闸门只剩 287 字符余量，任何一次扩写都会踩线。）

**自测框架也要能断言"不该报什么"**（S14 存在的理由）：只做正向断言的话，"把全部审计工件一律判失效"这种粗暴实现同样能通过自测。
所以框架新增 `expect_absent`：一个场景可以同时要求「该报的报了」与「不该报的没报」。
这条能力是被真实缺陷逼出来的——CG-1 最初把所有审计工件都拿去和**同一支**探针比哈希（见 §3.7.6）。

**两条反后门设计**（S9/S10 存在的理由）：任何"例外机制"都会被用来绕过门，所以例外本身必须带闸——
①字面量允许清单（`quoted_label_allowlist`）写在 `gate_baseline.json` 里，而 baseline **进 SHA256SUMS**，
扩容必然在 diff 中可见，且每条必须附理由；②哨兵区（`HISTORICAL-RUN-VALUES`）总长超过全文 **5%** 即 fail，
防止有人把大半篇文档包进"历史值区"来让回潮检测失明。

**自测的临时树必须"派生复制"，不能手抄文件清单**（本轮两次假失败换来的）：S0 对照先后因为
①清单里新增的 as-built 审计工件没被复制（CG-1 报"清单条目指向不存在的文件"）、
②派工单声明的交付源码没被复制（CG-6 在树里把**存在的**交付物也判成缺失，缺口 2 变 4，棘轮被虚假突破）而失败。
修法不是补手抄清单，而是让 `build_tree()` **从两份 `SHA256SUMS` + 派工单注册表 + 审计工件的 `subject_under_test` 派生**复制集合——
证据增加时自动跟随。教训的一般形式：**任何"手抄的副本清单"都会随系统长大而漏项，而漏项表现为"对照场景假失败"，最容易被误判成门坏了。**

**清单策略（写下来，因为它踩过坑）**：`SHA256SUMS` 只覆盖**输入**（脚本、工件、设计书、registry、baseline、workflow）。带时间戳的**运行记录**（`gate_run_*`、自测日志、自测结果 JSON）一律不进清单——否则会出现"刷新清单 → 本次运行又写了新日志 → 清单又不符"的**无穷回归**（我在实现时真的撞上了这个自指回路，S0 对照因此假失败两次）。运行记录的完整性由 git 与 `PROVENANCE.json` 保证。

**为什么治理债不进 hard fail**：`CONFLICT 39 / UNRATIFIED 21` 只能由治理方裁决消除，把它设成 hard fail 会让 CI **永久红**，而永久红的门等于没有门（人们会加 `|| true`）。所以它被**计数 + 棘轮**：任何一次让争用面变大的提交都会失败，而裁决每消解一号，baseline 就下调一次。这是"红得有意义"与"红到被忽略"的分界线。


### 3.7.5 as-built 对账：设计书的驳回结论在**别人写的代码**上被独立证实

§3.7.1~3.7.4 的证据都来自**我自己写的探针测我自己设计的方案**——这有一个天然弱点：
探针作者与方案作者是同一人， fixture 可能无意中偏袒采纳方案。所以我做了第四类证据：
**拿别人已经合进主干的实现，用它自己的类、它自己的表、它自己的分词器，在 1M 档重测一遍。**

被测对象：`src/aios_core/query/cjk_inverted_index.py`（525 行，2号派工单交付，`subject_sha256=09b4a1e6…ffe467`）。
探针：`reviews/architecture/evidence/verify_landed_m1_017_cjk.py`（**v1.1.0**，直接 `import` 被测类，不重写不替身）。
工件：`verify_landed_m1_017_cjk_{10k,100k,1m}_result.json` + `.log`（三份同一 `script_sha256=a3388fa1…`；CG-1 逐份校验探针哈希**与被测源码哈希**）。裁定见
`reviews/architecture/AIOS_Core_as_built_审查报告_第一批派工交付_2026-09-16.md`（新增 gap 号 `V3G-001~008`，已入 registry 0.3.3-PROPOSAL）。

| 查询路径（宪法 §89 原文用例 `[妈妈,生日,礼物]`，1M 实体、枢纽词覆盖 33%） | 100k p95 | **1M p95** | vs 50 ms 门 |
|---|---|---|---|
| `co_search()` 无界求交（as-built） | 38.147 ms | **382.074 ms** | **7.64×** ❌ |
| `co_search_scored(limit=200)`（前台最可能调用的 API） | 57.128 ms | **543.899 ms** | **10.9×** ❌ |
| `partial_search(min_matched=2)` | 73.387 ms | **740.660 ms** | **14.8×** ❌ |
| `co_search([体检,复诊])` 低频对 | 0.665 ms | 6.690 ms | 0.13× ✅ |
| **同 schema 换计划**：选择性升序两两求交 + LIMIT 早停 | 1.893 ms | **2.744 ms** | **0.05× ✅（139× 于 as-built）** |
| （对照）选择性**每次现算** `COUNT(*)` | — | 55.836 ms | 1.12× ❌ |

四条比数字更重要的结论：

1. **机理级证据升级**。as-built 的 `EXPLAIN QUERY PLAN` 实测输出第二行是 `USE TEMP B-TREE FOR GROUP BY`：
   主键 `(term, entity_id, occurred_at)` 的索引序按 term 优先，`GROUP BY entity_id` 用不上它，
   于是 1M 档约 78 万行命中被逐行插入临时 B-tree，**成本与结果集大小无关**（只返回 1 条也付全价），超阈值还会溢出到磁盘临时文件。
   这比 §3.5-B 原来的纯计时证据强一档：不只是"慢"，而是**能指出慢在哪一行计划上**。
2. **`LIMIT` 不救场，反而更慢**（543.899 > 382.074 ms）：`ORDER BY latest DESC LIMIT 200` 必须先完成全量分组再排序再截断。
   ⇒ 前台最想用的 API 恰好是最慢的那个。这条要写进 §3.5-C 的驾驶舱读路径规约：**top-K 不是"全量算完再截断"，而是"早停"**。
3. **规模敏感度是 ×10/数量级**（3.488 → 38.147 → 382.074 ms）。100k 档 `co_search` 是 38.1 ms——**看起来达标**（<50）。
   若发布门只在 CI 档（100k）跑，这个 7.64× 的线上事故会被绿灯放行。§5.2"发布门必须跑 1M"由此获得**第二个独立证据**。
4. **选择性必须来自 planner 缓存**，不能现算（55.836 ms，超门 1.12×）。这是采纳计划的**隐藏前提**，
   不写进规约，下一个人会把它"优化"回超门状态。刷新节奏 = 摄入批次边界。

顺带被证实/被修订的设计条款：

- **`cap=8` postings/对象从"优化"升级为"必要条件"**：as-built 无 cap ⇒ **29.02 行/实体**、1M 实体索引 **4,219 MB**（我方案同口径 ≈900 MB，4.6×）。
- **摄入内存必须流式**（`V3G-002`，P0）：as-built `index_many()` 先物化全部 postings 再单事务写入 ⇒ 峰值 RSS = O(总量)。
  200k 实体对照：单批 **1,019.1 MB** vs 分批 **390.2 MB**（−61.7%），耗时不增反降 1.5%（抖动内 ⇒ 分批免费）。
  **1M 档首次运行被 OOM-kill（SIGKILL/exit 137）**，改分批后才跑通（建索引 176.6 s，5,662 实体/s）。
  端侧 RAM 更小 ⇒ "派生物必须可重建"（铁律 1 第③类）在 as-built 下**事实上不成立**。设计书原版没写摄入内存上限，这是**漏洞，现补**：
  任何批量写路径的峰值 RSS 必须 = O(chunk)，验收断言 `peak_rss(chunked) < peak_rss(single_batch)`。
- **别名归一不能靠模块自觉**（`V3G-007`）：宪法 §89.2 要求索引覆盖别名，实测查询 `母亲` 命中 10,990（= 字面含"母亲"的实体数），
  查询 `妈妈` 命中 333,334 ⇒ 别名召回缺失 **96.7%**。别名归一的主责模块（4号工单）**根本没交付**，
  而 registry 里 `M1-021 keyword-alias-inverted-projection` 既未派单也未实现，`Entity.aliases` 字段存在但写入侧不消费。
  **两个模块各自"合规"，系统层面 §89.2 不成立**——这是 §2"模块边界处最容易死人"的实例，且缝是**已知的**（号都发好了）。
- **设计书自身的漏洞（现补）**：我管住了"设计 → 断言 → CI"，**没管住"断言 → 派单 → 实现"这一跳**。

### 3.7.6 第二个 as-built 对账（`M1-001R` 端侧摄入）与两条一般化教训

第一份 as-built 报告的对象是检索热路径（§3.7.5）。第二份换到**端侧摄入与隐私红线**：
`src/aios_core/ingest/multimodal_edge.py`（工单 1号，555 行）。报告：
`reviews/architecture/AIOS_Core_as_built_审查报告_M1_001R_端侧摄入与声纹TTL_2026-09-16.md`；
探针 `verify_landed_m1_001r_edge.py`（v1.3.0）+ 修复前/后两份工件（前者标 `HISTORICAL`）；
gap 号 `V3G-009~011`。裁定：**交付成立**，三条违宪红线全部可执行地满足（10/10 门通过），
但查出 2 个真实缺陷（已修）与 1 个口径分歧（待裁决）。

关键实测：单帧清洗（含 2 MB 擦除）p95 **0.173 ms** vs 工单"50ms 初筛"⇒ **289× 余量**；
128 维 LSH 单次哈希 **0.797 ms**；10 万条声纹档案 sweep **437.408 ms** / advance **550.465 ms**；
陌生声纹 > 180 天墓碑召回 **1.0**（10,000/10,000），已绑定实体误伤 **0**（0/2,000）。

两个缺陷的形状很不一样，值得各记一条一般化教训：

- **`V3G-009`：隐私计量撒谎**（P1）。`RawByteSink.purge()` 对**不可变 `bytes`** 也累加 `purged_byte_count`。
  Python 里 `bytes` 无法擦除（实现方在 docstring 中已诚实声明，这是加分项），但把"真擦除"和"只丢引用"
  混进同一个计数器，就让这个客观限制**在指标层面消失了**——一个以"物理删除原始大图字节"为最高红线的模块，
  对外报告"已销毁 2,000,000 字节"，其中一半其实原封不动。
  修复：`purged_*` 保留为总量（向后兼容），新增 `zeroed_*` 与 `released_*`；`released_frame_count > 0`
  从此是"设备适配层交了 `bytes`"的**可观测告警**。
  **教训**：合规类指标必须能**自证区分度**。"做不到"是可以接受的工程事实，"做不到但指标看起来做到了"不是。
- **`V3G-010`：循环内的不变量**（P2）。`bind_nearest_entities` 每次比较都把两个 32 字符十六进制串
  `int(...)` 解析一遍 ⇒ 2,000×500 = 100 万次比较 **748.6 ms**；把解析提到循环外后 **204.3 ms（3.66×）**，
  `bound_count` 前后同为 969（语义 parity）。
  **但真正的教训是我自己犯的错**：第一版"优化"漏写 `.bit_count()`，排序依据从海明距离变成 XOR 数值大小，
  300 个 profile 里 **178 个绑定结果改变**——而 **650 个既有测试全绿放行**。
  原因：既有测试钉住了 fail-closed 分支（并列 ⇒ 不绑）与格式校验，**没有任何测试钉住"成功绑定"这条正路**。
  ⇒ **规约（写进 §5.2 禁止事项）**：对"只改性能不改语义"的重构，验收断言必须是**与旧实现的行为差分**
  （保留一份旧形状的参考实现，断言输出逐一相同），而不是新实现的自证测试。
  自证测试只会重复你此刻的理解，而此刻的理解正是最可能出错的地方。
- **`V3G-011`：同一模块里"180 天"有两套口径**（P1，**不擅自统一**）。Manager 严格 `> 180d`、
  StateMachine 包含 `>= 180d`，边界日给出相反的隐私结论；两者各有测试钉住、docstring 主动声明 ⇒ 有意共存。
  审查方**不裁判**：改成 `>=` 会改变既有验收断言，改成 `>` 会削弱隐私保守性。探针门 E7 因此只断言
  "分歧被显式测出并记录在案"。**分歧可以存在，不可以没人知道。**
- **门自己也踩了坑（CG-1 多探针）**：我最初把所有审计工件都拿去和**同一支**探针比哈希，
  于是 M1-001R 的工件被误判"溯源断裂"。修法是按工件解析各自的探针（`provenance.probe_script` 显式自述优先，
  文件名约定兜底），并新增负向自测 **S14**——它同时断言两面：改 A 模块的源码 ⇒ A 的工件必须失效（`expect`），
  且 B 模块的工件**不得**被牵连（`expect_absent`，自测框架为此新增的能力）。
  只做正向断言的话，"把所有工件一律判失效"这种粗暴实现也能通过自测。负向自测现为 **15 场景**。

> 顺带修正一处旧记录：`RawByteSink`/`bytes` 的擦除价值**不在峰值内存**。E11 实测 4,000 帧 × 512 KB 流式摄入，
> 可擦除与不可擦除两条路径的峰值 RSS **完全相同**（268.6 MB vs 268.6 MB）——CPython 分配器两种情况都复用已释放块。
> 擦除的价值在**取证面**（冷内存、swap、core dump、崩溃残留）。这一条如实记录，不用它去支撑"擦除省内存"的说法。


### 3.7.7 第三个 as-built 发现：**进程级单调高水位不能当模块预算门禁**（`V3G-012`）

本轮把本方工作叠到其他号位已落地的提交之上时，全量套件出现 1 项失败：
`tests/simulation/test_30day_headless_life_simulation_independent.py::test_gate3_peak_rss_within_128mb`。
**审查方的第一动作不是读代码，而是回到不含本方任何提交的父提交 `a04964e` 上跑同一套全量套件**——
这一步在 40 秒内把"我打坏的"与"本来就坏的"分开，比任何代码审读都更快给出因果结论。

| 情形 | 结果 | 说明 |
|---|---|---|
| 单独跑该项（当前树） | **1 passed**，1.39 s | 进程小，高水位低于阈值 |
| 全量套件（当前树，第一次） | **1 failed**，797 passed | 前面数百项测试已抬高进程高水位 |
| 全量套件（当前树，第二次） | **798 passed** | 同一份代码，结论翻转 ⇒ 非确定性 |
| 全量套件（**父提交 `a04964e`，不含本方改动**） | **1 failed**，778 passed | **失败与本方改动无因果关系** |

**根因（量错了对象，不是阈值太紧）**：`headless_life_driver_independent.py:468` 取
`resource.getrusage(RUSAGE_SELF).ru_maxrss` 作基线，`:939` 只用它做 `max()` 累积，
`:943` 直接 `return self._rss_peak_kb / 1024.0`。`ru_maxrss` 是**整个进程的单调高水位**（Linux 单位 KB，只增不减），
不减基线 ⇒ 数字**不可归因**到被测模块；单调不回退 ⇒ 结论**与测试执行顺序耦合**。
于是那道"峰值 RSS ≤128 MB、并留余量 <64 MB"的门禁，实际裁定的是 **pytest 运行器进程**的总内存。

**正确范式就在同一个仓库里**（另一份并行实现，无需外求）：

| | 缺陷实现（`*_independent.py`） | 正确范式（`headless_life_driver.py`） |
|---|---|---|
| 取值来源 | `ru_maxrss`：进程**单调高水位** | `/proc/self/statm` 常驻页 × 页大小：**时点** VmRSS |
| 是否减基线 | 否（返回绝对值） | 断言里显式用差值：`final_rss − initial_rss ≤ 32 MB`（泄漏判据） |
| 顺序耦合 | 有（前面测试的峰值被永久计入） | 无（差值与时点值都不累积历史） |
| 实测稳定性 | 单跑过、全量挂，**非确定性** | 单跑与全量**均确定性通过** |

**可泛化规则（写进 §9.3 类红线的位置，此处先立论）**：
> 任何**资源预算门禁**的判据必须同时满足两条：**可归因**（数字只反映被测对象）与**顺序无关**
> （在同一份代码上，改变测试执行顺序不改变结论）。凡读取进程级单调量（`ru_maxrss`、`VmHWM`、
> 累计计数器）来充当模块级预算，必须**减基线**或**子进程隔离测量**；否则该门禁不是在验收模块，
> 而是在验收"谁碰巧排在它前面"。**并且：放宽阈值不能修好它**——阈值从来不是问题所在。

**处置**：登记 `V3G-012`（`NUMCI`/`Gate0`/P2，`OPEN_NEEDS_FIX_BY_OWNER`）。
缺陷位于 SIM-001 交付方的产品代码与其自建门禁测试内，**审查方不改他人代码**，
只登记、给出可验收修法（差值型判据或子进程隔离 + 连跑三次全量套件均绿），并禁止三种伪修法
（拿 `ru_maxrss` 绝对值当模块预算、以"单跑通过"当门禁成立的证据、为让套件变绿而放宽阈值）。
与 §3.7.6 的 E11 教训同源：**RSS 类数字天然是环境量**，要么差值化归因，要么就只能当取证线索、不能当验收判据。

# 四、工作台交互与虚拟测试规范配套升级建议

## 4.1 《AIOS认知工作台功能规格》升级（V0.1 → V0.2）

### 4.1.1 三层 UI 契约：**契约与渲染分离**，PC 与穿戴共用同一 DTO

旧规格的 §2（PC 三栏布局）与 §3（初始工作包 11 项）把**布局**当成了契约。V3 要求同一套认知能投影到 5~6cm × 23cm 的柔性屏、PC 控制台与未来的 App，因此必须把契约抽成**设备无关的三层**：

| 层 | 契约对象 | 内容 | 手环渲染 | PC 渲染 |
|---|---|---|---|---|
| **L1 体态层（Ambience）** | `AmbientState{mood_tone, urgency, epoch}` | 不打断的持续状态：今日基调、是否有未决安全项、AI 是否在后台工作 | 弧面边缘的微光/单次微震语义 | 状态灯 + 一行文字 |
| **L2 态势画布层（AmbientCanvas）** | `AmbientCanvas{wake_reason, timeline_span, dim_cards[], ready_tasks[], evidence_pointers[]}` | 本次 Wake 的看板投影：**只放指针不放正文**（第九十条） | 正面 6cm 主视区：1 个唤醒原因 + ≤3 张维度卡 + ≤2 条就绪任务 | 三栏布局（旧规格 §2 保留，作为 L2 的 PC 渲染） |
| **L3 挂载技能层（SkillCard）** | `SkillCard{capability_id, version, min_projection, receipt_schema}` | 可执行能力的卡片化投影与回执要求 | 侧键长按呼出，单手可操作 | 工具面板 + 执行日志 |

**关键裁定**：旧规格 §3 的"初始工作包 11 项"是 **Single-Shot Cockpit Manifest 的雏形，但不违宪也不完整**——它缺四步序段序、缺预算档、缺水位、缺 receipt。因此处置是 **升级为 `RC-021` 的 manifest 投影**，而不是推倒重写（与元裁决 §"措辞边界"一致：补契约、补 owner、补验收）。

### 4.1.2 23cm 柔性屏的物理约束如何驱动设计（不是美学，是硬约束）

| 物理事实 | 工程后果 | 设计约束（写进 `RC-030` / `RC-031` 验收） |
|---|---|---|
| 宽 5~6cm、长 23cm **环绕手腕** | 只有正面约 6cm 弧面在自然抬腕时处于最佳视角，侧面弧区存在**视角衰减与触控畸变** | L2 主视区**限定正面 6cm**：≤1 个唤醒原因 + ≤3 张卡 + ≤2 条任务；侧面弧区只允许 L1 体态层（微光/边缘提示），**禁止在弧面畸变区放可点按目标** |
| 柔性屏 + 单手可操作 | 精确点按不可靠 | **侧键是唯一硬按钮**；其余交互为"抬腕 / 按耳 / 忽略"三条粗粒度通道（第九十八条之一 FSM 的三通道），**禁止设计需要精确滑动或多指手势的核心路径** |
| 微型外放喇叭 + 超宽频震动马达（兼具骨传导） | 公共场合外放有隐私风险；骨传导音质偏闷、偏低频 | **私密音频必须由先导震动的 epoch 授权**（I6）；外放需侧键显式二次确认；骨传导通道的信息密度按"偏低频、短句"设计 ⇒ 与 1~3 句法则**互相强化**（§4.1.5） |
| 全向麦克风常开 | 误采集与投毒风险 | 麦克风内容一律走 `DATA` lane，**不得升格为指令**（`RC-027` 记忆写入防火墙）；旁人语音归 `BYSTANDER` speaker，**不自动归属用户** |
| 端侧微型摄像头 | 原图不可回传、不可原样存 | 一律端侧语义化（caption/OCR/关键物品/人物关系）后以文字 Observation 入库（第三十三条第 2 款），关键帧只留 TTL 冷存或哈希 |

### 4.1.3 防误触状态机（FSM）：**epoch 是唯一钥匙**

```text
【IDLE 静默休眠】 骨传导断电、手势深度休眠（杜绝挠头/托腮误触）
   │ AI 产生主动沟通意图 ⇒ C15 分配 epoch = monotonic_increase(wake_id)
   ▼
【TRIGGERED 震动唤醒】 马达发送震动语义（单次微震=常规 / 急促强震=紧急高危）
   │ 同时开启 5~10 s 应答检测窗口（PAR 默认，可调）；**窗口与 epoch 绑定**
   ├──通道 A 抬手看表──► 【ENGAGED_DISPLAY】 柔性屏点亮 L2 文字摘要；侧键 ⇒ 外放真人语音
   ├──通道 B 手指按耳──► 【ENGAGED_PRIVATE_AUDIO】 **仅当 epoch 有效**才通电骨传导
   └──通道 C 超时/忽略──► 【DISENGAGED】 窗口销毁、epoch 失效、回 IDLE
                            ROUTINE ⇒ 进未读胶囊；URGENT ⇒ 可重发一次（重发用**新 epoch**）
   任意状态 ──传感器/通道故障──► 【FAULT】 停止私密音频，降级为震动 + 屏显，并生成调试任务
```

**零误触铁律（I6）的工程化表达**：`private_audio.enable()` 的**前置条件**是 `epoch_registry.is_valid(epoch) ∧ epoch.wake_id == current_wake ∧ now ∈ [epoch.opened_at, epoch.opened_at + window]`。四个条件缺一不可，且 epoch **单调递增、用后作废**（防重放、防并发通知串线）。Linux 侧由 `SimulatedInteractionPort` 打桩验证，包括"用户挠头但无 epoch""epoch 过期后按耳""两条通知并发"三种注入。

| 断言 | 门限 |
|---|---|
| 无先导震动时私密音频开启次数 | **= 0** |
| epoch 过期后按耳触发音频的次数 | **= 0** |
| 并发通知下音频串线（播错 wake 内容）次数 | **= 0** |
| 紧急高危（急促强震）与常规提示（单次微震）的节奏/强度可区分度 | fixture 可判（不同 `haptic_pattern_id`） |
| FAULT 状态下私密音频开启次数 | **= 0**（必须降级为震动+屏显） |

### 4.1.4 防长篇说教：把"真人老友语调"变成可测指标

宪法要求 1~3 句、反说教、反谄媚。旧规格没有任何可判定口径。本设计书把它落到 `RC-030` + `RC-037`：

1. **输出长度预算器**：`max_sentences = 3`（PAR 默认），例外**必须枚举**且留痕：`{SAFETY, ACCESSIBILITY, USER_EXPLICIT_EXPAND, LEGAL_OR_MEDICAL_DISCLAIMER}`；例外之外超长 ⇒ **长篇拦截器**截断并改写，同时写入 `CommunicationExperience.longform_violation`。
2. **三个可统计指标**（数据来源唯一 = `CommunicationExperience`，不得由模型自评）：`sentence_count_dist`（句数分布）、`sermon_rate`（说教率：祈使句/劝导句占比）、`interruption_rate`（被打断率：用户在 AI 未说完时接管对话的比例）。
3. **反谄媚事实阈值不变性**：同一事实判断在 `rapport` 高/低两档下的**结论必须一致**，只允许表达方式变化（`rapport` 只影响表达成本）。测试用同一 fixture 跑两档 rapport，断言结论相同。
4. **不以讨好换接受率**：A/B 评估的净收益指标必须**同时**包含"帮助成功率"与"谄媚/操控率"，后者恶化即判负（`RC-037` + M5 门）。

### 4.1.5 必须废黜的一条：§7.2「待办任务必须进入定期任务盘点」

【工作台规格】§7.2 L227 的这条规则 = **把 Token 空转制度化**，与第八十六条第 2 款"严禁在每次 AI 醒来时都无条件跑一遍"正面冲突。处置：**废黜该入口**，改为：

- 待办任务的暴露**只由条件就绪决定**（`RC-017`），未就绪任务在后台静默休眠；
- "盘点"作为一种**用户可显式发起**的能力保留（`SkillCard{capability_id='task.review'}`），或作为 `REVIEW` 档的低频后台任务（带预算与降级），**不得挂在每次 Wake 的必经路径上**；
- 巡检类需求（如 UNKNOWN 条件普查，实测 616.3 ms）归入**巡检调度**，与 1 s 首字热路径物理隔离。

### 4.2.1 场景编号：`TS-001~TS-051`，一次性消灭孤儿验收与悬空引用

### 4.2.2 规模表必须拆成两列（现规范与实测差 1.8~9.2 倍）

| 档 | 现规范 §5（L92-96）「条」 | 实测 reduction 模型（宪法第三十三条口径） | 偏差 |
|---|---|---|---|
| 1 天 | 2,000 ~ 10,000 | **1,090 行/日**（长期库对象行） | **1.8 ~ 9.2×** |
| 1 月 | 60,000 ~ 300,000 | ≈ **32,700 行/月** | 同比例 |
| 1 年 | 70 万 ~ 360 万 | ≈ **397,850 行/年** | 同比例 |

⇒ V0.2 必须把规模表拆为 **`raw feed volume`（端侧原始采样量，可以是 50/100 Hz 级）** 与 **`long-term object rows`（入库长期对象行数）** 两列。**混淆这两列是现规范最大的定量错误**：按现规范的"条"去建库，会直接违反第三十三条第 1 款（严禁高频灌水），并且让所有存储/检索基准失去可比性。

### 4.2.3 时间口径必须分离报告

任何时间窗基准必须**分别**报告 `occurred_at`（发生时间，宪法口径，payload 内无索引 ⇒ as-built 1,201~1,468 ms）与 `learned_at`（得知时间，有索引 ⇒ 4.824 ms）两组数字。**只报一组的基准一律无效**（铁律 2）。这一条能防止"规模门绿灯但滑动条不可用"的最隐蔽失败。

### 4.2.4 双 profile

| profile | 用途 | 关键默认值差异 |
|---|---|---|
| `linux-virtual` | 本阶段全部开发验收 | 容器 FS、Mock 模型、无无线约束；本设计书全部实测数字属此 profile |
| `wearable-target` | 未来端侧验收 | 真实闪存 fsync、TTFU/TTFAudio、震动与骨传导时序、离线降级；**同一套断言，不同默认值** |

### 4.2.5 隐藏真值生成器 v2 + 盲测门

- **隔离**：隐藏真值（`HiddenTruthV2`）与生产查询物理隔离（不同 schema/不同连接），生产路径**不得**读到真值表（旧规范 §2 四层隔离保留并强化）；
- **v2 新增能力**：迟到数据（`occurred_at` 在过去、`learned_at` 在现在）、时钟倒挂、声纹再遇、跨会话承诺、脏数据族、**别名与否定表述**（"不是生日是周年"）、**投毒注入**（外部 OCR/群聊试图升格为指令）；
- **盲测纪律**：评估标准与 fixture 在盲测开始前**版本冻结**（hash 入 registry）；旧规范 §16 L393"不得看完盲测结果后修改标准"保留，并补一条**版本窗口**：标准变更只能在下一个盲测周期生效，杜绝"当场修补"的时间窗。

### 4.2.6 Token / 成本 / 延迟账本断言

每个场景结束后必须能对账：`reserve` 总量 = `settle` 总量 + 未用释放量；分类账（七类）之和 = 总用量；超支场景必须触发**降级阶梯**并留 `degraded_to`。年度上限参考 **68.6 M token / ≈$316**（profile 默认，非宪法常量）。**无账可查 = 场景不通过**，因为"零预算"是 V3 与 R2 最大的区别之一。

### 4.2.7 7 向归因回放

每个失败场景必须能用 `ContextReceipt` + `ContextSnapshot` 重放，并归因到 §4.1.6 表的 7 个方向之一。**无法归因的失败不得关闭**（否则同一错误会在 M5~M8 反复出现且无人知道归属）。
