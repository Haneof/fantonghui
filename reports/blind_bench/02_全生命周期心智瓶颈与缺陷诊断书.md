> 证据来源：`reports/blind_bench/bench_run.json`（scale=1.0，seed=20260916）

## 1. 三个"最"的答案（先给结论）

| 问题 | 答案 | 实测数字 |
| --- | --- | --- |
| **哪个阶段最烧 Token？** | **阶段八（驾驶舱 + 终极对话）** | 4,720 / 5,121 Token = **92.2%**（其中对话 4,365、看板 355） |
| **哪条查询最烧 I/O？** | **`SELECT object_revisions`**（每次读世界都要把修订行拉一遍） | 3,700 条语句 / 扫描 **114,163 行** / 195.34 ms；扫描行数最多的阶段是 S3（137,385 行，主要是检索倒排写入） |
| **哪个认知抽象扭曲最多？** | **端侧宏观化（50 Hz → 宏观观察）**，误差界占用率 **100.0000%** | IMU 误差 0.4000/0.4g、心率误差 3.9971/4.0bpm；紧随其后是时间金字塔文本抽象 99.889% |

三者的机制不同：**Token 热点是"输出侧"问题**（对话装配比认知本身贵），
**I/O 热点是"读放大"问题**（按修订号点查却用了全表扫描式读法），
**抽象失真是"端侧不可逆"问题**（原始高频流按铁律 4 不能留，只能靠误差界兜底）。

## 2. Token 账单：为什么钱花在"说话"上

| 阶段 | Token | 来源字段 | 说明 |
| --- | --- | --- | --- |
| S1 摄入 / 提纯 | **0** | 机械阶段 | 压缩、裁决、落盘全在端侧；`model_calls = 0` |
| S2 时间金字塔 | **14** | `year_synthesis_tokens` | 年总结叙事文本 |
| S3 共振 / 生命周期 | **140** | `cooccurrence_tokens` | 4 组共现召回的结果页估计 |
| S4 认知演进 / 门槛 | **0** | 机械阶段 | 拐点识别 + 熔断 + 三重门限全机械 |
| S5 单跳隔离 | **0** | 机械阶段 | 注解写入 + 单跳标记，0 次推理 |
| S6 共生决策 | **92** | `advice_tokens` | 一条 3 句建议 |
| S7 沟通博弈 | **155** | `actions_token_cost` | 6 条行动的内容 + 理由 |
| S8 驾驶舱 / 对话 | **4,720** | `manifest_total_tokens` + `conversation_total_tokens` | 看板 355 + 10 轮对话 4,365 |
| **合计** | **5,121** | | |

**诊断**：全链路 73.8% 的 Token 花在最后 10 轮对话上，而"真正干活"的认知阶段（S2+S3+S6）只占 4.8%。
这不是坏事 —— 它说明**认知本身是省钱的**（机械算子把 113 万条流压成 14 Token 的年度叙事），
但也说明**一个真正的风险**：如果对话轮次从 10 轮涨到 50 轮，Token 会线性膨胀到 2 万+，
而其中大量 Token 花在"把看板里已有的结构化事实重新说一遍"。

## 3. I/O 归因：读放大在哪里

按墙钟区间把每条 SQL 归因到阶段（数字来自 `extras.diagnosis.io_attribution`）：

| 阶段 | SQL 语句 | 扫描行数 | 累计耗时(ms) | 头号语句 |
| --- | --- | --- | --- | --- |
| S1 | 11,321 | 25,636 | 49.21 | `SELECT object_revisions` 21,399 行 |
| S2 | 4 | 14,236 | 16.66 | `SELECT object_revisions` 14,236 行 |
| S3 | 22,178 | **137,385** | 46.91 | `INSERT search_postings` 99,948 行 + `SELECT search_doc,search_occurred` 18,020 行 |
| S4 | 2 | 7,118 | 24.06 | `SELECT object_revisions` 7,118 行 |
| S5 | 16 | 25,138 | 50.97 | `SELECT object_revisions` 25,006 行 |
| S6 | 161 | 40,409 | **57.51** | `SELECT search_doc,search_occurred` 25,228 行 |
| S7 | 205 | 3,684 | 4.55 | `SELECT object_revisions` 3,593 行 |
| S8 | 6 | 17,817 | 19.48 | `SELECT object_revisions` 17,816 行 |
| （启动/收尾） | 7 | — | — | 未归因 |

**读法**

1. **`SELECT object_revisions` 是全场最大读放大源**：3,700 条语句扫描 114,163 行，
   平均 **30.9 行/语句**。世界只有 3,624 条修订，却由于"每阶段都重新装载世界视图"
   被反复整表拉取（S1 21,399、S5 25,006、S8 17,816 行都是同一个动作的不同阶段重演）。
2. **S3 是最重的**写放大源**：3,604 条 `INSERT search_postings` 写了 99,948 行，
   即**每条事实平均写 27.7 条倒排 posting**（CJK 逐字 + 词元混合切分的固有成本）。
3. **S6 是"精度最贵"的阶段**：161 条语句扫描 40,409 行、耗时 57.51 ms，
   换来的是 6 条证据指针 —— 平均**每条证据 6,735 行扫描 / 9.6 ms**。
   多 facet 并集召回（每个关键词单独查一次再合并）是召回质量与 I/O 的直接交换。

## 4. 认知抽象失真：哪一层丢得最多、能不能补回来

| 抽象层 | 阶段 | 失真度 | 可恢复性 | 兜底机制 |
| --- | --- | --- | --- | --- |
| 端侧宏观化（50 Hz → 宏观观察） | S1 | **1.000000** | **不可逆** | 误差界 ε 硬约束 + 冲击点原值单独成 Observation |
| 时间金字塔文本抽象（年总结） | S2 | **0.998894** | 事实 100% 可下钻恢复，叙事文字不可恢复 | evidence_ids 断链率 0.0%，原始原话逐字节可比 |
| 跨维事件合成（同窗样本 → 1 个事件） | S3 | 0.000000 | 可逆 | 事件钉死来源修订号与证据集 |
| 维度曲线按天聚合 | S4 | 0.000000 | 可逆（曲线是附加物化视图） | 需要时刻精度时回落原始 Observation |

**为什么会这样（不是 bug，是权衡）**

* **端侧不可逆是宪法要求的结果**：铁律 4 要求高频原始流不落盘，于是"重建误差"成为唯一质量保证。
  本轮实测 IMU 误差 0.4000（ε=0.4g）、心率误差 3.9971（ε=4.0bpm），
  即**误差界被用满到 100.0%** —— 合法但零余量，见缺陷 D1。
* **年总结的"文本保留比"只有 0.11%**：年度叙事只有 14 Token，而它背后的原始事件有 12,659 Token 的体量。
  机制上没错（证据没丢），但**阅读体验会退化成"只有索引没有内容"**，见缺陷 D2。
* **共振与曲线的"低失真"要打折看**：S3 失真度 0 是因为窗口内样本全部进了合成事件，
  但同时窗样本只有 5 条 —— 覆盖率高不代表证据厚，见缺陷 D3；
  曲线的 0 失真只在"每天不超过一条事件"时成立，事件密集时这个数字会立刻上升。

## 5. 缺陷清单（只列被实测数字命中的条目）

### D1（高）端侧宏观化重建误差贴满 ε 上限，零安全余量

* **实测**：IMU 误差 0.4000 / ε=0.4g；心率误差 3.9971 / ε=4.0bpm → 误差界占用率 **100.0000%**。
* **机制**：自适应窗口在平稳段持续增长直到曲率预算耗尽；冲击点附近以最小窗切分，
  最大误差恰好落在 ε 上。由于原始流不落盘（铁律 4），这一层**不可逆**。
* **修法**：窗口合并判定改用 `0.7ε` 的保守裕度；或对疑似生理突变段临时收紧 ε 一档，
  用极少量存储换可证明的安全边际。
* **影响面**：所有依赖"宏观观察"的后续结论（疲劳、拐点、熔断）都建立在这一层的误差之上。

### D2（中）年总结文本保留比 0.11%，叙事层近乎空壳

* **实测**：年总结 14 Token / 年原始 12,659 Token，保留比 **0.001106**。
* **机制**：物化年总结只保留一段高度浓缩叙事，真正的故事都在 `evidence_ids` 指针里；
  一旦上层不会下钻，用户看到的就只是索引。
* **修法**：年总结物化"主题句 + 3~5 个关键片段（含指针）"的分层叙事，仍受 Token 预算约束。

### D3（中）共振窗内样本丰度不足，置信底座偏薄

* **实测**：同窗可用样本仅 **5** 条即合成事件（覆盖率 1.0，但基数极小）。
* **机制**：共振只要求"同窗 ≥3 维度"，不要求每维度样本数；三域各命中一条就能升级为事件，
  于是稀疏时段的事件与密集时段的事件共享同一置信口径。
* **修法**：把样本丰度写进合成事件置信度；2 维度的"弱共振"先进候选池，等第三维度到齐再升级。

### D5（高）单跳隔离把"新注解自身"计入直接消费者，审计口径需要显式区分

* **实测**：直接消费者 4 条，其中 3 条是历史下游、1 条是今日新注解本身。
* **机制**：`reverse_invalidate` 返回的 STALE 集合包含注解对象本身，若口径不区分，
  报告会把"3 个历史下游"说成"4 个消费者"，也会让"隔离到底碰了多少历史"看起来更大。
* **修法**：`InvalidationReport` 拆成 `historical_consumers` 与 `annotation_id` 两个字段
  （本轮已用 `annotation_counts_as_single_hop` 事实显式区分，代码侧字段拆分待做）。

### D6（中）建议的证据召回以 Observation 为主，高阶对象未充分参与

* **实测**：`advice_evidence_types = observation`（6 条指针全是 Observation）。
* **机制**：检索投影对 Claim / EventAnchor 的权重低于 Observation，导致"已经推理过的结论"
  在建议里没有被复用，用户看到的建议更像是"复述原话"。
* **修法**：把 Claim/EventAnchor 纳入同一召回面，并在建议里标注证据层级（事实 / 结论）。

### D8（中）驾驶舱单轮 Token 峰值仍偏高（看板未分片装载）

* **实测**：单轮峰值 552 / 1,500 Token = **36.8%**；看板一次装载 355 Token、折叠 3,512 Token。
* **机制**：四透镜亮点一次性装载，虽然没越预算，但相对"1~3 句"的输出仍有大量结构性开销；
  轮次一多就会线性放大（见 §2 诊断）。
* **修法**：按透镜懒装载 + 把 `elided` 计数当作"可继续追问"的钩子，而不是全量装载。

### 已修复条目（留档）

* **D7（低）风格推荐与回避清单冲突**：旧实现会在"得分最高"里挑风格，被 100% 抵触的风格
  仍可能因"矮子里拔将军"被推荐。已修：`ExperienceTracker.get_effective_style` 先剔除回避清单，
  无合格风格时回落基础人设（实测 S7：损友接受率 0.0 → 进回避清单；老友 0.5 → 推荐；
  案发场景推荐风格从"损友"变为"default"）。
* **S6 标点污染（偏高）**：建议文本曾出现 `；银行流水…` 起头与 `出资款。。` 双句号。
  已修：证据摘录先做标点卫生（去悬空分隔符、折叠重复标点），拼接按"前句已收尾则直接接续"处理，
  压缩改为"保留最可执行的末句 + 向前尽量拼证据"，绝不从句子中间截断
  （实测：116 字 / 3 句 / 6 条证据指针 / 接地复核 True）。

## 7. 一句话总结

当前实现的"不完美"集中在三处：**端侧压缩用满了误差预算（D1）**、
**叙事层被压得几乎不剩文字（D2）**、**读路径反复整表拉修订行（§3 读放大）**。
三者都不是语义错误，而是**质量/存储/延迟三角**上刻意选的边 —— 本轮压测的价值在于把它们量化，
让下一步的取舍有数字可依。
