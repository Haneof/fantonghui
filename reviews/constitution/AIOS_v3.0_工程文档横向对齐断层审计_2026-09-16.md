## 〇、明确判词

> ### 按现有【架构规划】+【总工任务书】+【工作台规格】直接编码，项目不会“崩”，会**在 M1 静默偏航、在 M2 机制性卡死**。

所以本次审计发现的断层**不是工程团队理解偏差，而是文档链在 2026-09-15 修宪后没有做过一次同步**。82 个 Issue 里没有一个 Issue 的“上位依据”指向 v3.0。

| A03 | 事件由大模型判断而非底层生成 | 未知实体改名后，旧引用仍能解析 |
| A04 | 事件是锚点，引用而非复制 | 修正一项底层主张，能找到受影响认知和任务 |

| A06 | 世界搜索可用 | 重复投递、重启和模型重试不产生重复行动 |
| A07 | **时间缩放可用** | **无用户提问时能够触发、调查、决策、任务化** |
| A08 | **AI 操作可回放** | **用户接受、执行成功、目标改善三个结果分别记录** |

## 一、唤醒与看板机制对齐审查（Single-Shot Cockpit vs 十三步循环）

**【V3宪法】要求**（第 84 条）：①单次看盘聚合看板一次性交付，严禁多轮低效提示词；②四步序 ①照镜子 ②校准羁绊（`DIM_AI_RAPPORT`）③定态度语调 ④看世界与触发源，**顺序绝不可颠倒**。

**现有文档实际内容**：

| 位置 | 实际规定 | 判定 |
|---|---|---|
| 【架构规划】C10 模块（第 3 节表格） | “工作台与会话｜面板、工具协议、**十三步循环**、检查点、上下文接续” | **冲突** |
| 【工作台规格】§10 | 十三步顺序为：1 唤醒来源 → 2 紧急程度 → 3 当前世界 → **4 AI自身状态与承诺** → 5 观察计划 … | **顺序与四步序相反**（v3.0 要求“自身/羁绊”在第 1、2 步，触发源在第 4 步；这里触发源第 1、自身第 4） |
| 【总工任务书】M2-009 | `workspace.open` 返回“当前时间、Wake原因、紧急事项、世界概要、Task/Goal、未确认认知、AI自身状态、数据质量和可用工具”，“工作包只给相关摘要+索引入口” | **部分对齐**（单次交付的思想已在，但无羁绊模型专列、无 token 预算、无四步序字段、无就绪任务过滤） |
| 【总工任务书】M2-012 | “**不能退化成固定十三步脚本**”；“系统提示只规定责任/约束/工具，**不强制先看哪个维度**”；“首包 workspace.open；**模型可多轮 tool calls**” | **正面冲突**（既否定固定序，又把多轮工具循环写成实现方式） |
| 【工作台规格】§10 执行约定 | “不要求生成或保存模型的私密思维链；保存可观察的工具调用、引用、判断摘要、决定和结果” | **可利用**：这正好是把四步序实现为“结构化决策字段”而非串行散文的落点，与 v3.0 不矛盾 |

**断层后果**：编码代理按 M2-012 实现后，AI 每次唤醒会先看 Wake Reason、自由决定路径；而 v3.0 验收（尤其 V3-02 关系节奏、第 11 条分寸感）要求羁绊模型先于世界判断被校准。**两种实现不能同时通过验收，且 M2-012 的“明确禁止”条款（禁止每次必须先读全局人生）会被误读为禁止四步序的第 1 步。**

**修补方向**：区分“**数据装载顺序**”与“**决策因子完整性**”——四步序作为 Cockpit 的四个**结构化输出字段**（`self_state / rapport_state / stance / focus`）强制存在，但**不要求串行生成、不要求先加载全量自身记忆**；十三步循环降级为“会话必须覆盖的责任清单”，与 v3.0 第 15 条第 17 款（禁止流程教条化）一致。

## 二、任务调度与 Token 浪费防范审查（条件驱动 vs 无脑遍历）

**【V3宪法】要求**（第 86 条）：所有待办任务**必须显式声明触发条件** `time_reached / context_matched / event_occurred / dependency_ready`；唤醒时**仅挂载已就绪任务**；等待中任务后台静默休眠，严禁挤占上下文。第 15 条第 18 款把“无差别执行全部待办”列为**严重违宪**。

**现有文档实际内容**：

| 位置 | 实际规定 | 判定 |
|---|---|---|
| M2-005 Task Center | “scheduler 根据 **next_wake/deadline/recurrence** 生成 Wake”；接口 `task.create/update/query/cancel/transition` | **缺失条件引擎**：三个调度维度全是时间，无 `context_matched`、无 `event_occurred`、无 `dependency_ready` |
| M2-006 类型语义 | “**todo 必须 next review**”；测试“待办无 deadline 仍会盘点” | **正面冲突**：待办靠“定期盘点”唤醒 = 遍历 |
| 【工作台规格】§7.1 任务字段 | 20 个工程字段中**没有** `trigger_criteria` / `condition` / `condition_kind` | **缺失** |
| 【工作台规格】§7.2 待办任务 | “有目标但无固定执行时间 → **必须进入定期任务盘点或相关情境唤醒**” | **冲突（“盘点”未加条件约束）** |
| M2-007 观察/验证任务 | “Watch 分 **mechanical condition 与 semantic question**；机械部分命中只 Wake AI”；“Watch 条件使用**有限 DSL/JSON，不允许任意 Python eval**” | **已对齐且可复用**——这是全套文档里唯一符合第 86 条精神的机制，但**只覆盖观察/验证任务，未覆盖十类任务全体** |
| M2-002~004 Wake | 机械触发、去重合并冷却、队列优先级饿死保护 | **对齐**（第 79/82 条） |

**断层后果**：**Token 空转必然发生，且是被文档制度化的。** 一个运行一年的虚拟人若积累 200 个 WAITING 待办，按“定期盘点”设计，每次盘点唤醒都要把它们塞进上下文（或让 AI 逐条判断）。按 v3.0 第 86 条这是**严重违宪**，但按【工作台规格】§7.2 这是**合规行为**。

**修补方向**：把 M2-007 的 Watch DSL **提升为全任务通用的一等条件对象**（`TriggerExpression` AST + 三值求值 + 事件订阅索引 + ready queue），并新增 `task.inspect_ready()`（v3.0 第 91 条已定义该原子操作，**在任务书与工作台规格中命中 0 次**）。

## 三、上下文管理与响应延迟对齐审查（长会话三级流水线）

**【V3宪法】要求**（第 85 条）：前台 1500 token / 5~8 轮活跃滑窗 + 后台异步增量切片萃取（Claim/事件锚点）+ 超链接按需联想回捞；保障 1 秒首字；连续 50 轮不爆 token。

**现有文档实际内容**：

| 检查项 | 命中情况 |
|---|---|
| “流式”“萃取” | 【任务书】**0 次**；【架构规划】0 次；【工作台规格】0 次；【测试规范】0 次 |
| “1500” | 【任务书】**0 次**（仅 V3 宪法 1 次） |
| “长对话”“50轮”“上下文窗口”“首字”“latency” | 全部 **0 次** |
| “token” | 【任务书】**1 次**（第 3510 行，M5-003 A/B 实验比较查询数/token/覆盖/正确性） |
| “context window” | 1 次（第 2084 行，指 Wake 去重的 `dedupe_key=subject+rule+context window`，**与对话上下文无关**） |
| 最接近的现有能力 | M2-011 Session 快照/Checkpoint（`session.start/checkpoint/finish/resume`、`workspace.changes`）；【工作台规格】§3“初始工作包只装载相关摘要和索引，其他资料由 AI 按需展开” |

**判定：完全缺失（0 个 Issue）。** 没有任何 Issue 负责：
1. 前台活跃滑动窗口的组装与淘汰策略；
2. 后台异步增量萃取（对话进行中每几轮/话题跃迁时静默产出 Claim 与 EventAnchor）；
3. 主动联想回捞（实体档案 + 历史事件锚点 + 未完成承诺 + 心理基线的自动注入）；
4. 首字延迟与 token 预算的测量与门禁。

**断层后果**：长对话模块**能跑，但会以两种错误方式跑**——
- 要么把 50 轮全塞进 prompt（token 与延迟双爆，且违反第 85.1 条）；
- 要么只用 M2-011 的 checkpoint 做“会话摘要接续”，即**金鱼脑**：第 85.2 条明令“严禁把 AI 做成只有 5 轮金鱼记忆的弱智”，而现有设计里对话内容只有到 M3-004（日总结）才进入世界，**会话进行中的增量沉淀没有任何机制**。

**注意一个真实冲突**：M2-011 明确“Checkpoint **不保存私密思维链**”，M2-012 也禁止把 hidden reasoning 当依赖。这与 v3.0 第 86.4 条“全操作过程支持**高保真回放**”并存时，**必须显式规定“组装进上下文的切片集合”要持久化**（否则 7 向归因中的“上下文组装问题”永远无法定位）。三份文档都没有这条。

## 十、结论

1. **判词**：按现有文档直接实施，**M1 会静默偏航（检索范式违宪且中文召回为 0，但测试会绿灯）**，**M2 会机制性卡死（四步序 vs 反固定序冲突 + 无条件引擎 + A 系列验收二义，M2-015 无法签收）**，**M3 会发现 R3-03/R3-05/V3-01 三项宪法验收没有任何实现载体**。
2. **最危险的三条**：GAP-02/03（检索：会绿灯通过却是违宪实现）、GAP-05（待办定期盘点：制度化的 Token 空转）、GAP-17/18（测试门缺失，且受 §16“不得事后改标准”约束，**有时间窗口**）。
3. **最便宜的三条**：GAP-15/16（FSM 与三层 UI 的软件契约，可在虚拟世界阶段用状态机 + 模拟器完成，M0-021 已证明团队有状态机冻结能力）、GAP-20/21/22（三个一等对象的契约任务，纯 schema 工作量）、GAP-26/27（编号与口径治理，改文档即可）。
4. **一句话**：**v3.0 已经把方向改了，但派单依据还停在 2.0。现在需要的不是新机制，而是一次文档链同步 + 29 个 Issue 动作（16 新增 / 4 重写 / 9 升级）+ 5 项治理级修补。**
