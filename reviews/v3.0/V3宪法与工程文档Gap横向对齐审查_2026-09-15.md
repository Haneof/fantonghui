## 一、明确判词：会在哪个里程碑卡死？

| 里程碑 | 是否卡死 | 卡死原因（对应 V3 条款） |
|---|---|---|
| **M0** | ⚠️ 部分卡死 | M0-007 Observation 契约未包含 `source_confidence / signal_quality / voiceprint_lifecycle`，无法支撑 V3 第33条边缘轻量化；M0-014 Task 契约未包含 `TriggerCriteria` 条件字段 |
| **M1** | ❌ **硬卡死** | M1-001 接入服务按旧方案会 50Hz 灌水+存原图，存储爆炸；M1-012 搜索仅单关键词 FTS，无法实现 V3 第89条 `world.co_search([妈妈,生日,礼物])` 拓扑交集；M1-010 时间镜头无 5D 滑动条原子接口 |
| **M2** | ❌ **彻底卡死** | M2-009 workspace.open 仍是旧“初始工作包+多轮工具循环”，与 V3 第84条 Single-Shot Cockpit Manifest + 四步心智法则直接冲突；M2-005/006 Task Center 无条件过滤引擎，违反第86条，每次 Wake 遍历全量 Task，Token 空转；M2 缺失长会话三级流水线（1500 token 窗口+后台切片萃取），违反第85条，50轮对话必爆 |
| **M3** | ❌ 连带卡死 | M3-001 依赖传播未定义批量复核与惰性失效，面对 V3 第93条老张关系翻转会算力雪崩；M3-004/005 总结无 Interpretation Layer，无法实现第31条之一反向标注 |

**最早卡死点**：**M1-001（边缘摄入）与 M1-012（共现检索）** 在 M1 结束前就会暴露；**M2-009（Cockpit）** 是 M2 的第一道门，必卡。

## 二、七大核心对齐项断层分析

### 1. 唤醒与看板机制对齐审查（Single-Shot Cockpit vs 旧多轮循环）

**V3 要求**：
- 第84条：Single-Shot Cockpit Manifest 一次性交付，严禁多轮低效提示词（系统发提示词->AI说好的->再发下一段）
- 第84条：心智启动四步序绝对不可颠倒：①照镜子（自省我是谁与底线）→②校准羁绊模型（关系厚度/冷战）→③定态度与语调→④审视用户世界与触发源
- 第78条：Wake Reason 为第一指针，严禁无差别全量扫描人生

**现有工程文档**：

| 文档 | 现状 | 冲突等级 |
|---|---|---|
| 【架构规划】C10 工作台与会话 | 描述“当前面板+结构化操作”“十三步循环”，未提 Cockpit Manifest，未提四步序 | **严重冲突** |
| 【工作台规格】第10章 十三步认知循环 | 明确写死 13 步：唤醒来源→紧急程度→当前世界→AI自身→观察计划→工具操作→认知产出→世界更新→帮助决策→后续任务→行动与等待→结果回写→AI自身更新。与 V3 四步法则直接冲突 | **宪法违宪级冲突** |
| 【总工任务书】M2-009 workspace.open | 定义初始工作包：当前时间、可见世界版本、唤醒原因、紧急事项、当前世界、任务摘要、承诺、未确认认知、AI自身状态、数据质量、操作范围。接近 Cockpit，但**缺失**：羁绊模型 `DIM_AI_RAPPORT` 切片、Capability Registry、带条件任务过滤后的就绪清单、四步序强制字段 | **缺失 40%** |
| 【总工任务书】M2-010 AI世界操作工具集 | 列出 world.view/zoom/shift 等，但未定义 `Cockpit Manifest` 的组装器，未定义四步序的校验器 | **缺失** |
| 【总工任务书】M2-012 AI Worker | 描述“首包 workspace.open；模型可多轮 tool calls”，这正是 V3 禁止的旧多轮模式 | **直接违背** |

**断层后果**：
- 若按 M2-012 实现，AI 每次唤醒先 open，再多次 tool calls，再 checkpoint，是典型的 **ReAct 多轮循环**，每次 tool 结果都要重新进 LLM，首字延迟 >3s，无法满足穿戴端 1秒
- 四步序未强制，AI 可能先看用户世界再看自己，出现“对冷战用户仍用亲密语气”的分寸灾难，违反第11条
- Wake Reason 第一指针未强制，AI 会无差别加载全量历史，违反第15条第5款

**必须修复**：重写 M2-009 为 Cockpit Assembler，新增 M2-012R 强制四步序校验。

### 2. 任务调度与 Token 浪费防范审查（条件驱动 vs 无脑遍历）

**V3 要求**：
- 第86条：待办任务必须带前置触发条件 `time_reached / context_matched / event_occurred / dependency_ready`，唤醒时仅挂载就绪任务，严禁盲目遍历空转
- 第15条第18款：禁止每次唤醒无差别执行全部待办（严重违宪）
- 第91条：`task.create_conditional(condition, action)`、`task.inspect_ready()`

**现有工程文档**：

| 文档 | 现状 | 冲突 |
|---|---|---|
| 【架构规划】C08 任务中心 | “十类任务、时间规则、状态、依赖”，但未提条件过滤引擎，未提 `condition_index` | 缺失 |
| 【总工任务书】M2-005 Task Center 核心状态机 | 定义 READY/WAITING_TIME/WAITING_EVIDENCE 等状态，提到 next_wake/deadline/recurrence，但**无** `context_matched / event_occurred / dependency_ready` 的 DSL，**无** condition_index | **严重缺失** |
| 【总工任务书】M2-006 定时/截止/周期/待办/跟进 | 仅细化时间规则，scheduled/deadline/recurring/todo/follow-up，未定义 `context_matched` 的 geo_fence、心率阈值、静默期等 | 缺失 50% |
| 【总工任务书】M2-002~004 Wake 调度 | 仅评估 Observation → Wake，未评估 Task condition → Wake。Task 到期是通过 scheduler 生成 Wake，但 scheduler 未定义条件索引扫描 | 缺失 |
| 【工作台规格】7.2 各类型规则 | 即时/定时/截止/待办/周期/跟进/观察/验证/维护/App，但激活方式仅时间，无 context/event 条件 | 缺失 |

**Token 空转实测推演**：
- 1年运行，Task 数保守 5k（生日提醒、跟进、观察、验证、维护）
- 旧方案：每次 Wake 加载 5k × 200 tokens = 1M tokens/次，50次/天 = 50M tokens/天，**直接破产**
- V3 方案：仅加载就绪 2-3 条，400 tokens/次，节省 99.96%

**断层后果**：按现有任务书实现，M2-015 一天虚拟人就会因 Token 账单爆炸，且违反宪法 15-18 一票否决。

**必须修复**：M2-005R 重写，增加 `TriggerCriteria` 结构与 `condition_index`，M2-009R 增加 `inspect_ready()` 过滤。

### 3. 上下文管理与真人老友响应延迟对齐审查（长会话三级流水线）

**V3 要求**：
- 第85条：三级流式心智流水线
  - 前台：活跃滑动窗口 1500 tokens / 5~8 轮，保证对话流畅
  - 后台：异步增量切片萃取 Claim 和事件锚点，每隔几轮或话题切换时静默萃取
  - 联想：超链接全局网络按需回捞，100K~1M 作为深邃战略储备
- 第85条：四层上下文动态组装：触发指针层→工作状态层→主动检索记忆层→近期对话缓冲层
- 第14条之一：1-3 句话法则，1秒首字响应

**现有工程文档**：

| 文档 | 现状 | 冲突 |
|---|---|---|
| 【架构规划】C10 | 仅说“面板、工具协议、十三步循环、检查点、上下文接续”，无三级流水线 | **完全缺失** |
| 【工作台规格】第3章 唤醒初始工作包 | 初始包字段完整，但无 1500 token 窗口，无后台萃取，无四层组装 | 缺失 |
| 【总工任务书】M2-009/011 | M2-009 open 返回摘要+索引，M2-011 session 快照 checkpoint，但**无任何 Issue 负责** Active Rolling Window 组装、Background Streaming Extract、Proactive Associative Recall | **全缺失** |
| 【总工任务书】M3-004/005 日/周/月总结 | 总结是新观察层，但总结任务是定时触发，非对话中的增量切片萃取 | 概念混淆 |

**断层后果**：
- 长对话 50 轮，上万字，若全部塞入 Prompt，必超 100K，首字延迟 >5s，且 Lost in the Middle
- 若仅保留 5-8 轮，无后台萃取，中间轮次的关键事实（如“老张是骗子”）丢失，AI 变金鱼脑，违反 V3 第85条“严禁把 AI 做成只有5轮金鱼记忆的弱智”
- 无四层组装，触发指针层与记忆层混在一起，无法保证 1秒首字

**必须修复**：新增 M2-016 Active Window Assembler，M2-017 Streaming Extractor，M2-018 Associative Recall Engine。

| 文档 | 现状 | 冲突 |
|---|---|---|

- 5D 滑动条若无物化视图，1s 粒度聚合 1年需扫描 31M 点，SQLite OOM

**必须修复**：重写 M1-012R 为 Co-occurrence Engine，增加 `co_search` 与 `navigate`，M1-010R 增加 5D Slider 物化视图。

### 5. 端侧边缘数据轻量化摄入对齐审查（防存储爆炸）

**V3 要求**：
- 第33条：
  1. IMU 严禁 50Hz/100Hz 高频灌水，仅提宏观状态+显著波形
  2. 心率平稳 2h 仅压缩平均值，异常波动才独立写入
  3. 摄像头全语义化文字存入，不存原始大图，端侧视觉模型
  4. 语音转文字+声纹指纹绑定未知实体，6个月冷热淘汰，核心关系保护
  5. 手机数据垃圾规则过滤+大模型智能提纯
  6. 大模型每日复盘智能清洗，垃圾物理删除但有用事件永存，需 DeletionLog

**现有工程文档**：

| 文档 | 现状 | 冲突 |
|---|---|---|
| 【架构规划】C01 接入与清洗 | “接收多源资料，校验时间、单位、来源、重复包，生成 Observation”，**无** 多模态降噪、声纹、图像语义化 | **完全缺失** |
| 【总工任务书】M0-007 Observation 契约 | 定义 source_kind/modality/value/unit/data_quality/raw_locator，**无** `source_confidence / signal_quality / voiceprint_ref / image_semantic` | 缺失 |
| 【总工任务书】M1-001 接入服务与去重 | 仅 source_event_id 去重+格式/单位/时间清洗，**无** IMU/心率波形提炼、图像语义化、声纹绑定、6个月淘汰、垃圾清洗 | **严重缺失** |
| 【工作台规格】 | 未提及 | 缺失 |

**存储爆炸推演**：
- 旧方案：IMU 50Hz × 86400s = 4.3M 条/天，心率 1Hz × 86400 = 86k 条/天，照片 10张×5MB=50MB/天
- 1年：IMU 1.5B 条，SQLite 直接崩
- V3 方案：IMU 仅宏观状态 ~100 条/天，心率平均+异常 ~50 条/天，照片语义文字 ~10 条×200 bytes，节省 99.99%

**必须修复**：M0-007R 增加边缘字段，M1-001R 重写为 Edge Lightweight Ingest Service，新增 M1-001a Voiceprint Lifecycle。

### 6. 穿戴物理形态与交互状态机对齐审查（FSM 零误触与三层 UI）

**V3 要求**：
- 第98条之一：柔性全屏手环 5-6cm×23cm，超宽频微震马达（触觉+骨传导），震动语义（单次微震=常规，连续强震=紧急），FSM：IDLE（骨传导断电休眠，绝对零误触）→TRIGGERED（震动后 5-10s 窗口）→通道A抬手看屏/通道B按耳骨传导/通道C超时

### 7. 虚拟世界测试与验收门对齐审查（V21~V30 高阶场景）
